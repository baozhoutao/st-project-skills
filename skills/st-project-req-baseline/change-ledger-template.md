# 变更台账模板

> 配套 [st-project-req-baseline](SKILL.md) 第四节使用。台账文件的存放位置按项目仓库
> 约定;`CR` 编号全项目顺号。核心纪律一句话:**登记 ≠ 接受,评估 ≠ 承诺,客户书面
> 确认才排期。**

## 使用规则(先读)

1. 任何基准外新诉求,不管来自谁、多小、看起来多「顺手」,一律先登记再说;
   当场只回「已登记,评估后答复」;
2. 「客户已确认」之前,条目不得出现在任何开发队列——口头「先做着回头补手续」不算;
3. 「客户已否决」「搁置」的条目保留在台账不删——将来客户再提同一诉求时有据可查;
4. 试运行分诊(st-project-pilot-ops)判为「非缺陷·新需求」的,直接流入本台账;
   与差异分不清的,按 SKILL.md 第四节判定规则先按差异登记报 PM 归类。

## 状态流转

`已登记` → `已评估` → `已报价`(商务动作)→ `客户已确认` / `客户已否决` / `搁置`
→ `已排期` → `已落地`

## 台账总表(放文件开头,一行一条)

| 编号 | 一句话诉求 | 提出人/日期 | 状态 | 确认凭证 |
|---|---|---|---|---|
| CR-001 | (示例)新增 X 报表按 Y 维度汇总 | 张三 / YYYY-MM-DD | 客户已确认 | (链接/归档号) |
| CR-002 | (示例)Z 流程增加一级审批 | 李四 / YYYY-MM-DD | 已评估 | — |

## 变更条目模板(逐条复制)

```markdown
### CR-NNN:<一句话概括>

#### 1. 登记(当场填)

- 提出人/日期/渠道:(谁、何时、口头/邮件/会上/试运行现场)
- 诉求原文:(尽量记原话;转述必须注明「转述」)
- 与基准的关系:签字基准(签字版+修正链)哪里没有 / 超出了什么——引用相关章节,
  写明「已核对,基准内无此项」;若落在 SRS 范围外章节明列的除外项上,注明条目
  (这正是当初写范围外章节的回报)
- 当场回复:「已登记,评估后答复」(禁当场承诺做/不做/免费)

#### 2. 影响评估(AI 出料)

- 范围:动哪些功能/对象/端/角色
- 工作量:区间(乐观/悲观)+ 依据(类比已交付项 / 平台原生能力 / 纯定制,纪律同
  st-project-pre-quote)
- 对已有功能的影响:回归面;是否触碰已验收功能(触碰的单独标出——已验收功能的
  返工风险与扯皮风险最高)
- 前提与假设:评估基于什么假设(数据量、接口、客户配合项);假设不成立时评估作废

#### 3. 计价与确认(人/商务动作,AI 只登记结果)

- 计价口径:引用合同变更条款第 X 条 / 售前假设与除外清单约定的变更计价方式
  (无明文约定 → 标注「无约定口径」并提示 PM;AI 不代拟计价条款)
- 报价:(商务填;AI 不填)
- 客户书面确认:凭证类型(签字/盖章/邮件确认)+ 归档位置或链接 + 日期
- 否决/搁置的:记录客户答复原文与日期

#### 4. 落地(确认后填)

- SRS 增量:新版本号/附录编号;该增量已完成客户书面确认(大变更走签字流程全程)
- 转入细化:对应工作项编号(进 st-project-req-refine)
- 完成核对:落地后回对本条「范围」栏,实际做的超出登记范围的部分回到步骤 1
  重新登记——变更蔓延同样是蔓延
```
