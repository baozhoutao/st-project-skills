# st-project-req-baseline — 唯一基准与变更管理

> 建设状态:可用(未实战) | 批次:第二批 | 主责 AI 岗位:AI 需求分析师 | 人类闸门:客户签字定基准;差异由 PM 拍板;变更由客户书面确认

**会话命名(2026-08-12 约定)**:进入本 skill 第一动作把会话标题设为
**`基准 | <动作:成稿/评审会/CR-N> | <MMDD>`**;工具机制与无工具豁免见 pm-test
「会话命名」权威条款。

**设计核心:项目只允许一份真相——客户签字的 SRS+验收标准。签字版本体永不改动,
此后的一切演化只有两条合法通道:基准内出入走「差异登记→人拍板→修正 N」,基准外
诉求走「变更台账→影响评估→客户书面确认」。两条通道全程留痕,AI 在任何一条上都
无权自裁。**

## 目标(防什么错)

验收扯皮的根源 100% 是这份文件没签好。本 skill 防四类错:

1. **基准糊着开工**——没有签字版就进开发,验收时「你说的」「我说的」各执一词;
2. **两个真值打架没人裁**——代码和文档各说各话,AI 看哪边顺眼按哪边来,基准悄悄漂移;
3. **范围蔓延**——新需求混在缺陷/优化里被免费做掉,做得越多亏得越多,验收还不认账;
4. **历史拍板被覆盖**——修正记录改来改去,将来归因/审计找不到「当时是谁按什么理由定的」。

## 角色与授权边界(硬)

- AI 是**成稿者、登记员与证据提供者**,不是基准的决定者:
  - 基准冲突(代码/文档/SRS 任意两方对不上)→ 只许登记上报,**禁止「看代码更合理
    就按代码来」**,也禁止反向的「文档为准」就自动改代码——选边永远是人的动作;
  - 变更评估:AI 出范围/工作量/影响面的料,**计价与折扣是纯商务决策**(同
    st-project-pre-quote 的边界),客户确认前 AI 不得给客户任何计价或做/不做的承诺;
- **签字是客户的动作,推动签字是 PM 的动作**:AI 的输出边界=可送审的成稿+签字流程
  的材料与状态提醒;不催客户、不代签、不以「客户口头说行」当签字;
- 差异拍板人默认 PM;拍板结果涉及客户利益(范围/业务口径变化)时,由 PM 决定是否
  升级为客户确认——升不升级 AI 不裁,只在登记条目里提示「疑似涉客户口径」。

## 输入

1. st-project-req-research 的结构化需求 + 对齐会确认结果(成稿主料);
2. 售前的**假设与除外清单**(st-project-pre-quote 产出)——范围边界「明确不含什么」
   的直接素材;
3. 合同中的变更条款(变更计价口径的引用源;项目没有明文变更条款 → 登记为风险报 PM,
   不由 AI 代拟条款);
4. 运行期:任何人报来的「不一致线索」与「新诉求」(开发自测、验收走查、试运行分诊、
   客户反馈都是入口)。

## 产出(逐项可核对)

| # | 产出 | 核对点 |
|---|---|---|
| 1 | SRS(含验收标准) | 范围边界含「明确不含什么」;验收标准逐功能可实测;格式过 st-project-std-docs 自检清单 |
| 2 | 签字归档 | 签字版独立归档、永不改动;版本号 V1.0 起;归档与版本记录符合 std-docs 版本纪律 |
| 3 | 差异登记台账 | 按 [diff-ledger-template.md](diff-ledger-template.md);逐条编号;每条有现象/两边说法/影响面/拍板记录;修正编号只增不改 |
| 4 | 变更台账 | 按 [change-ledger-template.md](change-ledger-template.md);每条有影响评估三件套与客户书面确认凭证;未确认不排期 |

## 一、成稿:结构化需求 → SRS + 验收标准

格式、封面、版本记录、Word 工艺全按 st-project-std-docs,本节只写内容要求。

### 范围边界:必须写「明确不含什么」

「范围外」章节的素材有三个来源,逐条收进去:

1. **售前假设与除外清单的除外项**——一条不落地搬进来。售前答应过「不含」的东西
   如果不进 SRS,签字后等于重新变成「含」;
2. **调研中客户提过、对齐会明确「本期不做」的需求**——写明「X 本期不实现,后续
   如需走变更流程」,这行字是将来变更谈判的地基;
3. **容易被默认「顺带包含」的通用能力**——历史数据迁移范围、接口对接、性能指标、
   并发规模、旧系统并行期,逐项写「含到什么程度」或「不含」。

自检:只写「含什么」、不写「不含什么」的 SRS 不许送审——范围外章节为空 = 没做
这一步,不是项目真的没有范围外。

### 验收标准:逐功能写到可实测粒度

- 每条格式:**前置(角色/数据)+ 操作 + 「在哪里看:看到什么」**。这与
  st-project-pm-case 的预期结果格式同构——写好一条,pm-case 起草用例就能直接搬
  一条;写坏这里,用例→验收→回归全链路遭殃。
- 判定标准:一个不了解项目的人,按这条做一遍,能无歧义判「过/不过」。
- **禁不可测表述(出现即返工)**:「界面美观」「操作流畅」「性能良好」「符合习惯」
  「友好提示」。确有体验类要求 → 转成可测的代理指标(如「列表页 X 条数据下打开
  时间 ≤ N 秒」);定不出代理指标就做成疑点问客户,不写糊话。
- 涉及角色权限的功能,验收标准必须含至少一条「无权者看不到/做不了」的反向条目。
- 成稿中拿不准的值按 st-project-req-research 的选择题纪律收敛(若 A 则…若 B 则…,
  附建议与理由);**送审稿里不留【待确认】**——预审和评审会就是清疑点的场合,
  签字版必须零悬案。

## 二、签字流程:预审 → 评审会 → 签字归档

| 步 | 做什么 | 产出/凭证 | 卡住怎么办 |
|---|---|---|---|
| 1 预审 | 送审稿(V0.x)发客户预审,附「重点看什么」引导(范围外章节、验收标准、疑点拍板结果) | 发送记录 + 客户反馈清单 | 客户不看/没空 → 报 PM 安排评审会现场逐章过;预审缺席不豁免评审 |
| 2 评审会 | 逐章确认;现场改的内容当场记录;疑点当场拍板 | 评审纪要(改动清单+拍板清单) | 现场定不了的点 → 明确责任人与期限,SRS 对应处标注,不带着悬案签字 |
| 3 修订定稿 | 按纪要修订出定稿版,回发客户核对「改的就是说好的」 | 定稿版 + 客户「无异议」回复 | 客户又提新意见 → 回步 2 逻辑:小点邮件确认,大点再开会 |
| 4 签字归档 | 客户签字(纸签扫描或书面确认的电子版);签字版按 std-docs 版本纪律单独归档,版本号定 V1.0 | 归档的签字版文件 | 签字拖延 → 报 PM 推动;**墨迹未干也比口头强**:退而求其次至少拿到客户邮件/IM 书面确认并归档 |

### 未签字不进开发(门禁,硬)

- 基准未签字,工作项不得进入细化与开发队列;st-project-req-refine 的「① 对基准」
  即以本基准为锚。
- 唯一例外:PM **书面**明示「以 X 文档 V 版为临时基准先行启动」并自担风险——AI
  不得建议、不得默认走例外;例外启动的工作项必须逐个标注所依据的临时基准与版本,
  签字后逐个回对。

## 三、运行期:差异登记(基准内两个真值打架)

**什么算差异**:基准内的同一件事,代码、文档、SRS(或任意两方)说法不一致——
实现与 SRS 不符、SRS 前后自相矛盾、工作项描述与 SRS 冲突,都算。

流程(逐条走,台账模板见 [diff-ledger-template.md](diff-ledger-template.md)):

1. **登记**:发现出入(自己撞见、测试报来、下游 skill 退回)→ 立即在差异台账登记
   一条,编号 `DIFF-NNN` 全项目顺号:现象(在哪看到什么)/ 两边各怎么说(逐方引用
   原文 + 出处锚点)/ 影响面(涉及哪些功能、是否疑似涉客户口径);
2. **上报拍板**:攒批报 PM(阻塞开发的即时报);报的是登记条目本身;AI 的倾向与
   理由**仅作参考项**,条目里写明「倾向不构成默认,等拍板」;
3. **出修正**:拍板后落「修正 N」——N 全项目顺号,记录:对应 DIFF 编号 / 拍板人
   与日期 / 结论(以哪边为准,或第三种口径)/ 波及动作(改 SRS?改代码?都改?);
4. **同步落地**:按修正结论更新 SRS 工作版(版本记录注明「按修正 N」),需改代码的
   转为工作项走正常开发流;**签字版原样不动**——当前有效基准 = 签字版 + 修正链,
   读基准必须两样一起读。

硬纪律:

- **AI 无权自裁(最硬)**:两个真值打架时,任何「按更合理的一边先做着」都是违规,
  包括「显而易见是笔误」——笔误也登记,只是标注「疑似笔误,建议快裁」;
- **修正编号只增不改**:历史修正是审计链;拍板被推翻 = 出新修正声明「推翻修正 N,
  改为…」,不许回去改写修正 N 的正文;
- 拍板前,该差异涉及的开发**冻结在争议点上**:争议点之外可继续,争议点上禁止
  「两头下注各做一半」。

## 四、运行期:变更台账(基准外的新诉求)

**什么算变更**:签字基准(签字版+修正链)里没有的新功能、新范围、口径扩大。
判定拿不准「是差异还是变更」→ 先按差异登记报 PM 判定归类;**归类本身不由 AI 裁**
——归成变更就涉及计价,商务敏感。

流程(台账模板见 [change-ledger-template.md](change-ledger-template.md)):

1. **登记**:新诉求(客户提的、试运行现场冒出来的、评审会后追加的)→ 变更台账登记
   `CR-NNN`:诉求原文(谁、何时、原话)/ 与基准的关系(引用章节说明「查过了,
   基准里没有」)。登记不等于接受——当场只回「已登记,评估后答复」,禁当场承诺
   做/不做/免费;
2. **影响评估**(AI 出料):范围(动哪些功能/对象/端)/ 工作量(区间+依据,纪律同
   st-project-pre-quote)/ 对已有功能的影响(回归面;是否触碰已验收功能——触碰的
   单独标出,返工风险最高);
3. **计价**:计价口径**引用合同变更条款**(或售前假设与除外清单里约定的变更计价
   方式);AI 只出工作量与影响评估,报价数字由商务出;
4. **客户书面确认后才排期**:确认凭证(签字/盖章/邮件确认)归档并挂台账;**没有
   书面确认的变更不进开发队列**,口头「先做着回头补手续」不算数;
5. **落地**:确认后的变更转为 SRS 增量(新版本或附录,至少完成该增量的客户书面
   确认,大变更走「二、签字流程」全程),再进 st-project-req-refine 细化。

与 st-project-pilot-ops 的衔接:试运行分诊出的「非缺陷·新需求」全部流入本台账,
**新需求绝不当缺陷修**——这是试运行期范围失守的头号漏洞;分诊归类有争议时,按
上面的判定规则报 PM。

## 防错要点(硬纪律速查)

1. **AI 无权自裁基准冲突(硬)**:登记上报是唯一合法动作;「按代码来」「按文档来」
   「显然是笔误」都不是;
2. **修正编号只增不改(硬)**:推翻旧拍板 = 出新修正,不改历史;
3. **签字版是文物(硬)**:签字版发现错误也不改它,演化全走修正链与新版本
   (同 std-docs 版本纪律);
4. **验收标准禁不可测表述(硬)**:「界面美观」类出现即返工;体验要求转代理指标,
   转不出就进疑点;
5. **范围外章节不许为空**:没有「明确不含什么」的 SRS 不许送审;
6. **未签字不进开发(硬)**:例外只有「PM 书面明示临时基准」一条路;
7. **变更无书面确认不排期(硬)**:登记≠接受,评估≠承诺,确认凭证归档才排期;
8. **差异/变更归类不由 AI 裁**:归类影响计价;拿不准一律先按差异登记报 PM。
