# st-project-req-refine — 工作项细化与就绪门禁

> 建设状态:可用(未实战) | 批次:第一批 | 主责 AI 岗位:AI 需求分析师 | 人类闸门:PM 判 DoR

**会话命名(2026-08-12 约定)**:进入本 skill 第一动作把会话标题设为
**`细化 | <模块或批次> | <MMDD>`**;工具机制与无工具豁免见 pm-test「会话命名」
权威条款(全库前缀总表在该条款)。

**设计核心:把「需求写清楚了没有」从感觉题改造成证据题——就绪的唯一证明是 AI 真的
仅凭描述写出了测试计划草稿并挂在工作项上,而不是 AI 说一句「我觉得清楚了」。**

## 目标(防什么错)

模糊需求是全流程最贵的返工源头:细化期一句话能补掉的缺口,漏到开发期变成一次返工,
漏到验收期变成一场扯皮。本 skill 防三类错:

1. **模糊需求进开发**——开发按自己的理解做,验收按 PM 的理解判,两头对不上;
2. **细化空对空**——AI 拿开放式问题轰炸 PM(「这里想怎么做?」),对齐会开成发散会;
3. **细化夹带实现**——工作项写死了表结构/接口/组件,把 st-project-dev-design 的设计
   空间提前锁死,还让 PM 在自己看不懂的技术字段上签了字。

## 角色与授权边界(硬)

- AI 是**整理者与证据提供者**,不是需求的决定者:拿不准的值(边界值/角色/文案/多种理解)
  一律进疑点选择题,禁止自作主张填「合理值」;
- **切「待开发」是 PM 的签字动作**:AI 的输出边界 = 七要素齐全的描述 + 就绪证据 + 判定
  建议。PM 明确授权「判过即切」的项目才可由 AI 代切,且代切时必须在工作项上留判定依据;
- 细化会话**不动代码**:可读现状实现用于理解与提问,但禁止开分支/改代码,且禁止从现状
  实现反推验收标准——「实现成什么样」不是「需求该是什么样」的依据
  (与 st-project-pm-case「预期只来自需求」同一红线);
- 状态的具体标签名/看板列按项目仓库约定读取(参见 st-project-std-git),本 skill 只约定
  「待细化」「待开发」两个过程状态。

## 输入

1. **签字基准**(上游 st-project-req-baseline 的产出):SRS + 验收标准,细化的唯一依据;
2. 一条粗需求,或已存在的「待细化」工作项;
3. 项目仓库的工作项模板与状态约定(从项目配置/模板目录读取,本 skill 不写死)。

项目尚无签字基准(如首个迭代基准未成稿)→ 经 PM 明示认可后以当前最新版需求文档为准,
并在工作项里写明所依据的文档与版本;禁止 AI 自行决定「拿原始说明书顶一下」。

## 产出(逐项可核对)

| # | 产出 | 核对点 |
|---|---|---|
| 1 | 细化后的工作项描述 | 七要素逐项能在描述里指出对应段落;全文只有业务语言 |
| 2 | 就绪证明:测试计划草稿 | 以评论挂在工作项上;逐行带「依据」锚点;「写不出的点」为无 |
| 3 | 判定结论 | 就绪:DoR 三项逐项给证据,报 PM 切「待开发」;不就绪:按打回模板列缺口,保持「待细化」 |
| 4 | 疑点清单(有歧义才有) | 选择题形式,每题带建议+理由;拍板结果已回填描述正文 |

## 流程

每步三件事:做什么 → 产出什么 → 卡住怎么办。

### ① 对基准(范围门禁)

- 做什么:核对这条需求在不在签字基准内,找到对应章节。
- 产出:基准锚点(写进工作项描述的「业务场景」段)。
- 卡住:基准里找不到/与基准冲突 → **停**,转 st-project-req-baseline 的变更/差异登记
  流程;禁止把基准外需求悄悄细化进开发队列——那是范围蔓延的标准入口。

### ② 定粒度(要不要拆)

- 做什么:一个工作项 = 一次可独立开发、独立验收的业务能力增量。命中任一拆分信号就考虑
  拆:验收标准超过 ~10 条;含多个互不依赖的入口/端;内部有明显先后依赖链。
- 产出:单个工作项,或拆分后的一组(每个独立走 ③~⑦,互相标注依赖)。
- 卡住:怎么拆都别扭 → 通常是需求本身没想清楚,把 2~3 个候选拆法做成选择题并入 ④。

### ③ 七要素核对

七要素(逐项「合格 vs 不合格」对照示例与核对点见 [checklist.md](checklist.md)):

1. 业务场景描述——谁、在哪个流程环节、为什么
2. 触发操作——在哪个端(Console/手机 H5)、具体页面/入口/按钮,含可用条件;
   本工作项引入/改动的**全部**用户可点按钮(列表/行/批量/详情)逐个列,不只主入口
3. 输入与字段(业务面)——本工作项涉及的对象与字段逐项列出,来源与格式齐全,
   含非输入字段(系统算/带出/列表显示列);技术落点归 dev-design
4. 校验规则——每条 = 触发条件 + 系统行为 + 提示,三件套成对
5. 输出/反馈——界面变化 + 数据变化 + 联动影响
6. 依赖关系——编号引用并注状态;无依赖显式写「无」
7. 验收标准——「什么现象出现即通过」,含权限反例

- 做什么:对照 checklist 给每项判「有 / 缺 / 模糊」。
- 产出:核对结果(缺与模糊项 = ④ 的疑点原料、⑦ 的打回原料)。
- 卡住:描述粗到没法逐项核 → 不逐项空转,带着「基准里它该是什么」直接进 ④。

### ④ 疑点收敛(有歧义才做)

- 做什么:按 [templates.md](templates.md) 模板一输出「AI 理解与疑点」评论:理解复述 +
  假设清单 + 选择题(若 A 则…若 B 则…,附建议与理由,理由优先引用基准锚点)。
- 硬规则:疑点**一律选择题**,禁止开放式问题;**攒成一批一次提交**,不逐条打断 PM;
  每题选项互斥且写明连带影响。
- 产出:疑点评论挂工作项,等 PM 拍板。
- 卡住:PM 迟迟不拍板 → 该项保持「待细化」,不阻塞其他工作项,**禁止按自己的建议先行
  细化开工**;拍板答案与基准冲突 → 回 ①,转差异登记,不擅自选边。

### ⑤ 补写描述

- 做什么:按七要素结构重写/补全工作项描述;PM 拍板的答案**合并进描述正文**——描述是
  唯一真值,评论区不是,下游(开发/用例起草)只读描述。
- 产出:七要素齐全、纯业务语言的工作项描述。
- 卡住:某要素只有 PM 口头说法没落字 → 把口头说法写进描述并请 PM 确认;禁留
  「详见会议讨论」这类悬空引用。

### ⑥ 自证就绪:真写测试计划草稿

- 做什么:**只看工作项描述**(不翻基准、不翻代码、不翻对话记录),按
  [templates.md](templates.md) 模板二写测试计划草稿:每行测试点标注依据描述的哪一段;
  写不出或只能靠假设写的,如实列进「写不出的点」。
- 产出:测试计划草稿,以评论挂在工作项上——这就是 DoR 判 1 的证据。
- 卡住:草稿写不下去 → 那正是描述的缺口,禁止靠假设硬写完,回 ④/⑤ 补;
  「写不出的点」非空 = 判定必不过,直接进 ⑦ 打回。

### ⑦ DoR 判定与流转

三项判定全部操作化成可核对点:

| DoR 判定 | 核对点(过/不过一眼可判) |
|---|---|
| 1. 仅凭描述能写出完整测试计划 | 工作项上存在 ⑥ 的草稿评论;逐行有依据锚点;「写不出的点」为无 |
| 2. 校验规则的成功/失败反馈全部写明 | 描述里每条校验规则三件套齐(条件+行为+提示);草稿里每条规则至少一正一反两条测试点;描述中无「合法/正确/正常/相关」等不可判定词 |
| 3. 依赖关系已标注、可判并行 | 描述有「依赖」小节;依赖逐个编号引用并注当前状态;无依赖显式写「无依赖,可并行」——留空不算 |

- 三项全过 → 报 PM 判 DoR(附三项证据),PM 确认后切「待开发」;
- 任一不过 → 按 [templates.md](templates.md) 模板三写打回意见(缺什么 / 补什么 /
  补到什么程度算好),保持「待细化」;
- 卡住:PM 与 AI 判定不一致(PM 说够了,AI 核对不过)→ PM 有最终裁量权,但 AI 必须把
  不过的核对点写在工作项上留痕——将来返工归因时有据可查。

## 防错要点(硬纪律)

1. **只写业务,不写实现(硬)**:描述里出现存储结构/接口/技术组件选型 = 越界,删掉留给
   st-project-dev-design;业务对象与业务规则用客户的语言写。**这条线的准确位置
   (2026-08-12 PM 拍板)**:字段与按钮的**业务定义**(业务名/类型/数值边界/来源/
   显示位置/可见条件)是要素 2、3 的本分,低代码平台上它们就是业务本身,PM 看得懂
   也该签;越界的是**技术落点**——落哪个对象、复用已有字段还是新建、API 名、
   用 hook 还是自动化、原生视图还是自定义页面,这些归 dev-design。
   「要什么交互」写细化,「用什么承载」不写。
2. **细化可查配置清单对齐命名(2026-08-12 加入)**:写字段/按钮业务定义时,**允许只读
   查阅** st-project-dev-inventory 派生的对象×字段/按钮清单,对齐既有叫法、发现复用
   候选(发现疑似已有同义字段 → 写进疑点选择题让 PM 选,不自行拍复用)。查清单对齐
   词汇 ≠ 从现状实现反推验收标准——后者仍然全面禁止:清单只许影响「叫什么」,
   不许影响「预期是什么」。
3. **细化不扩范围(硬)**:细化 = 把基准内的需求写清楚,不是顺手加功能;细化中
   「发现还需要……」的一律走 ① 的变更通道。
4. **疑点一律选择题、成批提交(硬)**:开放式问题是把思考成本推给 PM;逐条打断是把 PM
   当同步接口用。
5. **拍板必回填(硬)**:PM 在评论/会上拍的板不合并进描述正文 = 制造第二真值,下游只读
   描述,必踩坑。
6. **就绪证明必须真写出来(硬)**:「我确认仅凭描述可以写出测试计划」这句话不是证据,
   挂在工作项上的草稿才是。
7. **草稿 ≠ 验收用例(硬)**:草稿唯一用途是证明描述可测;正式验收用例由
   st-project-pm-case 起草并经 PM merge 定稿,草稿只是其素材,不构成约束、不回填维护。
8. **AI 不替 PM 拍板(硬)**:写不出可判定验收标准的点,说明需求本身没定,标【待确认】
   上交,不填「合理值」。

## 反向优化:开发者介入率(改模板,不是骂 AI)

- **定义**:统计周期内,过了 DoR 进入开发后仍需要人介入需求层面的工作项占比。介入 =
  开发中追问需求 / 因需求理解偏差被打回返工 / 开发者替 PM 补了需求决定。纯技术介入
  (平台缺陷、环境问题)不计入。
- **阈值**:连续两个统计周期 > 20%~30% → 判为细化质量问题,不是 AI 能力问题,更不该让
  开发者长期救火。
- **处置**:逐个介入案例归因——七要素哪一项没写住?哪个疑点没问出来?把教训落成
  [checklist.md](checklist.md) 对应要素的新「不合格示例」或 [templates.md](templates.md)
  的新条目,走 st-project-meta-retro 落库。
- **禁止的处置**:要求开发者「以后多问问」(把门禁成本转嫁下游);给 AI 加「更仔细」类
  不可执行指令。一时归因不到具体要素的案例先记录,同类攒满三例再立新规则。
