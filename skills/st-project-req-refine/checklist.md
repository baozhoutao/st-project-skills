# checklist — 七要素对照与细化核对单

> 用法:流程 ③「七要素核对」时逐项对照,⑦ 判定前把核对单整个过一遍。
> 示例全部是通用业务示例(报销类),只示范「写到什么程度算合格」——判断时拿**结构**对,
> 不拿业务对;任何具体项目的业务内容都不该出现在本文件里。
> 本文件是活文档:开发者介入案例归因出的新「不合格示例」要追加进对应要素。

## 七要素「合格 vs 不合格」对照

### 1. 业务场景描述 — 谁、在哪个流程环节、为什么

| | 示例 |
|---|---|
| ❌ 不合格 | 「增加导出功能」——不知道谁用、在什么流程里用、为什么用 |
| ✅ 合格 | 「财务专员每月初要向上级单位报送上月报销汇总,需要在报销单列表按月份筛选后一键导出 Excel 存档」 |

核对点:能回答「谁 / 在哪个流程环节 / 为什么」三问;写明基准锚点(SRS §x.x)。

### 2. 触发操作 — 具体入口

| | 示例 |
|---|---|
| ❌ 不合格 | 「系统支持导出」——没有入口,开发和测试都不知道从哪进 |
| ✅ 合格 | 「报销单列表页工具栏【导出】按钮;列表无筛选结果时按钮置灰」 |

核对点:页面/入口/按钮名齐全;新增入口写明放在哪个页面哪个位置;入口的可用/不可用
条件写明;**写明使用端(Console / 手机 H5 / 双端,2026-08-12 加入)**——H5 的入口
与交互形态和 Console 不同,不写端 = 开发默认只做 Console,手机场景到验收才发现缺;
端的取值以蓝图「端覆盖」精判为准,超出蓝图端覆盖的写法是变更信号,回 req-baseline。
**按钮列全(2026-08-12 PM 拍板)**:本工作项引入或改动的**每一个**用户可点按钮——
列表工具栏 / 列表行 / 批量操作 / 详情页——都属本要素,逐个列名、逐个写可见/可用
条件,不只写主触发入口;**漏列的按钮 = 没提的需求,开发不做不算错**。交互形态需求
(向导分步/看板拖拽等)在此用业务语言写、可挂原型图;用原生视图还是自定义页面承载
归 dev-design 选型,不在此拍。

### 3. 输入与字段(业务面)— 对象、字段、来源、格式

| | 示例 |
|---|---|
| ❌ 不合格 | 「用户填写相关信息」 |
| ✅ 合格 | 「导出范围 = 当前筛选结果(系统带出);文件格式 = xlsx(固定);导出列 = 单号、申请人、金额、状态,与列表列一致」 |
| ❌ 不合格(数字) | 「报销金额:数字类型」——小数位/上下限/能否为负全没说,开发只能按平台默认建模 |
| ✅ 合格(数字) | 「报销金额:数字,单位元,保留 2 位小数(四舍五入),必须 > 0(0 与负数不合法),上限 99999.99」 |

核对点:逐项列出;每项标来源(用户填 / 系统带出 / 上游数据);有格式或取值范围;
有默认值的写默认值。**数字类型逐项写全「数值四件套」:① 小数位数(含舍入规则)
② 最小值(能否为 0 / 能否为负)③ 最大值(量级上限)④ 单位与显示格式**——四件套
缺项,开发侧只能拿平台默认精度与无界范围建字段,「负数存得进、超量级不拦、精度
对不上」这类缺陷全在验收轮才炸出来(2026-08-12 开发实战教训)。越界后的系统行为
(拦截/提示)写进要素 4 校验规则,与此处的边界声明成对。

**覆盖面升级为「对象与字段」(2026-08-12 PM 拍板)**:本要素不止用户输入项——
本工作项涉及的**每个业务对象、每个字段**都要列:系统算出来的(状态、汇总)、
带出后只读的、列表要显示的列,一样逐项写业务名 / 类型(数字带四件套)/ 来源
(用户填 / 系统算 / 带出)/ 显示在哪(列表列 / 详情 / 仅后台)。低代码平台上
字段就是业务本身,这层 PM 看得懂、也该由 PM 签。**仍然禁写技术落点**:落哪个
对象、复用已有字段还是新建、API 名,归 dev-design。写字段时**允许只读查
dev-inventory 派生的对象×字段清单**对齐既有叫法、发现复用候选(疑似已有同义
字段 → 进疑点选择题请 PM 拍,不自行定复用);查清单只许影响「叫什么」,
不许影响「预期是什么」——从现状反推验收标准仍然全面禁止。

### 4. 校验规则 — 条件 + 行为 + 提示,三件套成对

| | 示例 |
|---|---|
| ❌ 不合格 | 「金额要合法」「做好必要的校验」 |
| ✅ 合格 | 「金额 ≤ 0:拦截保存,提示『金额必须大于 0』;金额 > 50000:允许保存,单据状态置『待总监审批』并通知总监」 |

核对点:每条规则 = 触发条件 + 系统行为 + 提示文案/后续状态,三件套成对;成功路径与
每条失败路径都有明确反馈;禁「合法 / 正确 / 相关 / 正常」等不可判定词。

### 5. 输出/反馈 — 界面变化 + 数据变化 + 联动影响

| | 示例 |
|---|---|
| ❌ 不合格 | 「导出成功」 |
| ✅ 合格 | 「点击后浏览器下载 xlsx,文件名『报销汇总-年月』;页面提示『导出成功』;文件行数与当前筛选结果条数一致」 |

核对点:界面反馈、数据变化、联动影响(通知 / 台账 / 统计口径)逐项写;没有联动要显式
写「无联动影响」,不留空。

### 6. 依赖关系 — 编号引用,显式无

| | 示例 |
|---|---|
| ❌ 不合格 | (整段没写)/「依赖前面的功能」 |
| ✅ 合格 | 「依赖 #12(报销单列表筛选)已完成;与 #15(报销单打印)无依赖,可并行」 |

核对点:依赖逐个用工作项编号引用并注当前状态;无依赖显式写「无依赖,可并行」——
留空 ≠ 无依赖。

### 7. 验收标准 — 什么现象出现即通过

| | 示例 |
|---|---|
| ❌ 不合格 | 「导出功能正常可用」 |
| ✅ 合格 | 「财务角色登录,筛选 3 月报销单共 N 条,点【导出】得到 N 行 xlsx 且列与列表一致 → 通过;无导出权限的角色在列表页看不到【导出】按钮 → 通过」 |

核对点:每条 = 「在哪里看:看到什么现象即通过」;含权限反例;不看对话记录的第三方能
照着判定;禁「美观 / 流畅 / 友好」等不可测表述。

## 细化核对单(⑦ 判定前逐工作项过一遍)

**范围**

- [ ] 需求在签字基准内,基准锚点已写进描述
- [ ] 粒度合适:可独立开发、独立验收;不合适的已拆分且互标依赖

**七要素**

- [ ] 1 业务场景:谁 / 流程环节 / 为什么 三问可答
- [ ] 2 触发操作:入口具体到页面与按钮,含可用条件;写明端(Console/H5/双端);本项全部新增/改动按钮(列表/行/批量/详情)逐个列名带可见条件
- [ ] 3 输入与字段:涉及对象与字段逐项列全(含系统算/带出/列表显示列),有来源与格式;数字类型逐项带数值四件套(小数位/最小值/最大值/单位),含能否为 0、能否为负;无技术落点(复用/新建/API 名)字样
- [ ] 4 校验规则:条条三件套(条件 + 行为 + 提示)
- [ ] 5 输出/反馈:界面 + 数据 + 联动齐全
- [ ] 6 依赖:编号引用注状态,或显式「无依赖,可并行」
- [ ] 7 验收标准:条条可判定,含权限反例

**纪律**

- [ ] 全文业务语言,无表结构/接口/组件等实现细节
- [ ] 疑点已按选择题模板拍板,答案已回填描述正文(评论区无悬空拍板)
- [ ] 没有从现状实现反推的验收标准

**就绪证据(DoR)**

- [ ] 测试计划草稿已挂工作项,逐行带依据锚点
- [ ] 草稿「写不出的点」为无
- [ ] 草稿覆盖:主流程 ≥1;每条校验规则一正一反;权限一正一反;联动断言(描述有联动才要)
