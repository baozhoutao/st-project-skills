# st-project-dev-review — 合并前代码评审

> 建设状态:可用(未实战) | 批次:缺口补强(2026-08-14 补建) | 主责 AI 岗位:AI 评审工程师(评审子 agent) | 人类闸门:决策清单(升级项)

**设计核心:2026-08-12「调度员自主合并 PR」拍板后,合并链路上不再有任何环节读代码——
自测与验收是黑盒(看功能不看 diff),收单核实明文只验流程完整性,反静默降级的符合度
清单由开发子 agent 自己填。本 skill 把评审闸门装回链路:AI 写、AI 测之外,再加一个
_独立读代码_ 的 AI,专防只有代码能暴露、黑盒结构性看不见的那几类错。**

| 防什么错 | 为什么别的关口防不住 |
|---|---|
| 越界改动(动了工作项边界外的老功能/共享资产,没走 dev-design) | 黑盒验收只测本项功能,破坏面在别处;改动面只在 diff 里可见 |
| 静默降级(清单标 ✅,代码里是 TODO/被注释的校验/简化实现) | 4.5 清单是自述;收单核实只查清单格式,不查真伪 |
| 三禁违规(动平台包/patch 依赖/绕行实现) | 表面功能可能正常,炸在平台升级时 |
| 安全与数据风险(越权入口、无校验写库、明文敏感信息) | 正常路径的黑盒测试测不到 |
| 硬拍板未落地(数字字段四件套、std-copy 文案红线) | 自测可能恰好没踩到默认值边界 |

## 定位:工序壳,不是评审教程(硬)

通用代码质量分析**直接用 Claude Code 内置 `/code-review`**,本 skill 一条不复述它的
检查项——工具升级白得红利。本 skill 只固化**工序**:谁执行、输入是什么、卡在哪、
库专属核查哪几条、发现怎么分级、每级走哪个出口、留什么痕。

## 上下游边界(硬)

| 方向 | 对接 skill | 交接约定 |
|---|---|---|
| 上游 | [st-project-pm-dispatch](../st-project-pm-dispatch/SKILL.md) ⑤ | 只接**收单核实全项通过**的 PR——流程完整性先过关,评审不替收单核实兜底 |
| 下游(过) | pm-dispatch「调度员自主合并」 | 阻塞/应修清零的评审报告是自主合并入场券之二(之一是收单核实) |
| 下游(修) | [st-project-dev-issue](../st-project-dev-issue/SKILL.md) | 应修/阻塞的修复归**原开发子 agent**在原分支追加提交(不切状态、不改处理人);评审子 agent 零代码 |
| 下游(升级) | pm-dispatch ⑥ 决策清单 | 静默降级证据坐实、二轮复查不清零 → 升级,不退回 |

**边界三条**:评审不判功能达标(归验收线);评审不重复收单核实(流程项已验过);
评审子 agent 只读——发现问题只报告,一行修复代码都不写。

## 角色与独立性(硬)

评审子 agent 由调度员派发,**冷启动、指定 Opus 模型**(与开发/盲审子 agent 同口径),
输入只给三样:

1. 工作项全文(含验收标准);
2. PR diff(全量);
3. 步骤 4.5 需求符合度清单原文。

**禁给开发子 agent 的返回报告、对话记录、自测报告**——评审对象恰恰包括「清单自述与
代码是否相符」,带着开发者的解释去看代码,评审就成了给自述背书。与 pm-test 盲审
同构:切断执行上下文污染,**独立的是判断**。

开发子 agent 提 PR 前自跑 `/code-review` 是值得鼓励的卫生动作(问题越早发现越便宜),
但**不是本闸门、不留痕不算数**——自评也是自述,不采信。

## 评审档位(复用 dev-design 风险分级,不造新分类)

| 档位 | 适用 | 内容 |
|---|---|---|
| 轻量档 | dev-design 低风险(纯新增、单模块)且 diff 小 | `/code-review` 常规档 + 专属核查四条(**不可省**) |
| 全量档 | dev-design 高风险(改已有/跨模块)、返修单、diff 大、或拿不准 | `/code-review` 高档 + 专属核查四条 + 被改已有代码的**调用面抽查**(谁在用被改的函数/字段/组件,有没有被顺手改坏) |

档位判定信号在派发时已存在(分级声明/放行记录),调度员随评审派发注明;拿不准一律
全量档(与 dev-design 同一不对称成本裁决:误判轻量的代价远大于多花一档)。

## 库专属核查四条(内置工具不知道的纪律,逐条必查)

| # | 查什么 | 怎么查 | 坐实 = |
|---|---|---|---|
| 1 改动面越界 | diff 是否触碰工作项边界外的已有功能/共享资产 | diff 文件与改动逐个对照工作项描述 + 分级声明/放行记录 + 扩围/搭车留痕;**修改**(非新增)的部分逐处问「这处改动是本项要求的吗」 | 越界且无放行/无留痕 → 🔴 阻塞 |
| 2 降级对账 | 4.5 清单 ✅ 条目在代码里是否真的完整实现 | 逐条 ✅ 定位到实现代码;找 TODO/FIXME、被注释掉的校验、比需求少的分支、被简化的交互 | 清单 ✅ 与代码矛盾 → 🔴 阻塞(静默降级证据,按自述失真口径) |
| 3 三禁痕迹 | 动平台包内容、对依赖目录打补丁、绕行实现 | diff 路径含依赖/平台目录;patch 类文件;绕开平台标准机制的自造实现 | 任一坐实 → 🔴 阻塞 |
| 4 硬拍板落地 | 数字字段四件套(小数位/最小/最大/单位,dev-issue 步骤 3);新增用户可见文案过 std-copy 红线 | 新建/修改的数字字段逐个核四件套是否显式定义;diff 中新增用户可见字符串逐条过红线 | 未落地 → 🟡 应修 |

## 发现分级与处置(硬)

| 级 | 定义 | 处置 | 阻塞合并? |
|---|---|---|---|
| 🔴 阻塞 | 纪律违规或高危:越界无放行、静默降级证据、三禁、安全/数据风险、夹带并行项文件 | 静默降级证据/自述失真 → **直接升级决策清单,不退回**(与收单核实「自述失真」同口径);其余 → 退回原开发子 agent 修复,一次机会 | 是 |
| 🟡 应修 | 普通代码问题但影响正确性:边界条件、错误处理缺失、明显缺陷、硬拍板未落地 | 退回原开发子 agent 原分支追加提交(不切状态、不改处理人,dev-issue 既有条款) | 是,修完复查即合 |
| ⚪ 记录 | 技术债/风格/可维护性建议 | 写进评审报告留痕;值得跟踪的按 dev-issue「独立问题照立单」立单(查重口径同 pm-test ⑥) | **否**——评审卡在风格上,吞吐拍板就白拍了 |

**轮次纪律**:修复交回后,复查**只查修复点 + 是否引入新问题**,禁重开全面评审——
否则每轮都能挑出新毛病,PR 永远合不了。**第二轮复查仍有阻塞/应修** → 停,升级决策
清单(与收单核实「第二次仍不过」同口径):两轮修不干净说明问题不在代码在理解,
独自重试无益。

**两态出结论**:评审结论只有「可合并」「不可合并(附发现清单)」两态,禁「基本可以」
「建议合并」类含糊词——含糊结论 = 评审无效,等同没评。

## 评审报告(留痕)

挂 **PR 评论**(合并动作的核对面在 PR;工作项与 PR 已互链,不重复挂)。格式:

```
## 代码评审报告(st-project-dev-review)
档位:轻量/全量(依据:<分级声明/放行记录链接>)
结论:可合并 / 不可合并
通用质量(/code-review):<发现数与摘要;无发现写「无」>
专属核查:
  1 改动面越界:✅ 无越界 / 🔴 <文件:位置,越的什么界>
  2 降级对账:✅ 清单相符 / 🔴 <清单条目 ↔ 代码证据>
  3 三禁痕迹:✅ 无 / 🔴 <路径与证据>
  4 硬拍板落地:✅ / 🟡 <哪个字段/文案,缺什么>
发现清单:<级别 | 位置 | 问题 | 处置出口>(逐条;无则写「无」)
```

四条专属核查**逐条必有输出行**,没查的条目不许省略——省略 = 没查,与 pm-test 盲审
「逐案例核对行」同一防偷懒机制。复查轮报告只列修复点核对结果,追加在同一评论串。

## 防错要点(速查)

- 评审子 agent 冷启动只喂三样输入;禁带开发上下文,禁采信开发自述
- 通用质量交内置 `/code-review`,本 skill 不复述检查项;专属核查四条逐条必查必输出
- 评审只读:发现只报告,修复归原开发子 agent 原分支追加提交
- 记录级不阻塞合并;阻塞/应修清零才合;结论两态,禁含糊词
- 复查只查修复点;二轮不清零升级决策清单,禁无限评审循环
- 静默降级证据 = 自述失真,直接升级——不是退回补作业能解决的
- 评审通过 ≠ 验收通过:功能达标仍归验收线判定
