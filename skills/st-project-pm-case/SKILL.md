# st-project-pm-case — 验收用例起草

与 [st-project-pm-test](../st-project-pm-test/SKILL.md) 凑成一对:**pm-case 造用例,pm-test 跑验收**。
本 skill 只负责「入库前」;**merge 永远是 PM 的动作**——merge 之前用例不存在,merge 之后
AI 不得再改内容(修订也走新 PR)。

**会话命名(2026-08-10 约定)**:进入本 skill 第一动作把会话标题设为
`用例 | <用例文件短名或 #issue> | <MMDD>`(如 `用例 | S03报工 | 0810`);
工具机制与无工具豁免见 pm-test「会话命名」权威条款。

## 边界(硬)

- **AI 绝不自行合并用例 PR**。用例 PR 的 merge = PM 核对定稿的签字,任何授权模式都不豁免。
- 用例内容体现 PM 的验收意志:AI 起草是整理与结构化,**不是替 PM 决定验收标准**——
  写不出可判定预期的点说明需求本身没定清楚,标【待确认】上交,不自作主张填合理值。

## 防 AI 犯错(硬纪律)

1. **预期只来自需求**:从现状实现抄预期 = 用实现验证实现,验收当场失效。
   起草不需要起 UI、不需要环境——验收本来就要暴露「实现与说明书不符」,
   起草时抄实际 UI 反而会把差异掩盖进用例。
2. **步骤写到业务意图层级**:「打开作业岛列表,点击【新建】」这个粒度即可;
   说明书明确规定了入口/交互的,按说明书写并挂锚点。**禁止编造说明书没有的 UI 细节**
   (具体菜单层级、控件形态)——那些留给 pm-test 执行时在真实 UI 里解析,
   解析不出才标 ⚠️,按钮换位置不算用例过时。
3. **推断显式标记**:需求明文没写、靠 AI 推断补的预期,条目末尾必须标 `(推断)`;
   PR 正文单列**推断清单**(与【待确认】清单并列),PM 重点审这两个清单。
   不标推断 = 把 AI 的理解冒充需求,是本 skill 最严重的违规。
4. **每条预期挂需求锚点**(§章节/issue 号);挂不上锚点的预期只能是「(推断)」。

## ① 素材(按优先级)

1. **被验收 issue** 的需求描述与验收标准(issue-refine 阶段写的验收标准是首选素材);
2. **说明书 docs/spec**(唯一基准;发现 issue 与说明书有出入 → 按铁律登记差异报 PM 拍板,
   不擅自选边写进用例)。**读原文必须连同项目的差异/修正登记一起读**(如「说明书修正登记」
   一类文档)——被登记覆盖的章节以登记为准写预期,把已拍板作废的原文口径写进用例 =
   整组界面预期恒不符(2026-08-10 教训:某场景 6 条预期照被取代的旧流程图写,执行轮全数
   对不上);
3. **用例库与项目已有测试文档**:`docs/验收测试用例/` 已有文件、项目既有测试方案——
   同场景已有用例优先**修订**而非另起新文件,避免两套用例漂移。

(起草**不需要**实际 UI 和运行环境——步骤写到业务意图层级,执行时由 pm-test 在真实 UI
里解析;见「防 AI 犯错」第 2 条。)

## ② 起草规则

- **外来用例文档**(他人/其他工具产出,任何格式)一律**转换成规范格式**再核对入库,
  lint 不迁就外来格式;转换不是搬运——同步做内容核对(对说明书、对实际 UI、对项目已知
  能力),发现自相矛盾/与需求冲突/与实现不符的,逐条标【待确认】列给 PM,并主动剔除
  劣质结构(复读式栏目、数据与步骤两处维护、执行后回填段)。

- 按 [case-template.md](case-template.md) 全要素起草;编号 `AC-001` 起,
  修订已有文件则续号,**不改已有案例的编号**(历史验收 issue 在引用它们)。
- **前置条件里的业务数据优先引用 `docs/import-data/` 已有导入文件**(UI 导入灌入,项目约定);
  缺的数据做成新导入文件随用例 PR 一并入库(同受 PM 核对),不写「手工造 N 条」这类
  每轮重来的前置。
- 角色/账号按业务角色写,配项目权限基线的真实测试账号;权限类判定配一条零授权对照案例。
- **权限/入口可见性类预期对照项目授权文档写**(实施手册/权限矩阵/权限集清单):入口受
  **显式授权制**能力门控制(不随业务角色权限集自动携带)的,前置条件必须写明测试账号
  需绑定的权限集,预期锚点挂授权文档而非泛泛的「角色可操作」——否则执行侧漏绑授权时,
  「入口可见」预期会把按设计的不可见测成缺陷疑点;零授权对照的预期同样按授权文档写实
  (无授权对象是「整表不可见」还是「只读」以文档/权限声明为准,不靠推断)。
- 预期结果 = 「在哪里看:看到什么」,逐条可判定。
- 拿不准的值(角色选谁 / 边界值 / 数据前提 / 多种理解)一律标 `【待确认】`。
- 自检到零错误:
  ```bash
  node scripts/acceptance-lint.cjs --draft docs/验收测试用例/<文件>.md
  ```
  `--draft` 下【待确认】只警告;正式门禁(pm-test 跑的默认模式)里【待确认】=错误,
  所以 **PM 合并前必须把【待确认】清零**(在 PR 里逐条拍板后由 AI 或 PM 落字)。

## ③ 提 PR 待 PM 核对

- 分支 `case/<slug>`,**只含用例文件**,不夹带任何其他改动;
- PR 标题:`用例:<批次/模块名>`;正文三段:
  1. 素材来源(issue 号 / 说明书章节 / 参照的剧本);
  2. **【待确认】清单**——PM 重点看这里,逐条拍板;
  3. 一句声明:「merge = PM 核对定稿」;
- assignee/reviewer 设为 PM(issue 创建人);对话里回报 PR 链接后**停手等 merge**,
  不催不代合;PM 打回的意见改完再推同一 PR。

## ④ 修订已有用例

- 需求变更、或 pm-test 跑出 ⚠️「文件写X实际Y」经 PM 判定为用例过时 → 起修订 PR,
  正文写明修订原因(哪个需求/哪轮验收暴露的);
- **验收轮判为「要改用例」的回流入口(2026-08-11 加入)**:pm-test ⑥ 把某条 ❌ 归档为
  `case-stale`(用例与现行说明书+系统都对不上)、且 PM 确认该档后,该用例回流到这里起
  修订 PR——**入口只有 PM 确认这一条**,验收会话自己不得改用例(pm-test ① 硬规则)。
  修订 PR 正文额外写明:验收记录 issue 号 + 用例编号 + 该轮的「依据」原文,
  并在【待确认】清单里单列一条「本次修订是按现状改用例,代码与说明书均不动」——
  这是 `spec-divergence` 拍成「双冻结」时唯一的书面痕迹,说明书当轮不会同步,
  漏写就没人知道用例为什么变了。merge 后由 pm-test 下一轮按新用例复测,复测 ✅ 才算绿;
- 修订同样走【待确认】纪律与 --draft 自检;历史案例编号不动,作废的案例整段删除并在
  PR 正文注明(不留僵尸案例)。
