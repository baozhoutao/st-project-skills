# st-project-dev-test — 开发自测与证据报告

> 建设状态:可用(未实战)| 批次:第一批 | 主责 AI 岗位:AI 开发工程师(自测)/ AI 测试工程师(独立复测)| 人类闸门:PM 扫报告首页

## 定位:自测轻于验收,证据纪律不降级

本 skill 是**开发侧自测**,与 st-project-pm-test(PM 验收测试)的分工边界:

| | dev-test(本 skill) | pm-test |
|---|---|---|
| 执行者 | 开发侧(常与开发同一会话) | 独立验收流水线(主 agent 调度 + 子 agent 执行/盲审) |
| 输入 | 工作项七要素描述 | PM 核对定稿的标准用例文件 |
| 发现缺陷 | 回修 → 受影响用例重测重截 | 只记录不动手 |
| 发布面 | 测试报告挂到工作项 | 验收记录 issue |
| 证据纪律 | **与验收同级,不降级** | 同左 |

**自测通过 ≠ 验收通过**:自测报告供 PR 评审与验收线参考,不替代 pm-test 的独立复测。

## 两条原则(全文总纲)

1. **测试计划只从需求推导,禁从代码反推。** 照实现写用例 = 把 bug 测成 feature——代码
   怎么写的就怎么「通过」。计划完整落盘之后才许动手测。
2. **结论必须有证据。** 功能证据 = 真实环境 UI 操作截图;代码 diff、单元测试输出、API
   直调返回值都不算(证据硬标准见 st-project-std-evidence)。

## 输入与前置检查

- 工作项的七要素描述(要素定义见 st-project-req-refine;尤其校验规则与验收标准);
- 可运行的真实环境 + 各角色测试账号——环境地址、账号映射、启动方式一律**从项目仓库自身
  配置/文档读取**,本 skill 不写死;
- **DoR 复核**:仅凭描述写不出完整测试计划 = 工作项不就绪 → **停**,退回
  st-project-req-refine 列出具体缺口,不许脑补开测。

## 第一步:从需求推导测试计划(先写完,再动手)

### 七要素 → 用例的推导法

| 需求要素 | 推出什么用例 |
|---|---|
| 触发操作 | 主流程用例的入口步骤(按钮/菜单名与需求逐字一致) |
| 输入 | 每个输入项的有效值用例 + 格式/边界用例 |
| 校验规则 | **每条规则 ≥2 条用例:成功分支 1 条 + 失败分支逐种各 1 条**——规则写了几种失败,就有几条失败用例,预期含具体提示文案 |
| 输出/反馈 | 主流程的断言点(界面变化、数据出现在哪个列表/详情、通知等联动副作用) |
| 验收标准 | 逐条映射到用例——**每条验收标准至少被一个用例承接**,对不上号 = 计划没写完 |
| 业务场景/依赖 | 前置数据准备与用例执行顺序(主流程在前留数据,权限只读收尾不污染) |

### 用例矩阵:四类缺一不可

| 类 | 至少覆盖 | 允许缺类的唯一形式 |
|---|---|---|
| 主流程 | 触发操作→输入→输出/反馈完整走通;有状态流转则覆盖需求写明的每个变迁 | 不允许——任何工作项都有主流程 |
| 边界 | 必填项空提交、超长/格式非法输入、数值边界(0/负数/上限)、重复提交或查重 | 写明「本项无用户输入」才可豁免 |
| 异常 | 每条校验规则的每种失败分支(见上表);中断/非法状态下触发操作的出路 | 写明「需求未定义校验规则」——这句话本身往往就是该退回细化的信号 |
| 权限 | 目标角色正例 + 无权角色反例,至少一对 | 写明「本项与权限无关」及判断依据 |

**存量数据用例(改已有类工作项的附加必测)**:工作项改已有对象/字段/校验/口径,或
新增会触碰存量的资产(校验规则、必填、默认值、状态机——口径见 st-project-dev-design
「存量数据必答」)的,四类之外必须补存量用例,且**必须在带存量数据(或其副本)的
环境上执行**——只在空库/纯新造数据上测,永远测不出「新校验把老单据锁死」这类缺陷:

- **旧数据走新逻辑**:打开/编辑/流转一条真实存量记录,断言不被误拦、口径不算错;
- **处置结果抽查**:方案声明的迁移/回填,按其第四问的对账口径抽样断言
  (总数对上 + 抽样点逐条核);兼容双轨的,新旧数据各测一条走向;
- 方案写「存量不涉及/显式不处理」→ 本类用例可豁免,但计划里写明豁免依据
  (引用方案该条),禁静默跳过。

### 用例格式(每条)

编号 / 标题 / 类型(四类之一)/ 端(按项目实际,如 PC 端、移动端)/ 角色 / 前置条件 /
操作步骤(**具体输入值内嵌步骤**,一处真值)/ 预期结果(一条一断言,格式 =
「在哪里看:看到什么」;禁「功能正常」「符合预期」等不可判定表述,「成功」必须带具体观察物)。

### 计划纪律

- 计划完整写完并**落盘**后才开测——它就是报告第 3 节的总表,实测只回填结果列;
- 测试过程中**禁改预期迁就实际**。实测发现计划写错(自己理解偏差)→ 先改计划并记明改动
  原因,受影响用例按新计划重测;发现需求本身可两解 → 走「歧义出口」(见下),不自行拍板。

### 计划完整性核对:对照需求符合度清单(反降级联动)

st-project-dev-issue 步骤 4.5 要求提 PR 前产出「需求符合度清单」(逐条要求标
✅/⚠️/❌ 三态)。测试计划与它同源同粒度——都从需求条目逐条展开,因此互为核对面:

- 用例矩阵必须**覆盖符合度清单的全部条目**:清单每条要求至少一条用例承接(与「每条
  验收标准至少被一个用例承接」同一机制,扩展到全部要求条目);
- 某条要求**写不出对应用例** = 强信号:要么实现缺失(没做的东西写不出可操作的步骤),
  要么需求不可判定(预期写不出断言)。对照清单核查后按三出口处置——需求歧义走本 skill
  「歧义出口」,平台受限/实现困难按 dev-issue 三出口条款引用对应挂起/升级记录;
  **禁把写不出用例的条目静默从计划里漏掉**;
- 报告里符合度清单条目与用例矩阵条目**一一可对**:每条清单条目能指出承接它的用例编号
  (映射附在报告第 3 节总表之后),验收侧与调度员逐条核对,不采信自述。

## 第二步:真机实测

证据硬标准整体以 **st-project-std-evidence** 为准,以下只列自测场景特有与最高频违规项:

- **真机 UI 操作**:按用例步骤在界面上逐步操作,禁拿代码实现、构建产物、API 直调返回值当
  功能证据;API/DB 查询只能作为写操作落库的**第二观察点**佐证,不能替代 UI 断言。
- **环境基线先核实**:开测前确认 serving 的代码确实包含本次改动(存疑就重启服务取证,
  不信热重载日志)。陈旧基线对自测尤其高危——改动没生效,测的全是旧代码,结论整体作废。
- **写操作 before/after 成对**:先截前置状态(列表计数/记录不存在),操作后截结果态。
  没有 before 证明不了因果——种子数据碰巧满足预期会骗过你。
- **截图落盘后回看**:每张截图落盘后立即打开回看,确认 ①截到的是目标页面 ②内容支撑要写
  的结论 ③非半加载/空白态;不符当场重截。瞬时提示(toast)等到出现再抓拍,没截到就复跑,
  禁凭「应该弹了」下结论。
- **权限用例用目标角色账号**:管理员跑通不算通过(管理员什么都看得见,永远测不出权限
  缺陷);无权反例要真实登录无权账号,截到「看不到 / 被拒」的现场。
- **失败分支逐条真实触发**:每种校验失败都真实操作触发一次,截图拍到具体提示文案;
  禁「同类失败测一种代表」。

### 测出问题怎么办(自测特有:可以修,但修完必须重测)

- **疑似缺陷先排误判**:降维复用 [st-project-pm-test/traps.md](../st-project-pm-test/traps.md)
  的假阴性区——环境、时序、账号状态问题别当产品缺陷记。
- **确认缺陷 → 回修 → 重测**:修完重启/重部署,**受影响用例从头重测、证据全部重截**。
  修复前的截图只能进报告「问题记录」,禁充当通过证据——代码改了,旧截图就是另一个版本的
  证据。
- **需求歧义**(实际与预期不符,但根源是需求可两解/有缺口):停测该用例,走歧义出口。

## 第三步:出测试报告

结构按附件 [report-template.md](report-template.md),要点:

- **首页 = 结论 + 关键截图**,PM 30 秒定去留;
- **结论只有两态**:`✅ 通过`(当且仅当全部用例通过)或 `❌ 存在问题`(附问题清单;含
  「待细化」歧义用例时也算存在问题)。禁「基本通过」「大体没问题」等含糊表述;
- **问题一律表格呈现,三件套缺一不可(2026-08-18 维护者要求)**:每个问题必须给出
  **问题现象、问题原因、处理建议**三列——原因写初步定位,定位不到写「待排查」并附
  排查线索,禁止只报现象不给原因和建议,也禁止没定位就编一个原因;另标**严重程度**
  (阻塞/严重/一般)与路由短标签(【要改代码】【需求没写清】【环境问题】【平台受限】),
  偶现问题与有无临时绕行办法在明细层写明(细则见模板);
- 后接:测试环境与账号 → 测试计划与逐用例结果总表 → 逐用例明细(步骤 + 截图)→ 问题记录;
- 交付格式(Word 等)与排版按 st-project-std-docs;截图贴到工作项时的图链规范按
  st-project-std-evidence(commit SHA 图链、贴后核对)。

## 测试实例独立性(自证偏误防线)

开发和自测常是**同一个会话**——写代码的记忆会污染判定(「我记得实现了」≠「界面上看到了」)。
按条件分两档,取高不取低:

- **条件允许(优先)**:自测交独立实例执行(独立子 agent / 新会话),只喂工作项需求描述 +
  环境信息,**不喂实现过程上下文**——它没有实现记忆,只能看界面说话。
- **最低限度(同会话自测必须做到)**:**按计划逐条对,不按记忆下结论**——逐用例把
  「预期 vs 实际观察」成对写下,每条结论都指向对应截图;禁总结式的「都测过了,没问题」。
  计划先于实测存在(第一步)+ 逐条对照回填,是同会话自测仅有的两道防线,一道都不能省。

## 自测效率纪律(UI 测试为主的成本设计)

自测以 UI 测试为主,UI 测试的固定成本(起环境、起浏览器、登录、截图)决定了自测的节奏
设计。六条纪律一个方向:**证据纪律不降级的前提下,把往返轮数与固定成本压到最低。**

1. **独立的是判断,不是环境**:独立自测子 agent 直接复用开发侧交接的运行中环境
   (本 worktree 的 dev 实例),**不重搭**——独立性防的是实现记忆污染判定,不是环境
   污染。与 st-project-pm-test 的区别:pm-test 必须自起隔离环境,因为验收要防「开发
   环境里碰巧能跑」;自测测的就是开发环境本身,重搭反而测了另一个环境。
2. **独立性跟随风险级**(分级判定归 st-project-dev-design,不复读):高风险工作项
   (改已有/跨模块)→ 必须派独立自测子 agent(一律指定 Opus 模型,与全库子 agent
   口径一致),即上节「条件允许」档;低风险(纯新增)→ 允许同会话自测,上节
   「最低限度」档的两道纪律(计划先落盘、逐条对照)一道不能省。
3. **一次浏览器会话串测**:一次启动浏览器、一次登录,按用例依赖序串完全部用例,
   **禁逐用例重起浏览器/重复登录**——启动与登录是 UI 测试最大的固定成本。权限用例要
   换角色登录,集中排在收尾段(与计划纪律「权限只读收尾不污染」同向),减少切换次数。
   浏览器选择同 pm-test ③(权威条款,引用不复读):探索性核对**优先内置浏览器
   (Browser 面板)**,产证据步骤走全局 playwright + channel chrome(截图必须落盘),
   禁用用户本人的 Chrome 会话。
4. **证据分级**:主流程 + 校验规则用例 = 全套 UI 操作 + 截图回看,证据纪律丝毫不降;
   边界/异常分支 = UI 照走,只留关键帧截图(触发现场 + 提示文案);环境探路(数据
   就绪、账号可登、服务存活)用 API 探针最快——但探针只用于探路,**不作判定证据**
   (「真机 UI 截图才是功能证据」的总纲不破)。
5. **fail-fast 交错**:主流程用例一断**立即停测回修**——主流程断了,后续用例全是
   blocked,测完一轮再修 = 白测一轮;修完重启重走受影响用例。非阻塞缺陷(不拦后续
   用例)记录在案继续测,收尾统一回修重测。自测的目标是 **PR 干净、往返轮数最少**,
   不是单轮报告完整。
6. **脚本一条三用**:自测的 UI 驱动脚本必须复用验收框架层的公共 lib(登录、浏览器
   启动与截图、导入向导等现成封装,位置与复用清单见 st-project-pm-test),禁另起
   炉灶;跑绿后同一脚本可升级为验收场景脚本,再入回归巡检清单——回归层零截图、以
   退出码表达断言结果,是 st-project-dev-regression 的既有约定,引用不复读。

## 上下游交接

- **上游**:st-project-dev-issue 的自测步骤触发本 skill;工作项状态按项目状态机流转
  (状态/标签名以项目仓库约定为准)。
- **下游**:报告挂到工作项上 → 提 PR 进评审;验收由 st-project-pm-test 独立复测,
  本报告是参考件不是验收结论。
- **歧义出口**:实测中发现需求可两解、校验规则缺失、预期写不清 → **不自行解释后按自己的
  理解测**,把疑点整理成「理解 + 假设 + 选择题」退回 st-project-req-refine 补细化;
  已测部分照常出报告,歧义用例标「待细化」列入问题清单。

## 防错要点(速查)

- 计划从需求推,不从代码反推;计划先落盘再开测,测中禁改预期迁就实际
- 每条校验规则:成功 + 全部失败分支都有用例;每条验收标准至少一个用例承接
- 用例矩阵覆盖符合度清单全部条目,一一可对;写不出用例的条目按三出口处置,禁静默漏掉
- 一次浏览器会话串测;主流程一断先修再测(fail-fast);API 探针只探路,不作判定证据
- 真机 UI 截图才是功能证据;before/after 成对;截图落盘必回看
- 权限验证用目标角色账号,管理员截图无效
- 改已有类工作项必有存量用例,且在带存量数据的环境上执行——空库跑通不算通过
- 修了代码 = 受影响用例重测重截,旧证据作废
- 结论两态,禁「基本通过」
- 需求歧义退回细化,不自行解释;判 ❌ 前过 pm-test 的 traps.md 假阴性区
