# st-project-dev-inventory — 平台配置清单派生

> 建设状态:可用(未实战) | 批次:补建(2026-08-12 PM 拍板) | 主责 AI 岗位:AI 开发工程师/架构师 | 人类闸门:无(只读派生,无决策)

**设计核心:「系统里现在到底有哪些字段/按钮/hook/定时任务、谁可见谁可用」这层信息,
真值只有一份——平台元数据本身。本 skill 不新建第二真值,只约定怎么从元数据**派生**
全景视图:要看重新生成,永不手工回写。与「用例测试历史从验收 issue 派生、禁回写用例
文件」同一哲学——手工维护的中间层文档必漂移,漂移的文档比没有文档更害人。**

## 与相邻工序的分层(先分清,再动手)

| 层 | 归属 skill | 时机 | 回答的问题 |
|---|---|---|---|
| 量级规划 | st-project-dev-blueprint | SRS 签字后、开发前 | 「计划用平台哪类能力、大概多少」(计数,只随变更更新) |
| 逐项方案 | st-project-dev-design | 每工作项开工前 | 「这一项动哪些资产、增还是改」 |
| **全景实况(本 skill)** | st-project-dev-inventory | 实现后任意时点 | 「系统里**实际**有哪些、长什么样」(名单,即查即生成) |

蓝图管开工前的**计划量级**,本清单管运行期的**实际明细**,两者不打架;
对不上正是有用信号(见「与蓝图对账」)。

## 视图固定清单(逐张生成;项目没有的能力,该视图明写「零条目」不留空白)

| # | 视图 | 内容要点 |
|---|---|---|
| 1 | 对象 × 字段表 | 逐对象列字段:名称/类型/**数值边界(小数位/最小/最大)**/必填/默认值/引用哪个对象——数字字段边界列直接可核「数值四件套」落地情况 |
| 2 | 页面与按钮矩阵 | 逐对象:列表按钮 / 列表行按钮 / 批量操作按钮 / 详情页按钮;每按钮:可见权限集 + 显隐条件 |
| 3 | 相关列表 | 逐对象详情页显示哪些相关对象,顺序与过滤条件 |
| 4 | 流程清单 | 流程 × 节点 × 处理角色/岗位,触发对象与状态 |
| 5 | 权限矩阵 | 权限集 × 对象 CRUD × 页面/按钮入口;角色→权限集绑定 |
| 6 | hook 清单 | 挂在哪个对象 / 触发时机(before/after × 增删改)/ 一句话职责 / 源文件路径 |
| 7 | 自动化与通知清单 | 触发条件 / 动作 / 通知对象 |
| 8 | 定时任务清单 | 周期 / 一句话职责 / 源文件路径 |
| 9 | 自定义页面清单 | 页面名 / 路由 / 挂在哪个入口 / 所属模块 |
| 10 | 内部自定义接口清单 | 路径 / 方法 / 用途 / 已知调用方(对外集成接口归蓝图接口台账,此处只登记项目内部 API) |
| 11 | 端覆盖实况 | H5 端实际启用的对象/页面/入口清单——与蓝图「端覆盖」精判对照 |

**每份生成物必须带指纹头**:生成时间、元数据基线 commit(40 位 SHA)、生成方式
(脚本名或「手工盘点」)。没有指纹的清单无效——不知道基于哪个版本的清单,
与过时文档同罪(纪律同 pm-test 基线指纹)。

## 生成纪律(硬)

1. **只派生,禁回写**:清单是只读产物。发现清单内容与期望不符,改的是**元数据**
   (立工作项走 dev-issue),不是清单;直接编辑生成物 = 制造第二真值,发现即作废重生成;
2. **要看重新生成,不存陈旧副本当真值**:入库的只有**生成脚本**(设施,按
   std-git 归 `scripts/tools/` 并在 scripts/README 登记);生成结果默认阅后即弃,
   只有交付场景(pm-accept 附件、里程碑归档)才固化一份——固化版凭指纹头声明时点,
   过时不更新,要新的再生成;
3. **脚本按项目元数据结构实现**:各项目对象/页面/权限的源文件布局不同,本 skill 只约定
   视图结构与纪律,不写死解析方式;**脚本是加速器不是门槛**——脚本缺位时按视图清单
   手工盘点等价执行(同样带指纹头),不阻塞下游;
4. **与蓝图对账**:清单聚合数(对象数/定制点数/定时任务数/内部接口数/H5 场景数)与
   蓝图汇总统计表对照,对不上 → 报 PM 查因——漏做(计划有实际无)、超范围
   (实际有计划无,可能是默默吸收)、或变更没回填蓝图;**禁改数硬对,差异本身是产物**;
5. **生成是只读动作**:任何会话都可生成,但生成会话不顺手改元数据(与 pm-test
   「验收会话禁改代码」同构)——看见问题记下来立单,不当场修。

## 下游引用(谁拿它干什么)

| 使用方 | 用法 |
|---|---|
| st-project-dev-design | ① 影响面侦察先查清单再翻代码:共享资产、按钮/hook 被引用面一眼可查,三问判定(改已有/跨模块)有据;字段/按钮落点(复用还是新建)判定的核对底数 |
| st-project-req-refine | 细化写字段/按钮业务定义时**只读**查对象×字段/按钮清单对齐既有叫法、发现复用候选;只许影响「叫什么」,禁影响「预期是什么」(其防错要点 2 的权威引用) |
| st-project-std-docs | 合同要求交《设计说明书》时,交付版详细设计 = 蓝图 Word 化 + 本清单固化视图(带指纹头)组装成时点快照(其文档族总表「方案/设计文档」行的权威引用) |
| st-project-pm-test | 账号授权基线核对的**权限矩阵来源**:视图 5 派生自元数据即真值,替代手工维护的授权文档 |
| st-project-pm-accept | 交付文档「系统配置清单」章节 = 终验时点生成的固化版(带指纹头) |
| st-project-req-baseline | 清单与 SRS/蓝图对不上 = 差异登记线索 |
| 平台升级评估 / 下一单报价校准 | 能力使用面底数:定制点在哪、用了多少,复盘与估算都有账可查 |

## 首次在项目启用

1. 按项目元数据源文件布局写生成脚本(能生成几张算几张,视图清单是目标不是门槛),
   归 `scripts/tools/`,登记进 scripts/README;
2. 生成一轮全量视图,与蓝图做首次对账,差异报 PM;
3. 此后按需生成:dev-design 开工前、pm-test 批次开测前(权限矩阵)、pm-accept
   编档时、平台升级评估前。
