# st-project-dev-issue — 开发闭环

> 建设状态:可用(未实战) | 批次:第一批 | 主责 AI 岗位:AI 开发工程师 | 合并闸门:AI 独立代码评审(st-project-dev-review,阻塞/应修清零才合并)

## 目标

一个工作项从接单到提 PR 的全链路封闭执行,三条不变式:

1. **代码永远走隔离分支**——主干零直接写入,一切改动经 PR;
2. **产出永远带证据**——"做完了"由测试报告说话,不由开发者自述说话;
3. **状态永远在看板可见**——每次推进同一步完成"换状态标签 + 交接处理人",任何时刻
   看板都答得出"这条现在卡在谁手里"。

## 启用前置(新项目第一次用之前)

本 skill 不含任何项目具体值(仓库名、标签名、账号、命令、地址),这些值全部由项目侧按
[project-setup.md](project-setup.md)(项目启用清单)声明。**首次在一个项目使用前逐项核对
该清单;标记「必填」的项缺失 → 不开工,先让项目侧补齐。** 下文所有 `<映射:xxx>` 都指从
该清单的状态标签映射表取项目实际值。

## 逻辑状态机与处理人交接(总览)

本 skill 用**逻辑状态**描述流转;项目实际标签名由启用清单 §B 映射(前缀、措辞允许项目
自定),用之前以项目侧实查为准,禁凭记忆写标签名。状态轴之外的类型轴/优先级轴标签,
见启用清单 §B 附表「全项目标签体系总表」(启用时一次建齐)。

```
待开发 → [方案确认中] → AI开发中 → 自测报告中 → PR审查中 → PM验收中 → 人工测试中 → 已完成
             ↑归 dev-design                          ↘ 已打回(处理人交回开发侧,返修)
                                                     ↘ 已挂起(平台能力受限等外因)
```

| 逻辑状态 | 处理人 | 进入该状态的动作(谁做) |
|---|---|---|
| 待开发 | 就绪池(未认领) | 上游细化/派发的产物,不归本 skill |
| 方案确认中 | 人(技术负责人) | 归 st-project-dev-design;本 skill 进门时它已结束 |
| AI开发中 | **开发侧** | 接单(步骤 1):assign 自己 + 切标签,同一步 |
| 自测报告中 | **开发侧** | 测试报告挂上工作项后切(步骤 4) |
| PR审查中 | **验收侧** | 提 PR 的同一步:切标签 + 处理人交给验收侧(步骤 5) |
| PM验收中 / 人工测试中 | 验收侧 | 验收线推进,开发侧不动状态 |
| 已完成 | 验收侧 | 关闭动作归验收线;PR 绝不自动关闭工作项(std-git 铁律);切「已完成」前置检查:该工作项的场景断言已入回归巡检清单或已登记豁免(权威条款见 st-project-dev-regression)。**验收派生缺陷 issue 例外**:修复 PR 合并后开发侧改标签+交接处理人即直接 close,不走验收线,批次复测把关(权威条款见 st-project-pm-test ⑥) |
| 已打回 | **开发侧** | 验收侧打回时反向交接,处理人改回开发侧(支线 A) |
| 已挂起 | 人(按启用清单) | 平台受限等外因挂起,停止消耗(支线 B) |

**硬规则:换状态标签与交接处理人必须是同一次操作。** 分成两步做,中间时段看板上就是
"状态说轮到验收、处理人还挂开发侧"的双头蛇——漏交接是看板失灵的头号原因。

## 主线步骤

### 步骤 0 — 进门检查(不合格就不开工)

1. 读工作项全文。确认:状态 = `<映射:待开发>`;描述过 DoR——要素齐到**能独立写出测试
   计划**的程度。写不出测试计划 → 不动手,状态退回 `<映射:待细化>` 并在工作项下列出缺
   什么(细化归 st-project-req-refine)。
2. 确认方案已放行:低风险(纯新增、不改已有、路径唯一)可直接开工;高风险(改已有/
   跨模块/多路径)必须已有 st-project-dev-design 的确认记录。没有 → 先回 dev-design,
   不许边写边等。
3. 读项目专属纪律(启用清单 §H 声明的必读文件),加载 st-project-std-git /
   st-project-std-evidence。

### 步骤 1 — 接单

**动手(除读代码外的任何操作)之前的第一个工作项动作**,一步完成:

- 处理人 = 开发侧自己(启用清单 §A 声明的账号);
- 状态 `<映射:待开发>` → `<映射:AI开发中>`。

以 GitHub Issues 为例(标签实际名取自映射表):

```bash
gh issue edit <n> --add-assignee <开发侧账号> \
  --remove-label "<映射:待开发>" --add-label "<映射:AI开发中>"
```

禁止跳过、禁止事后补:接单动作就是并行防撞机制,没接单就动手 = 两个实例可能同时开工
同一个工作项。

**批量派发场景的例外**:走 st-project-pm-dispatch 时,接单占坑由调度员在派发瞬间完成
(同样是防重复派发)——被派发的子 agent 开工前**核对**占坑已到位(处理人与状态正确)
即可,不重复执行;核对不过(没占坑/占给了别人)→ 停手上报调度员,不自行抢单。

### 步骤 2 — worktree 隔离

**一工作项 = 一分支 = 一 worktree**。git 铁律见 st-project-std-git(绝不动主干;并行实例
禁共用远端分支)。本 skill 补充 worktree 专属纪律:

- 分支名与 worktree 目录按启用清单 §C 的约定(建议默认 `issue-<n>-<slug>`),基于主干
  最新提交建;
- **worktree 新建后必须跑启用清单声明的初始化命令**(依赖安装等)——worktree 不共享
  主工作目录的依赖与构建产物,跳过安装的典型症状是"旧依赖静默吞掉新配置",坏起来
  无声无息;
- 本会话**只改本 worktree 路径下的文件**;发现自己在改别的目录(主仓库工作区、别的
  worktree)立即停手、如实报告,不许悄悄挪回来当没发生;
- 并行工作项各自独立 worktree + 各自独立 dev 环境(端口/数据隔离按启用清单 §D),
  禁止借用别的工作项或别人正在使用的运行实例;
- 陈旧构建产物/缓存会制造"改了没生效""删了还在"的幽灵行为:验证任何行为前先确认
  服务跑的就是本 worktree 的当前代码,存疑就按启用清单声明的方式清理并整体重启。

#### 减少合并冲突(并行分支纪律)

多工作项并行时,合并冲突不是运气问题,是纪律问题。五条,方向一致:**让每条分支
改得少、活得短、离热点远**:

1. **分支短命,小步快合**:从建分支到 PR 合入的时间越短,冲突窗口越小。一个工作项
   憋成大分支 = 给所有并行分支制造冲突;工作项本身太大,在细化阶段就该拆
   (归 st-project-req-refine),不靠大分支硬扛;
2. **改动面收敛,离共享文件远**:只改本工作项必需的文件;新功能优先新增独立文件
   承载(与 dev-design 落点判定同向)。**禁止顺手重排/全文件格式化/无关重命名**——
   一次全文件格式化能把所有并行分支同时打成冲突,这类清理想做就单独立项串行做;
3. **注册表类共享文件按模块分区追加**:菜单、权限总表、翻译词条、路由/清单类
   「人人都要登记一笔」的文件,是冲突的头号高发点。项目侧优先按模块拆成多文件;
   拆不了的,各工作项**只在自己模块的区块内追加**,不动别人的区块、不重排既有条目;
4. **主干推进及时跟进**:主干合入新提交后,尚未合入的分支尽快把主干同步进来
   (merge 或 rebase 按 st-project-std-git 与启用清单的约定),冲突早解决、小块解决;
   解决冲突**以主干为准重放自己的改动**,禁在解决冲突的提交里夹带任何逻辑变更——
   夹带 = 绕过评审的暗改;
5. **热点撞车即上报**:开工侦察发现本项要动的对象/共享资产,也在另一条在跑分支或
   蓝图共享对象热点名单(st-project-dev-blueprint ④)的影响范围里 → 报调度方
   (pm-dispatch)排串行,不抢跑、不赌谁先合——热点串行是调度决策,分组依据归
   蓝图,本条只管「发现了要报」。

### 步骤 3 — 实现

- 遵守项目约定文件与平台知识 skill(`steedos-*` 族);平台语义拿不准**先查再写,
  禁止猜**;
- **数字类型字段建模四件套(2026-08-12 PM 拍板,硬)**:新建或修改任何数字字段,
  必须显式定齐 ① 小数位数(含舍入规则)② 最小值(能否为 0 / 能否为负)③ 最大值
  ④ 单位,**禁止按平台默认精度与无界范围建字段**——默认建模是「负数存得进、超量级
  不拦、小数位对不上」类验收缺陷的高发源头。四件套的取值**只能来自工作项描述**
  (细化阶段的数值四件套要素,见 req-refine checklist 要素 3);描述里缺 → 按需求
  歧义处理,退回细化或按选择题模板问 PM 拍板,**不许自行猜边界、更不许静默取默认值
  当作「实现完成」**(那是步骤 4.5 定义的静默降级);
- **存量数据处置落地(方案里答过的四问,这里兑现)**:dev-design「存量数据必答」
  定下的处置方式必须落成可核验的产物,不许停在方案文字上——
  - 迁移/回填走**入库脚本**(位置按启用清单约定),要求**幂等可重跑**(跑两遍结果
    一致),禁一次性手工改库不留痕;
  - 执行顺序显式声明:新校验/新必填/新口径这类「会拦存量」的改动,**先回填后上闸**,
    顺序反了存量当场被锁死;
  - 先在**带存量数据副本的 dev 环境演练**并留对账证据(处置前后总数/抽样,对账
    口径来自方案第四问),只在空库上验证过 = 没验证;
  - 方案声明「显式不处理」的,实现阶段发现存量实际会被影响 → 按 dev-design ⑥
    判错升级,不许现场自行加处理;
- 范围纪律见下小节「开发中发现新问题」:同因同域可并,独立问题立单可搭车,红线不折入;
- 提交规范见 st-project-std-git;临时调试产物不入库。

#### 开发中发现新问题:扩围与搭车执行(2026-08-10 PM 拍板)

**台账照拆、执行打包**——issue 粒度服务追踪与验收,执行粒度服务效率;两个粒度解耦,
不许用「都塞进一个 issue」去修执行效率。发现新问题按性质分三路:

- **同因同域 / 阻塞本项交付**(不修它本项交不了,或就在本项正改的代码路径上)→
  **并入本工作项处理**,不算蔓延;工作项评论记一行「扩围:发现 X,一并修」留痕,
  测试报告如实覆盖扩围部分;
- **独立问题** → **照立单**(查重口径同 pm-test ⑥:open+closed 都搜,已报的评论补充
  不重开),但允许**搭车执行**:小且同模块的,由发现它的本开发子 agent 在**同一
  worktree** 顺手接单——逐单独立 commit、PR 正文逐单关联、各单各自流转与关闭,
  禁混进同一个 commit;搭车以不拖垮本项交付为限,拿不准就只立单不搭车;
- **红线**:要动共享资产/跨模块/改业务口径的发现,再顺手也不折入不搭车,立单走
  dev-design 报审(「顺手修老问题 = 高风险信号」条款不变)。

### 步骤 4 — 自测 + 测试报告

开发完成 ≠ 步骤结束。按 **st-project-dev-test** 完成测试与报告,本 skill 只管交接面:

- 开发侧交出:工作项描述、可运行的真实环境(本 worktree 的 dev 实例)、测试账号
  (启用清单 §D);
- dev-test 要求测试实例独立于开发实例(自写自测 = 确认偏误);项目暂不具备双实例条件
  时,按启用清单 §H 显式声明的降级方式执行,不许默默单实例自测;
- 报告结构与截图/图链规范归 st-project-std-evidence / st-project-std-docs;
- 报告**挂到工作项上**(发布面是工作项,不是本地目录、不是代码主干),挂上后状态切
  `<映射:自测报告中>`(处理人不变,仍是开发侧)。

自测发现缺陷 → 就地修复重测,如实计入报告;修不掉 → 走「失败升级」,不许把带病版本
推向 PR。

- 自测子 agent 的派发时机与环境交接:按 dev-test「自测效率纪律」——独立的是**判断**
  不是环境,高风险工作项在本步派独立自测子 agent(一律指定 Opus 模型),复用上面交出的
  本 worktree 运行中 dev 实例,不重搭环境;低风险允许同会话自测(档位细则归 dev-test,
  此处不展开)。

### 步骤 4.5 — 需求符合度清单(提 PR 前硬门禁,反需求降级)

**为什么有这一步**:AI 开发最隐蔽的失败模式是**静默降级需求**——做不出就悄悄做小:
少做一条校验、换成更简单的交互、绕开平台问题。每一次降级都是**未经授权的需求变更**;
需求变更权归客户/PM,AI 零权限。降级本身不可怕,**静默**才可怕——本步的目的是让任何
降级在提 PR 之前就藏不住。

**清单怎么写**:逐条列出工作项的每个要求——触发操作(含每个按钮)、每个输入项/字段、
**每条校验规则单列**、输出/反馈、每条验收标准(粒度与 st-project-req-refine 的要素
对齐)——逐条标三态:

| 态 | 含义 | 必附 |
|---|---|---|
| ✅ 完整实现 | 与需求逐字相符 | — |
| ⚠️ 有偏差 | 实现了但与需求有出入 | 差异是什么 + 为什么 |
| ❌ 未实现 | 没做 | 原因 |

清单**挂到工作项上**(与测试报告同层级,同为提 PR 的前置产出);**禁「基本实现」
「大致完成」类含糊词**——出现含糊词 = 清单无效,等同缺失。

**清单会被独立对账**:合并前评审子 agent 按 st-project-dev-review「降级对账」把清单
逐条对照 PR diff 核真伪,✅ 条目与代码矛盾按静默降级证据处置(直接升级决策清单)——
清单是写给独立对账者看的,不是走形式。

**三出口条款(硬)**:任何非 ✅ 条目只有三个合法出口,条目上必须带对应记录的链接:

1. **需求歧义** → 退回 st-project-req-refine 细化(引用退回记录);
2. **平台能力受限** → 走支线 B 挂起(引用挂起记录——含平台上报链接,见支线 B);
3. **实现困难** → 走「失败升级」交人裁决(引用升级记录)。

**没有第四个出口叫「先简化实现」。** 静默降级——清单缺失、清单造假、或实现与清单
不符——定为本 skill **最严重违规**:发现即停单升级,违规案例按 st-project-meta-retro
复盘回填,查清是哪一步让降级有机会藏住。

### 步骤 5 — 提 PR + 交接(一步三件事)

1. **提 PR**:正文关联工作项编号但**不写自动关闭语法**(关闭动作归验收线,std-git
   铁律);附测试报告位置;
2. **切状态** `<映射:自测报告中>` → `<映射:PR审查中>`;
3. **处理人交给验收侧**(启用清单 §A 声明的规则,默认 = 工作项创建人)。

三件事同一步完成。以 GitHub 为例:

```bash
gh pr create ...   # 正文关联 #<n>,不写 Closes
gh issue edit <n> \
  --remove-label "<映射:自测报告中>" --add-label "<映射:PR审查中>" \
  --remove-assignee <开发侧账号> --add-assignee <验收侧处理人>
```

**开发子 agent 绝不自行合并 PR。** 走 pm-dispatch 的批次(委派强制下,即所有工作项),
合并由**调度员**在收单核实通过、评审闸门清零后自主执行、不询问(2026-08-12 PM 拍板,
权威条款见 pm-dispatch「调度员自主合并 PR」)——对开发子 agent 而言仍是「提 PR 即止」,合并
永远不是自己的动作。此外的场景合并归人/验收线;项目另行授权须在启用清单 §F
显式成文且写明范围条件,不存在"上次让合了这次也能合"。

**PR 通过 ≠ 验收通过**:合并前代码评审(调度员派独立评审子 agent 执行,权威条款见
st-project-dev-review)管代码质量;功能是否达标由测试报告 + 验收线判定。评审意见的
修复在原分支追加提交即可,不切状态、不改处理人。

## 支线 A — 被打回(返修)

验收侧把状态切 `<映射:已打回>` 并把处理人交回开发侧后:

1. **先读打回理由与证据、复现问题,再动代码**——不复现就修 = 又一轮盲改;
2. 在**原分支/原 worktree** 上修,同一工作项不开第二条分支;
3. 修完从步骤 4 重走:重新自测,报告须补充打回点的针对性验证证据,再走步骤 5 交回;
4. **AI 先接手第一轮,处理不了才请人(2026-08-10 PM 拍板,调整原「第一次打回即请人」)**:
   打回后 AI 先完整做一轮「读证据→复现→定位→修复→重测」;出现以下任一情形,在工作项上
   打 `<映射:人工介入>` 标记 + 评论写明卡点(已试路径/怀疑方向/要人拍板的问题,要素同
   「失败升级」五样),然后停手等人:
   - 按打回证据**复现不出**问题;
   - 根因是**需求歧义**/验收标准两解(AI 不选边);
   - 疑似**平台能力问题**(按支线 B 上报挂起,`人工介入` 不用重复打);
   - 第一轮修复后自测**仍不过**(与「失败升级:同一问题失败一次即升级」同口径)。
5. **同一工作项第二次被打回**(返修交回后又挂)→ 直接打 `<映射:人工介入>`,不再自动
   重试——两轮都没修对,说明 AI 的理解与验收标准存在系统性偏差,独自重试大概率在
   同一个坑里刨得更深。

## 支线 B — 平台能力受限(不绕行、不打补丁)

实现或返修中发现问题根源在平台(Steedos)能力——项目侧代码在不打补丁、不绕行的
前提下无法达成需求:

1. **停手**。三禁:禁改平台包内容(含对依赖目录打补丁)、禁绕行实现(绕行 = 永久技术债
   + 平台升级炸弹)、禁降级半成品冒充完成;
2. 按启用清单 §G 声明的渠道**上报平台方**:现象、最小复现、期望能力、平台版本——项目
   侧不自建平台缺陷台账,单一真值在平台侧;
3. 工作项打 `<映射:平台能力受限>` 标记 + 状态切 `<映射:已挂起>`,处理人交给启用清单
   声明的负责人,**停止在此项上消耗资源**;
4. 平台能力具备后由人拉回 `<映射:待开发>` 重新排期,不由 AI 自行复活。

**挂起合法性(硬,防「口头平台受限」)**:挂起动作必须在工作项上附**最小复现步骤 +
平台上报记录链接**(第 2 步上报的产物),两样缺一 = 不构成合法挂起——一句「平台不
支持」既无复现也无上报,往往是静默降级的前奏。需求符合度清单(步骤 4.5)走「平台
能力受限」出口的条目,必须逐条引用该挂起记录,可核对。

判定拿不准(是平台问题,还是自己没用对)→ 按「失败升级」交人裁决,不许按平台问题
直接挂起了事。

## 失败升级(同一问题失败一次即升级)

**同一问题的第一次修复尝试失败后就升级给人,禁止无限自我重试。**"同一问题" = 同一
报错/同一现象;换个写法再试一遍不算新问题。允许的自查是失败后的**一轮**诊断(读日志、
查文档、核对配置),诊断完仍无把握就停。

升级走启用清单 §G 声明的通道,必须带齐五样(缺一样,人就得反问一轮,升级就白升了):

1. **现象与报错原文**——全文粘贴,不转述不翻译;
2. **已试路径**——每条一行:做了什么 → 结果如何;
3. **怀疑方向**——按可能性排序,每条附依据;
4. **环境快照**——分支/commit、dev 环境状态、复现入口;
5. **要人拍板的具体问题**——能收敛成选择题就收敛成选择题。

升级后停在原地等回复,不许"边等边再试几把"——环境被试脏了,人来了也没法看现场。

## 防错要点

- **看板失灵三源头**:没接单就动手 / 提了 PR 没交接处理人 / 打回后没交回开发侧——全部
  用"换标签+换处理人同一步"堵死;
- 描述写不出测试计划就开工 = 最贵的返工源头,进门检查第 1 条不许省;
- 报告先于 PR:没有挂上工作项的测试报告,就没有资格提 PR;
- **存量数据处置先回填后上闸**,脚本入库、幂等、带存量副本演练留对账证据——只在
  空库上跑通不算数;
- **冲突纪律**:分支短命小步快合、不动无关文件、注册表类文件只在本模块区块追加、
  主干推进及时同步、解决冲突禁夹带逻辑变更、热点撞车报调度排串行;
- **符合度清单先于 PR**(步骤 4.5):逐条三态、禁含糊词;非 ✅ 条目只有退细化/挂起/
  升级三个出口,**没有第四个出口叫「先简化实现」**——静默降级是本 skill 最严重违规;
- 项目具体值(仓库名、标签名、账号、命令、地址)一律取自启用清单与项目配置,本 skill
  正文与任何产出物里都不写死;仓库名从 `git remote` 自动识别;
- 首次实战后按 st-project-meta-retro 回填本 skill:哪步顺序不对、启用清单哪项缺失,
  当场改。
