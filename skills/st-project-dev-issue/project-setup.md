# project-setup — st-project-dev-issue 项目启用清单

一个新项目启用 st-project-dev-issue 前,须把本清单逐项落实,声明在项目自己的约定文件里
(CLAUDE.md 或等价文件,集中一节,便于 AI 开工前一次读全)。**skill 库不存任何项目实际
值**;本文件只定义"要声明什么"。

- **必填**项缺失 → 本 skill 不开工,把缺项清单报给项目侧补齐;
- **建议**项缺失 → 用条目里写明的默认值,并在首次使用时向项目侧确认。

## A. 身份与仓库

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| A1 | 仓库识别 | — | 不用声明:仓库名一律从 `git remote get-url origin` 自动识别,任何文档/脚本禁写死。启用时仅需核对 remote 指向正确仓库 |
| A2 | 工作项跟踪系统 | 必填 | 用什么系统管工作项(如 GitHub Issues)、编号引用格式(如 `#123`)、操作工具(如 `gh`) |
| A3 | 开发侧账号 | 必填 | 接单 assign 用的账号名(AI 以谁的身份操作工作项) |
| A4 | 验收侧处理人规则 | 必填 | 提完 PR 处理人交给谁:默认建议「工作项创建人」,也可以是固定 PM 账号。写成可执行的取值规则 |

## B 附表. 全项目标签体系总表(一次建齐)

全项目标签共**三轴**:状态轴、类型轴、优先级轴。各轴标签散落在多个 skill 里定义,
本表是唯一汇总面——新项目启用时按本表**一次建齐**,不必逐个翻 skill。原则同 §B:
下表一律**逻辑名**,项目实际标签名由项目侧映射并实查(`gh label list`),skill 库
不存项目实际值;前缀与措辞允许项目自定,逻辑语义不许变。

### 轴一:状态轴(必填)

即 §B 的 11 个逻辑状态 + 3 个标记,映射表见 §B,此处不复读。权威定义在
[st-project-dev-issue](SKILL.md) 状态机节;其他 skill(std-git / dev-design /
pm-dispatch / pilot-ops)均引用不另定义。

### 轴二:类型轴

| 标签(逻辑名) | 用途一句话 | 谁打 / 谁摘 | 来源条款 |
|---|---|---|---|
| 回归缺陷 | 夜间巡检断言失败自动立的缺陷单类型标记,派发/接单时置顶 | 打:巡检 runner 立单时自动(同场景 open 单去重不重立);摘:不摘,随单走——关单归分诊/修复闭环的处理人,runner 不自动关 | [st-project-dev-regression](../st-project-dev-regression/SKILL.md) 三(立单)、四(分诊)、六(流转置顶) |
| 验收记录 | 标记 pm-test 每轮发布的验收结果 issue,构成可派生查询的验收台账 | 打:pm-test 建验收 issue 时;摘:不摘,长期保留(历史反查的检索键);处置清单执行完关 issue,标签仍在 | [st-project-pm-test](../st-project-pm-test/SKILL.md) ⑤ 收单核实 + 发布(首次使用先建此标签与 acceptance-evidence 孤儿分支) |
| 试运行缺陷 | 试运行值守登记的现场缺陷类型标记,日报数字按它查询派生、禁手填 | 打:值守分诊立单时;摘:不摘,长期保留(日报"数据口径"的过滤键) | [st-project-pilot-ops](../st-project-pilot-ops/SKILL.md) 四(缺陷台账载体约定)+ [日报模板](../st-project-pilot-ops/daily-report-template.md) 数据口径 |
| (项目自定义类型) | 如 需求 / 缺陷 / 变更 等常规工作项分类,项目自选 | 项目侧约定 | 项目约定文件;逻辑名 + 映射原则同 §B |

### 轴三:优先级轴(建议)

| 标签(逻辑名) | 用途一句话 | 谁打 / 谁摘 | 来源条款 |
|---|---|---|---|
| P1 / P2 / P3(或项目自定) | 缺陷/工作项优先级,验收出口线按它计数(如"无未关闭 P1/P2") | 打:分诊人(试运行期归值守分诊);摘:升降级时由分诊人改打 | [st-project-pilot-ops](../st-project-pilot-ops/SKILL.md) 三(四级分诊 P1/P2/P3/非缺陷)、二(出口标准) |

优先级口径对齐(防两套 P 编号打架):

- 默认建议全项目**直接沿用 pilot-ops 的 P1/P2/P3 三级标签**,一套编号用到底
  ("非缺陷"是分诊出口不是标签,不建);
- 项目若自定分级(如 P0~P3 四级),必须在此写明与 pilot-ops 分诊级别的映射
  (例:P0/P1 → pilot-ops P1,P2 → P2,P3 → P3),否则试运行日报与日常看板各说各话;
- 「回归缺陷置顶」是**接单排序规则**不是优先级标签(dev-regression 六),不为它建标签;
  pm-test 用例里的 `priority` 是**用例字段**不是 issue 标签,同理不建。

### 一次建齐清单(新项目启用时)

映射填完后,以 GitHub Issues 为例一次建齐(`<映射:xxx>` 换成项目实际标签名;
颜色/描述项目自定;已存在的标签用 `--force` 幂等更新,或先 `gh label list` 实查跳过):

```bash
for name in \
  "<映射:待细化>" "<映射:待开发>" "<映射:方案确认中>" "<映射:AI开发中>" \
  "<映射:自测报告中>" "<映射:PR审查中>" "<映射:PM验收中>" "<映射:人工测试中>" \
  "<映射:已完成>" "<映射:已打回>" "<映射:已挂起>" \
  "<映射:平台能力受限>" "<映射:人工介入>" "<映射:待复测>" \
  "<映射:回归缺陷>" "<映射:验收记录>" "<映射:试运行缺陷>" \
  "<映射:P1>" "<映射:P2>" "<映射:P3>"; do
  gh label create "$name" --color "<项目自定>" --description "<轴:逻辑名>"
done
```

**启用自检:按本总表逐行核对——项目标签已建、映射已填。** 类型轴/优先级轴中项目暂
不启用对应 skill 的枚举(如尚未进入试运行)可暂缺,但**首次使用该 skill 前必须补建**
(各来源 skill 的"首次使用先建"条款仍然有效,本表只是让你能一次建齐)。

## C. 分支与 worktree

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| C1 | 分支命名约定 | 建议 | 默认 `issue-<n>-<slug>`;项目可改,但必须含工作项编号 |
| C2 | worktree 存放目录 | 必填 | worktree 建在哪(仓库内约定目录或仓库外目录);仓库内目录须确认已在版本忽略清单里 |
| C3 | worktree 初始化命令 | 必填 | 新建 worktree 后必须跑什么:依赖安装命令、环境文件准备、其他一次性初始化。逐条列出,按序执行 |
| C4 | 当前发布级别 | 必填 | ①开发期 main-only / ②试运行·生产起部署只认发布 tag / ③多版本并行 release 分支——三级判据与动作见 st-project-std-git「发布与分支策略」;级别变更时更新本行 |
| C5 | 发布 tag 命名规则 | ②③级必填 | 如 `vX.Y.Z`(规则项目自定);①级留空 |
| C6 | 发布台账位置 | ②③级必填 | 每次发布记录 tag/日期/环境/包含哪些工作项;载体项目自定(文档或工作项系统);①级留空 |

## D. dev 环境

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| D1 | dev 启动方式 | 必填 | 启动命令(用项目声明的脚本,不裸起运行时)、默认端口、日志在哪看 |
| D2 | 并行隔离约定 | 必填 | 多个 worktree 并行时端口如何避让、数据如何隔离(每实例独立库/数据目录的具体做法);"禁止借用他人实例"的边界 |
| D3 | 重启与缓存清理 | 必填 | 改哪些东西必须整体重启才生效;构建产物/缓存陈旧时的清理方式(哪些能删、哪些是数据不能删) |
| D4 | 测试账号与角色映射 | 必填 | 自测可用的账号清单(角色 → 账号);权限类验证必须有非管理员的目标角色账号(要求来自 st-project-dev-test) |

## E. 证据与报告

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| E1 | 报告形态与发布面 | 必填 | 测试报告用什么格式(模板见 st-project-std-docs)、怎么挂到工作项上 |
| E2 | 截图归档与图链形式 | 必填 | 截图存放位置(如证据专用分支/目录)、贴到工作项时的合法图链拼法——私有仓尤其要按 st-project-std-evidence 的规范声明经核实可显示的形式 |

## F. PR 与合并

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| F1 | PR 模板与评审人 | 建议 | PR 正文模板位置、默认评审人 |
| F2 | 合并权限 | 必填 | 默认铁律:**AI 绝不自行合并 PR**。库级已有一条成文授权,项目无需在此重复登记:pm-dispatch 调度员对本批收单核实通过且评审闸门(st-project-dev-review)清零的 PR 自主合并(2026-08-12 PM 拍板 + 2026-08-14 评审闸门,范围与条件见该 skill「调度员自主合并 PR」);此处只登记**其余场景**的额外授权(授权范围、生效条件、由谁批准),没有则写「无——仅库级授权生效」 |

## G. 升级与挂起

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| G1 | 失败升级通道 | 必填 | 升级给谁(技术负责人/PM)、走什么渠道(工作项评论/对话/其他)、期望的响应方式 |
| G2 | 平台问题上报渠道 | 必填 | 平台(Steedos)能力问题报到哪(平台仓库/联系人)、报告要素;挂起的工作项由谁负责跟踪排期 |

## H. 项目专属纪律

| # | 配置项 | 必填 | 要声明什么 |
|---|---|---|---|
| H1 | 开工前必读清单 | 必填 | 项目约定文件位置(CLAUDE.md 等)及其他开工前必读文档 |
| H2 | 测试执行方式 | 必填 | 自测是否用独立测试实例(st-project-dev-test 的默认要求);暂不具备双实例条件时,显式声明降级方式与补偿措施 |

## 启用自检

逐项过一遍:能对每个必填项给出明确答案 → 可开工;任何必填项答不出 → 不开工,把缺项
清单报给项目侧补齐。首个工作项跑完后,把被实战证明缺失或含糊的条目按
st-project-meta-retro 当场补进本文件——补的是"要声明什么",不是某个项目的实际值。
