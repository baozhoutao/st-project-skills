# st-project-dev-blueprint — 总体方案蓝图

> 建设状态:可用(未实战) | 批次:第二批(补建) | 主责 AI 岗位:AI 架构师 | 人类闸门:技术负责人审定蓝图

**会话命名(2026-08-12 约定)**:进入本 skill 第一动作把会话标题设为
**`蓝图 | <SRS Vx> | <MMDD>`**;工具机制与无工具豁免见 pm-test「会话命名」权威条款。

**设计核心:签字 SRS 与逐工作项开发之间缺一张全景图——没有它,「本项目到底用了 os
哪些能力」的统计和「第三方接口有几个」的正式台账都不存在,dev-design 判「跨模块/
改已有」也无图可查,只能靠逐项现场侦察。蓝图把这层补上:SRS 签字后一次性成图,
技术负责人审定,此后只随变更更新——它回答两个问题:①业务需求→steedos 能力怎么映射
(全景成册);②与外部系统的集成边界长什么样(接口台账)。蓝图是宏观的一次性产物,
微观留给 dev-design;两层各管各的,冲突时以蓝图+最新修正为准并回填蓝图。**

## 目标(防什么错)

1. **能力使用面无账可查**——项目做完了都说不清用了平台几类能力、定制点有多少;
   平台升级评估、复盘估算校准、下一单报价全都没有底数;
2. **接口边界无正式台账**——「跟某系统打通」散落在 SRS 各章,没人汇总过接口有几个、
   文档谁出、联调环境谁给;pre-quote 的接口对接假设签完约就没人对着落地追责,
   联调期互相等对方是集成类项目最经典的工期黑洞;
3. **dev-design 判定无地图**——三问判定树问「跨模块?」「改已有?」,但项目里有
   哪些模块、哪些共享资产,没有一张图可对,逐工作项现场侦察既慢又漏;
4. **超范围能力默默吸收**——推导中发现 SRS 要求的能力/接口超出报价工作项清单,
   不对账就没人发现,做了就是白做(范围失守从这里开始,不是从变更谈判桌上)。

## 与相邻工序的分层(先分清,再动手)

| 层 | 归属 skill | 时机 | 粒度 | 结论性质 |
|---|---|---|---|---|
| 场景级粗判 | st-project-pre-intake | 售前 | 逐场景标四态(原生/定制/做不了/待验证) | 初判,允许待验证 |
| **全景精判(本 skill)** | st-project-dev-blueprint | SRS 签字后、批量细化/开发前 | 逐模块「需求→能力类别」映射 + 全项目统计 | 精判,待验证项在此关闭或转验证 |
| 工作项级微观 | st-project-dev-design | 每个工作项开工前 | 动哪些资产、增还是改、三问分级 | 逐项方案,冲突时以蓝图+最新修正为准并回填蓝图 |

## 角色与授权边界(硬)

- AI 是**成图者与对账者**,不是审定者:蓝图生效以技术负责人审定为准,审定前的蓝图
  只是草稿,不得作为 dev-design / pm-dispatch 的引用依据;
- **对账发现超出报价范围的能力/接口 = 变更信号,报 PM 走 st-project-req-baseline
  变更台账,禁默默吸收**——「反正 SRS 里有就做了」是范围失守,不是敬业;
- 蓝图只定「用平台哪类能力」的宏观归类,不替 dev-design 做逐工作项选型:同一需求
  存在多条实现路径时,蓝图记录候选路径并标注「选型待 dev-design 逐项走高风险流程」,
  不越级拍板;
- 需求疑义(SRS 读不懂、前后矛盾)不由本 skill 解释:按 st-project-req-baseline
  差异登记上报,蓝图对应条目标「待修正 N」——**蓝图无权替签字基准圆场**。

## 输入

1. **客户签字的 SRS + 修正链**(st-project-req-baseline 产出)——蓝图唯一需求依据;
2. st-project-pre-intake 的平台能力覆盖度初判(有则用)——粗判前身,逐场景升级为精判;
3. st-project-pre-quote 的工作项分解清单 + 假设与除外清单(有则用)——对账基准;
   接口对接假设是接口台账的素材起点;
4. 更新时:req-baseline 的修正记录 / 已获客户书面确认的变更条目。

缺 1 → **不做蓝图**。未签字不进开发是 req-baseline 的门禁,蓝图同受约束;唯一例外
同其口径(PM 书面明示临时基准),且蓝图首页必须标注所依据的临时基准与版本。
缺 2/3 → 照常成图,但对账一节明写「无报价清单可对账」并把这一事实报 PM(通常
意味着售前资产断档,本身就值得登记)。

## 产出(逐项可核对)

| # | 产出 | 核对点 |
|---|---|---|
| 1 | steedos 能力映射清单 | 按 [blueprint-template.md](blueprint-template.md) §2;逐模块「业务需求→能力类别」映射,每条带 SRS 出处与判定依据;末尾全项目汇总统计表(各能力类别用量 + 定制点计数);只写「用哪类能力」,平台语义细节引用平台 skill 不复读 |
| 2 | 集成接口台账 | 按 [integration-ledger-template.md](integration-ledger-template.md);每接口一行九要素齐全;**含个数统计行**;零外部集成也明写「本项目零外部集成」——空白与零是两回事 |
| 3 | 对象模型总图 | 对象清单 + 关系清单(文字/表格形式,不强求画图);共享对象(被 ≥2 模块读写)单独标出 |

四件汇成一份蓝图文档(骨架见 [blueprint-template.md](blueprint-template.md)),
版本号与 SRS 版本/修正号对应。

## 流程

每步三件事:做什么 → 产出什么 → 卡住怎么办。

### ① 对基准:锁定推导底版

- 做什么:确认签字 SRS 版本与修正链读齐(当前有效基准 = 签字版 + 修正链,两样一起
  读);把「蓝图基于 SRS Vx + 修正 1..N」写进文档信息区;收齐 pre-intake 覆盖度
  初判与 pre-quote 报价清单备用。
- 产出:蓝图文档信息区(基准版本、输入清单)。
- 卡住:SRS 未签字 → 停,报 PM(见输入节);修正链散落找不齐 → 先回
  req-baseline 补台账,禁凭记忆凑「大概改过哪些」。

### ② 逐章推导能力映射(粗判→精判)

- 做什么:从签字 SRS **逐章**推导,按模块列「业务需求 → 用平台哪类能力」。能力
  类别按固定清单逐类扫(见下),每条映射带 SRS 出处 + 判定依据(纪律同 pre-intake:
  禁「应该可以」);有 pre-intake 初判的,逐场景对照升级——**粗判「待验证」项在此
  关闭(给出精判结论与依据)或转 POC 式最小例验证**,不许原样抄成蓝图结论。

  **能力类别固定清单(逐类扫,不涉及的类别明写「不涉及」)**:
  对象与关系规模 / 视图(列表/表单/看板等)/ 流程与审批 / 权限集与角色 /
  报表与看板 / 导入导出 / 通知 / 定时任务 / 自定义页面与代码点(定制点)/
  **端覆盖(Console/手机 H5:哪些模块、哪些角色、哪些场景在哪个端用,
  2026-08-12 加入)**——pre-intake 场景地图「端」列在此升级为精判,
  H5 场景清单是后续细化「触发操作写明端」与验收分端执行的依据。

  **只写「用哪类能力」,不复读平台语义**:平台某能力怎么配、有什么坑,引用对应
  `steedos-*` 平台 skill 或平台文档,蓝图里出现平台配置细节即写超纲。
- 产出:steedos 能力映射清单 + 全项目汇总统计表(产出 1)+ 待验证项关闭记录。
- 卡住:某需求映射不到任何能力类别、或对平台能不能做没把握 → 转 POC 式验证
  (搭最小例)或问平台方,结论回填后关闭;验证做不了当场做 → 条目标「待验证 +
  验证方式 + 期限」,**蓝图可以带少量限期待验证项送审,不可以带「应该可以」**。

### ③ 集成接口台账

- 做什么:扫全 SRS(含范围外章节——写明不含的接口正是台账要显式排除的),把每个
  与外部系统的集成点登记成行:编号 / 对接系统 / 方向(进/出/双向)/ 协议 /
  数据项概要 / 接口文档责任方 / 联调环境责任方 / 对方配合人 / 验收方式。末尾
  **个数统计行**。pre-quote 假设清单里的接口对接假设逐条核对是否都有对应行。
- 产出:集成接口台账(产出 2)。
- 卡住:责任方/配合人 SRS 没写 → 填「待定 + 向谁要 + 期限」,**「待定」必须带
  期限,无期限的待定 = 没登记**;全项目确实无外部集成 → 台账正文明写
  「本项目零外部集成(已扫 SRS 全文含范围外章节)」,禁留空白页。

### ④ 对象模型总图 + 模块依赖

- 做什么:从能力映射清单归纳对象清单(对象名/所属模块/一句话职责)与关系清单
  (谁引用谁、一对多/多对多);**被 ≥2 模块读写的共享对象单独标出**——这张名单
  就是 dev-design 第 2 问「跨模块?」的直接判据。再从对象引用与业务先后推导模块
  依赖,给出建议开发顺序(拓扑序),每条依赖带一句话理由。
- 产出:对象模型总图(产出 3)+ 模块依赖与建议开发顺序(产出 4)。
- 卡住:两模块互相依赖成环 → 如实记录环并给拆环建议(先建共同底座/接口先行),
  拆不拆、怎么拆报技术负责人定,禁擅自砍掉一边假装无环。

### ⑤ 与报价工作项清单对账

- 做什么:蓝图工作面(映射清单的能力条目 + 接口台账)逐条对 pre-quote 的工作项
  分解清单:对得上的标记对应工作项;**对不上的(SRS 推导出但报价清单没有的能力/
  接口)= 变更信号**,列成对账差异清单报 PM,由 PM 走 req-baseline 判定归类
  (差异还是变更),**禁默默吸收、禁自行判「小事就带做了」**。
- 产出:对账结果(蓝图文档 §6:对上清单 + 差异清单)。
- 卡住:报价清单粒度与蓝图对不齐(一项对多条/多条对一项)→ 按「能力条目是否被
  报价范围覆盖」判,不苛求一一对应;判不了覆盖与否的条目进差异清单交 PM,不猜。

### ⑥ 技术负责人审定

- 做什么:成稿送技术负责人审定(重点:能力归类对不对、定制点是否遗漏、依赖顺序
  是否可行、对账差异清单是否如实);审定记录(谁/何时/结论/批注)写进文档信息区。
  审定通过蓝图即生效,通知下游(dev-design 可引用、pm-dispatch 可按依赖分组)。
- 产出:审定生效的蓝图 V1.0。
- 卡住:打回 → 按批注修订再送审,版本号递增;技术负责人迟迟不审 → 如实上报闸门
  状态,**不得以「没人反对」当审定**(同 dev-design 的沉默不是放行口径)。

### ⑦ 运行期:只随变更更新(硬)

- 做什么:蓝图是活文档,但**更新触发只有两个:req-baseline 落了修正 N,或变更
  获客户书面确认**。触发后增量更新受影响章节,更新记录注明「按修正 N / 按 CR-NNN」,
  蓝图版本号递增并与 SRS 版本/修正号对应;dev-design 逐工作项实现中与蓝图的出入
  按其 ⑥ 判错兜底处理,结论回填蓝图(回填也算随修正更新,因为出入本身要先走差异
  登记拍板)。
- 产出:新版蓝图 + 更新记录。
- 卡住:有人要求「开发中顺手把蓝图改准点」→ 拒绝并说明通道:先走差异登记/变更
  台账,拍板后才动蓝图——**逐工作项开发不改蓝图**,否则蓝图漂移成第二真值,
  与 req-baseline 防的「两个真值打架」同罪。

## 防错要点(硬纪律速查)

1. **只认签字 SRS,不认口头(硬)**:蓝图唯一需求依据 = 签字版 + 修正链;客户/PM
   口头补充一律先进 req-baseline 两条通道,拍板后才进蓝图;
2. **能力判定带依据(硬)**:每条映射写明 SRS 出处与判定依据(同 pre-intake 纪律);
   「应该可以」出现即违规;拿不准 = 限期待验证,不 = 乐观假设;
3. **接口台账逐条有双方责任人,「待定」必须带期限(硬)**:文档责任方、联调环境
   责任方、对方配合人三项无着落的接口 = 工期黑洞,期限到了未落实报 PM;
4. **零外部集成也要明写(硬)**:「本项目零外部集成」是查证过的结论,空白是没做——
   与 proposal-template「无是查证过的结论,空白是没查」同构;
5. **只随变更更新(硬)**:更新触发 = 修正 N 或变更获批,逐工作项开发不改蓝图;
   蓝图版本与 SRS 版本/修正号对应,对不上号的蓝图不得引用;
6. **与 dev-design 分工(硬)**:蓝图宏观一次性、dev-design 逐工作项微观;两层
   结论冲突时以蓝图+最新修正为准,dev-design 的新发现经差异登记拍板后回填蓝图;
7. **对账差异禁默默吸收(硬)**:超出报价范围的能力/接口报 PM 走变更台账,归类
   (差异/变更)不由 AI 裁;
8. **不复读平台语义**:平台能力怎么用、有什么边界,引用 `steedos-*` 平台
   skill;蓝图写的是「本项目用哪类、用多少」。
