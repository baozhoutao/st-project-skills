# st-project-pm-test — PM 验收测试

**设计核心:把「判定」从 AI 自由发挥改造成机器可核对的比对,让证据链先于结论存在。**
每个关键断言都有一个不经过模型的核对点(lint 脚本、指纹、results.json 渲染、证据一致性校验)。

**角色边界(硬)**:验收会话**禁止改代码、禁止打补丁**——测到一半顺手修了就是在测自己的修复,
基线也变了。缺陷只记录不动手。AI 的输出边界 = 证据 + 建议;打回/流转/起 issue 永远等 PM 确认
(除非调用时明确授权「测完直接处置」)。

**前置数据缺口自行编造补齐(2026-08-10 PM 拍板,反转原「禁止计划外造数」——旧口径曾把
一个主数据缺口连坐 11 条用例退回)**:用例声明或步骤依赖的前置数据在环境/仓库里不存在
(缺主数据文件、缺配套绑定、lookup 无候选)时,**不退回不测**——执行方在**环境准备阶段**
自行编造合理数据补齐:优先落成仓库导入语料(随批次小 PR 收编,数据即资产),来不及入库的
当场按产品 UI 造;编了什么一律如实登记进 `fingerprint.seeds`,并在报告里附「回填用例
前置声明」建议。执行中才发现缺数据 → 回环境准备补齐后重跑该用例。
**测试语料与初始化数据分家(2026-08-10 PM 纠正,硬)**:项目的**系统初始化数据目录**
(客户上线基线语料)不是测试数据目录——编造的测试语料**禁止混入**初始化目录,也**禁止
改写**初始化文件的既有行;测试语料落**独立的测试数据目录**(目录名以项目约定为准,
配 README 记录每个文件的造数目的与导入顺序),对初始化既有行的修改诉求做成执行轮
UI 手工步骤登记在该 README(导入通常无 upsert,改既有行本也走不了导入)。
**造数避让规则**:编造的数据不得改写**用例点名实体**的既有属性(点名人员/任务的岗位、
资质、归属被断言依赖,动了就毁断言)——补数据用新实体或未被任何用例点名的实体。
仍然硬禁的只剩一条:**为让某条预期成立而伪造/篡改被测流程本应产出的结果数据**——
前置可以编,结果不能编;判定依据的观察必须来自系统真实行为。

## 执行模型:主 agent 是调度台,测试动作全部下沉子 agent

**主 agent 全程不亲自执行任何用例、不下任何 verdict、不打开浏览器。** 它只做:lint 门禁、
按场景切执行包、出环境分配表、派发、收单核实、汇总发布、处置建议。

| 角色 | 数量 | 职责 | 硬约束 |
|---|---|---|---|
| 主 agent(调度台) | 1 | 门禁/切包/环境分配/派发/收单核实/汇总发布/处置建议 | 禁执行用例;禁下 verdict;禁替子 agent 补证据 |
| 执行子 agent | 每包 1 个 | 自起隔离环境→固化本包指纹→包内串行执行→只产观察,results.json+截图即时落盘 | 禁下结论;禁跨包操作 |
| 盲审子 agent | 每包 1 个(独立于执行者) | 只看验收标准(①-A 案例文件 / ①-B issue 期望+符合度清单)+截图+observed,三角核对回填 verdict | 只读;与执行子 agent 隔离;指定 Opus |

为什么强制下沉(不是可选优化):执行与判定分离靠**物理隔离**实现而不靠自律——执行细节
(选择器调试、环境修复、重试)会污染判定;主 agent 上下文只装分工表与各包摘要,长批次
不因执行噪音塌方,汇总质量稳定;场景级并行成为默认形态;单场景批次也照样委派
(1 执行 + 1 盲审),只是不开多环境。

## 流水线

```
主:① lint预检 → 切包+环境分配表 → 派发
子(每场景一包,互不干扰,可并行):② 基线指纹 → ③ 执行(只产观察) → ④ 盲审(独立子agent)
主:⑤ 收单核实 → 发布(验收issue) → ⑥ 处置建议
主(PM 授权后):⑦ 批次收口循环 = 处置落地 → 派发修复(pm-dispatch)→ 复测 → 至批次全绿
```

**零中途提问承诺**:①~⑤ 全程不向 PM 提问、不等待回复——一切不确定性按三问分诊收敛为
五态结论,「该问 PM 的问题」以 ⚠️/❓ 形式随验收 issue 交付,PM 两端参与
(测前:①-A 是 merge 用例、①-B 是**已写在缺陷单里的期望**——后者 PM 报单时就已参与完,
开测前无需再动手;测后都是看结果+确认处置),过程可以完全不在场。
唯一允许中途停机:P0 级环境阻塞修 2 次不好。
过程中的逐用例回报是透明日志,不要求 PM 回应。

## ① 输入:PM 的验收标准

**两条入口,按批次性质二选一** —— **场景验收**走 ①-A(用例文件),
**缺陷批次复测**走 ①-B(缺陷工作项本身)。两条入口只在「验收标准从哪来」这一点不同,
②~⑦ 的全部纪律**一律不降级**。

### ①-A 场景验收:PM 核对过的测试用例(默认入口)

**用例是 PM 的验收标准,是持久资产,不是 AI 的产物。** 三条硬规则:

- 输入**只认** PM 核对定稿的标准用例文件(格式见 [case-template.md](../st-project-pm-case/case-template.md)),
  保存于仓库 **`docs/验收测试用例/`**(约定目录,走 PR 合入 main,长期维护、多轮复用)。
  尚未入库的,开测前先入库(单独小 PR 或搭车);
- **不收粗需求**:pm-test 不做需求规范化。起草/修订用例走配套 skill
  [st-project-pm-case](../st-project-pm-case/SKILL.md)(AI 起草 → PR → **PM merge 即定稿**),
  合入 main 后才有资格作为本 skill 的输入;
- **AI 在验收流程中不得修改用例内容**:不代写、不脑补步骤、不重新解释预期。

开测前跑门禁(防格式/可判定性问题):

```bash
node scripts/acceptance-lint.cjs docs/验收测试用例/<文件>.md
```

退出码非 0 = 有案例要素不齐或预期不可判定 → **不齐的案例不进执行队列**,标 ⚠️ 无法执行并
写明缺什么,原样退回 PM 修订;其余案例照测。

### ①-B 缺陷批次复测:验收标准取自缺陷工作项本身(2026-08-17 PM 拍板加入)

**适用**:一批**已合入 main 的缺陷修复**要统一验证,而这些修复点**现有场景用例覆盖不到**。
**只收缺陷单**(硬判据:缺陷类标签 / 验收派生缺陷 issue,可用 `gh` 核标签)——**功能工作项
一律走 ①-A,无用例先补用例(pm-case)**:功能的验收标准必须经 PM 定稿用例承载,拿工作项
正文当标准 = 绕过 pm-case 的定稿闸门,那才是本入口真正要防的后门。

这不是例外情况而是常态 —— 缺陷是按**现场现象**报的,用例是按**原需求**写的,两者天然不同源:
修复新增的字段/入口/门禁,原用例的预期里根本没有(判例:某单给 H5 详情补了一个字段,
对应场景用例的预期字段清单里压根没这一项,用它去验只能验出「与用例一致」——什么也没验)。

**这种批次不强制先补用例文件。** 验收标准直接取自**缺陷工作项本身** ——
issue 里的「现象 / 期望 / 复现步骤」就是 PM 亲手写的验收标准,与用例文件**同源同权威**;
硬要先翻译成用例文件,是多一道转录、多一处失真,还把批次卡在 PR 合并上。

**入场门槛(逐单核,不齐的单不进执行队列)**:

1. **有可判定的期望** —— issue 正文或评论里写得出「应该看到什么 / 不该看到什么」的断言。
   **只有一张截图、没有文字期望的单** → 标 `not_run` ⚠️ 并写明缺什么,**退回 PM 补一句话,不猜、不代写**
   (与 ①-A 的 lint 门禁同一条纪律:预期不可判定就不进队列);
2. **修复已合入 main** —— 挂在分支上的修复不测,测了也是测分支;
3. **开发侧的需求符合度清单在盘** —— 那是开发对自己的逐条声明,验收正是要拿它对质。缺清单的单
   标 ⚠️ 退回开发侧补,不代替它写。

**门槛核查逐单留痕(硬)**:三条门槛的核查结果——每单的期望出处(issue 正文/评论的
永久链接)、修复合入 main 的 PR/commit、符合度清单评论链接——随 issue 清单写进验收 issue
正文,⑤ 收单核实照单核对。①-B 没有 lint 脚本那个不经过模型的核对点,**留痕就是它的
核对点**:核查只存在于主 agent 脑子里 = 没核查。

**验收标准的优先级(冲突时高者胜)**:

```
说明书/需求基准  >  缺陷 issue 里 PM 写的期望  >  开发侧需求符合度清单
```

清单与 issue 期望冲突 → **按 issue 判**,并把冲突记进 `side_findings`(那是静默降级的信号);
issue 期望与说明书冲突 → 该条按 `spec-divergence` 归档(⑥),**不自行选边**。

**明确不做的事**:

- **不把这些临时断言写进 `docs/验收测试用例/`** —— 那是 PM 定稿资产,不接受验收会话的产出
  (①-A 第三条「AI 不得修改用例内容」在本入口同样有效);
- 要把本批经验沉淀成长期用例,**走 pm-case 另起 PR**,与本轮验收**异步**,不阻塞;
  但沉淀不靠自觉——⑥ 的处置清单**必须带一行沉淀建议**(本批断言:建议沉淀 pm-case /
  建议豁免+理由一句)交 PM 勾选,否则「异步」= 永远不发生,用例资产库慢性空心化。

**结构落地**:

- 每个缺陷单派生 1~N 条断言,编号沿用 `<批次slug>-<序号>`(如 `H5R1-001`),
  在 results.json 的 `cases[].issue` 里填对应 issue 号 —— 一个 issue 可对多条断言;
- **断言清单首轮发布时随 issue 清单固化进验收 issue 正文,复测轮沿用编号,禁止重派生、
  禁止重编号**——「复测发布」按编号合并 results.json、acceptance-history 按编号排逐轮
  序列,编号一变机读历史即断(①-A 的编号写死在用例文件里天然稳定,①-B 的稳定性只能
  靠这次固化);
- **用例基准字段**填 issue 清单(编号 + 各自永久链接),替代 ①-A 的用例文件 blob 链接;
- 发布、状态标签、⑥ 分档、⑦ 收口循环**全部照 ①-A 走**,没有任何简化。

**与 ①-A 的唯一区别就是标准来源。** 执行/盲审分离、五态、指纹、证据落盘、三态分离、
负例正例成对、results.json 结构、双层语言纪律 —— **一条都不减**。
理由:本入口省掉的是「把 PM 已经写清楚的期望再抄一遍成用例文件」这道转录,
**不是省掉验证强度**;真要放松强度,省下的每一分钟都会在假绿里还回去。

## ② 基线指纹(执行子 agent 逐包固化;没有指纹的结果无效)

每个执行子 agent 在自己的隔离环境上、本包开测前固化,写进本包 results.json 的 `fingerprint`:

- serving 进程实际代码的 commit SHA——`lsof` 按端口查进程 cwd,到该目录 `git log -1`;
  **不信启动日志、不信热重载**,存疑就按端口重启取证;
- 进程唯一性(该端口仅 1 个进程)、库路径;
- 平台版本(规范格式:`@steedos/*@<版本>`——历史聚合按它对齐,禁自由文本)、种子脚本清单、全部测试账号(角色→账号映射);
- 核实 serving commit **已包含被验收的改动**(陈旧基线是历史上最贵的假缺陷源)。
- 起服务一律用**项目 package.json 的 dev/start 脚本**(裸起运行时会丢脚本携带的环境变量,
  登录路由/时区类问题会被误判成产品缺陷)。
- **测试必须自起隔离实例**(独立端口 + `-d file:` 独立库,launch 配置起),**禁止借用
  他人正在使用的服务实例**(PM 拍板 2026-08-08)——共享实例上的数据操作互相污染,
  且会写库的基线脚本在别人的库上重放有配置回退风险。跑任何脚本前先核对其地址
  环境变量(如 `OS_BASE`)确实指向自己的实例。

**前置业务数据约定:走 UI 导入页面灌入,两层目录分家**——**系统初始化数据**(客户上线
基线语料,如 `docs/import-data/`)先灌,**测试补充语料**(验收编造数据,独立目录,如
`docs/验收测试数据/`)后灌;两层严格分离(见开头「测试语料与初始化数据分家」)。数据即
资产,免每轮重造;导入了哪些文件记进 `fingerprint.seeds`(`<目录>/<文件>@<commit>`);
导入页覆盖不到的(账号/权限基线)才用脚本,测试数据目录 README 里登记的 UI 手工步骤
逐条照做。具体文件内容与导入注意事项以各目录和项目文档为准,本 skill 只约定结构。

**账号授权基线对照项目授权文档(2026-08-10 教训)**:测试账号该绑哪些权限集,以项目的
授权文档(实施手册/权限矩阵/权限集清单;权限矩阵**优先用 st-project-dev-inventory
从元数据派生的权限矩阵视图**,元数据即真值,2026-08-12 起)为准逐一核对齐全——尤其**显式授权制**的入口
能力集(不随业务角色权限集自动携带、需单独加一行绑定的),漏绑会把「入口按设计不可见」
测成缺陷疑点,整条权限用例白跑。用例账号命名与既有建号脚本不一致时,按用例为准建号,
并在报告里给出统一命名建议。

指纹中途变了(重启到了新 commit、换了库)→ 之前所有结论作废,整场重来。

## ③ 执行(执行子 agent)—— 只产观察,不产结论

- 真机 UI 逐步操作(Console/H5),禁拿代码实现、bundle、纯 REST 断言当证据。
- **浏览器选择(2026-08-10 明确)**:探索性操作——找入口、核对路由与选择器、复核页面
  状态——**优先用内置浏览器(Claude Code Browser 面板)**,起得快、免脚本成本;
  **产证据的执行步骤**一律走全局 playwright + channel chrome(证据只认落盘文件,
  Browser 面板截图存不了盘,见 [traps.md](traps.md) 末节);**禁用用户本人的日常
  Chrome 会话(claude-in-chrome)**——测试登录态与数据会污染用户自己的会话。
- 写操作案例先抓 **before**(列表计数/记录不存在),后抓 after——没有 before 证明不了因果。
- 每案例测完**立即**把原始观察追加写入本地 `results.json`(逐案例落盘,防崩防事后改口),
  并在对话里即时回一行:`AC-003 观察:after 列表计数与 before 相同,无新增(截图×2)`。
- 截图规范与命名见 [traps.md](traps.md) 末节。证据只认落盘文件。
- **截图回看确认(硬)**:每张截图落盘后立即用 Read 打开图片回看,确认三点:①截到的是目标
  页面/区域 ②图内容支撑要记的 observed ③非半加载/空白态。不符**当场重截**,禁止"拍了就算"。
  回看到的内容写进该证据的 `shows` 字段(一句话,写图里实际可见的东西,不是写预期)——
  `shows` 会渲染成 issue 里图片下方的图注,图注与图不符 PM 一眼可拆穿。
- 失败不中断:继续测下一个;仅 P0 失败且毁掉后续前置时,受影响案例记 blocked 并写因果。

### 执行中碰到问题:三问分诊

| 类 | 情形 | 处置 |
|---|---|---|
| A | 自己操作失误(点错/输错/弄脏数据) | 诚实记录,案例作废重跑;脏数据先重置。**禁把自己的失误当产品行为记入观察** |
| B | 环境问题(服务挂/登不上/数据没种上/前置数据缺失) | 可自修(重启/重跑种子/按「前置数据缺口自行编造补齐」条款回环境准备补齐),修完**重核指纹**、案例从头重跑;修 2 次不好→受累案例记 blocked,写进「环境异常记录」,不起缺陷 issue |
| C | 疑似产品缺陷(实际≠预期) | 正常产出:当场抓证据,**不修不绕不当场定罪**,终判交盲审 |
| D | 案例与 UI 对不上(按钮名/入口找不到) | 先过 traps N2/N14;仍不一致→记「文件写X实际Y」+截图,⚠️ 交 PM 判(可能文件过时,也可能产品改坏了,AI 不选边) |
| E | 复现不稳定/原因不明 | ❓ 无法判定:记两轮观察差异,交 PM。不猜 |
| F | 旁路发现(测A时瞄到B不对) | 记入 `side_findings`(一句话+截图),不展开追查不打乱执行序 |
| G | 权限类异常(无权提示/菜单看不到/403) | **先核对测试账号自身的岗位、权限配置是否合理**(对照项目权限基线与案例指定角色):配置不对 = 账号没配对,按 B 修复后案例从头重跑;配置合理仍异常才按 C 抓证据交盲审 |
| H | 慢/卡/超时(等不到元素、接口"要好几秒") | **默认按 B 环境类处置,不得直接按 C 记疑似缺陷**——脚本 `waitFor` 的墙钟时长 ≠ 产品耗时。要主张"产品慢",必须补两个数字:①服务端单点耗时(REST 直调计时)②端到端耗时;只有**服务端数字本身就慢**才够格记 C。判据见下方「性能类观察的立单门槛」 |

### 性能类观察的立单门槛(硬,2026-08-11 判例)

**判例**:某轮验收旁路记「H5 选人弹窗人员搜索 7~8 秒才返回」并据此立了缺陷单;开发侧排查实测服务端
34~90ms,且 limit 梯度 1→500 耗时平坦(与行数无关)、换账号无差、排序无成本,在 **7.5 倍数据量 +
2.4 倍 CPU 超配**下都复现不出。真身是**脚本等元素出现的墙钟时长**——同一轮报告自己还记着「因脚本
操作层问题(登录固定等待不足/搜索未等到/表单就绪未轮询)判 A 类作废重跑」,以及「另一处下拉等待
25 秒仍无候选」(与该接口毫无关系)。合并判断 = 执行机并发压力,不是产品缺陷。一个假缺陷单换掉了
开发侧一整轮排查。

因此,**「慢」要写进 side_findings 可以,要据此立缺陷单必须先过这道门槛**:

1. **量服务端**:对同一请求直接 REST 调用计时(绕开浏览器与脚本等待),取多次中位数;
2. **量端到端**:浏览器侧从触发到结果出现的耗时,并**扣掉已知的固有等待**(防抖、轮询间隔);
3. **排除数据量因素**:同一接口做 limit 梯度(如 1/10/50/N/2N),耗时随行数平坦 = 固定开销,
   与"数据多所以慢"无关;
4. **排除本机噪声**:记录当时 `load average` 与在跑的 dev server 数量;
5. 只有**服务端数字本身就慢**才够格记 C 类;服务端快而端到端慢 → 前端问题,写清是哪一段;
   两边都快 → **执行环境问题,按 B 记环境异常,不立单**。

**同轮多处不相干的「慢」(不同对象、不同接口)几乎必然是执行机负载**——先查负载,别逐个立单。

### 执行并发上限(硬):本机同时最多 2~3 套环境

每套验收环境 = 1 个 dev server + 1 个浏览器,是重负载。**开测前先清点本机在跑的 dev server**
(按端口 `lsof` 列一遍),把**历史遗留的僵尸实例先杀掉**——幽灵进程既抢 CPU 又可能共库污染。
执行子 agent 在 ② 固化指纹时**一并记录 `load average` 与本机 dev server 数量**;负载显著偏高
(如 load average > CPU 核数)时产出的耗时类观察一律不作缺陷依据,只作环境记录。

### UI 驱动脚本:沉淀复用,不每轮重写

**动手写任何脚本前,先按 `scripts/README.md` 的目录规范查现成的**(查找顺序:
`scripts/acceptance/README.md` 复用清单 → `scripts/README.md` 布局表 → 按能力关键词 grep);
环境基线类到 `scripts/setup/`、跨用途工具到 `scripts/tools/`,新增可复用脚本必须归类并登记。

执行用的 UI 自动化脚本分三层,复用规则不同:

- **框架层(跨场景复用)**:登录(Console/H5)、浏览器启动与截图落盘、**导入向导驱动**
  (上传→字段映射→预览→执行,对象无关)、环境探针(账号可登/数据就绪/测试编号无残留)、
  账号基线修复——统一沉淀在 `scripts/acceptance/lib.cjs`,执行时**先引用它,禁止重写**;
  磨合出的新框架能力(正确的 app 路由、新对象的向导差异等)回填进 lib;
- **场景层(同场景跨轮复用)**:驱动某场景用例的操作序列,放
  `scripts/acceptance/<与用例文件同名>.cjs`,与用例文件**同生命周期**——用例修订 PR 时
  脚本一并修;第 N 轮验收直接复用第 N-1 轮的场景脚本;
- **每轮一次性(绝不复用)**:证据目录与 results.json,每批次独立新目录,
  禁覆盖已发布的历史证据。

脚本入库:验收结束后把新增/修好的脚本提小 PR 进 main(**脚本是设施进仓库,报告是记录进
issue,两者不冲突**;脚本 PR 不夹带用例与业务代码)。场景脚本保留断言入口
(退出码 0/非0、honor `OS_BASE`)——将来项目重建回归体系时,验收跑绿的脚本可直接复用作
回归断言(2026-08-08 拍板:原回归设施已清理)。

**执行子 agent 返回物(收单契约)**:本包 results.json 路径、证据目录路径、指纹摘要、
环境异常记录、逐用例观察一行摘要。返回内容是自述不是真值——以 ⑤ 的主 agent 收单核实为准。

## ④ 盲审判定(盲审子 agent)—— 执行与判定分离

执行包收工后,主 agent 为每个包派发**独立盲审子 agent**(一律如此,不分重要/日常批次):
只喂验收标准 + 截图 + results.json 原始观察三样(①-A 的验收标准 = 案例文件;①-B 的 =
派发模板里全文粘贴的 issue 现象/期望/复现步骤,**外加开发侧需求符合度清单**供三角对质——
清单是 ①-B 的法定第四样,不算污染),切断执行上下文污染;**盲审子 agent 一律
指定 Opus 模型**,不用主会话模型。盲审逐条比对预期,回填每案例 `verdict`,**不许边测边下
结论**——执行者与判定者物理上是两个实例,分离靠架构不靠自律。

**盲审必须逐张 Read 截图**,核对三角一致:图内容 ↔ `shows` 图注 ↔ 该条预期的 observed。
任何一环撑不住,不得维持原结论——回执行阶段重截,或把该案例降级 ❓ 无法判定。
一张撑不住旁白的截图 = 没有证据,不 = 反面证据。

**盲审输出纪律(防偷懒)**:盲审必须在对话里逐案例输出一行三角核对结果,
如 `S02-001:图注✓ observed✓ 预期✗(列表无新增) → fail`——只给汇总总表不给逐案例行
= 没做盲审,按执行记忆下结论是盲审阶段最严重的违规。

五态:

| verdict | 含义 | 成立条件 |
|---|---|---|
| `pass` ✅ | 通过 | 全部预期逐条吻合,每条预期有截图支撑 |
| `fail` ❌ | 不通过 | 任一预期不符;**必须**:复跑≥1 次同现 + 过完 [traps.md](traps.md) 假阴性区(排除项写入 `traps_checked`)+ 复核指纹 + 有复现步骤 |
| `blocked` ⛔ | 阻塞 | 前置/前序失败连带,写明 `blocked_by` |
| `not_run` ⚠️ | 无法执行 | lint 不齐 / 环境不具备(限自行补不了的:平台能力/外部依赖;**前置数据缺口不算**,按「前置数据缺口自行编造补齐」处理)/ 案例与 UI 对不上待 PM 判,写明缺什么 |
| `inconclusive` ❓ | 无法判定 | 复现不稳、证据矛盾——诚实出口,不许硬猜成 ✅/❌ |

**五态之外不设第六态:❌「归到哪」是另一个轴,盲审不碰。** 盲审只判「符合不符合预期」——
一旦让它顺手判「这条属于业务口径不一致」,它就得自创口径重新解释预期,而那正是假绿的成因
(判例:某用例盲审自造口径把 ❌ 改判 ✅,复核才翻回来)。归类由主 agent 在 ⑥ 做,落进
`disposition[].class`,与 verdict 分属两个字段、两个环节、两个实例。

判定账号必须是案例指定角色(admin 跑通不算通过);权限类案例强制零授权对照,两边都截图。

**成本分级**:P0 全套(before/after+复跑+盲审+第二观察点如 DB 佐证——佐证不是替代);
P2 单遍执行即可,但五态与证据规则不降级。

## ⑤ 收单核实 + 发布 —— 首测每批次一个「验收记录」issue;同批次复测修正原 issue;不进 main

**发布前主 agent 逐包收单核实(不采信子 agent 自述)**:results.json 在盘且案例数与验收
标准对得上(①-A 对用例文件;①-B 对首轮固化的断言清单,并逐单核对入场门槛留痕齐全);
每条 evidence 引用的截图文件真实存在;指纹齐全且含「已包含被验收改动」的核实
记录;盲审逐案例核对行齐全。任一不过 → 该包整包退回重派,不进汇总。多包批次一场景一
验收 issue(或与 PM 约定按批次汇成一个)。

**results.json 最小结构**(渲染脚本会硬校验,fail 缺 traps_checked/reruns/repro 直接拒渲):

```json
{ "batch":"20260808-slug", "title":"批次名", "date":"2026-08-08",
  "fingerprint":{ "commit":"40hex", "server":{"port":3000,"verified_by":"lsof+restart"},
                  "platform":"@steedos/*@<版本>", "seeds":[], "accounts":{} },
  "cases":[ { "id":"AC-001", "title":"...", "issue":101, "priority":"P0",
    "verdict":"pass|fail|blocked|not_run|inconclusive", "summary":"一句话",
    "expectations":[ {"n":1,"expect":"...","observed":"...",
      "evidence":[ {"file":"AC-001-1-xx.png","shows":"图里实际可见的内容(渲染成图注)"} ] } ],
    "reruns":0, "traps_checked":[], "repro":[], "blocked_by":"", "notes":"" } ],
  "side_findings":[ {"desc":"现象一句话(说明文字只进这里)","evidence":["文件名.png"]} ],
  "env_incidents":[ {"when":"何时","symptom":"现象","diagnosis":"判断","fix":"怎么处理的","impact":"对结论的影响"} ],
  "disposition":[ {"class":"code|spec-divergence|case-stale|platform|undetermined",
                   "cases":["AC-003"], "action":"建议做什么(业务语言)",
                   "target":"#101", "basis":"归这一档的依据一句话(见 ⑥)"} ] }
```

⚠️ 三条契约坑(渲染脚本实测拒渲/渲成全「—」,执行子 agent 派发词里要带):
`side_findings[].evidence` 是**数组**且只放盘上真实文件名——说明文字、执行日志摘录一律进
`desc`,混进证据数组即拒渲;`env_incidents` 键名**照上**(when/symptom/diagnosis/fix/impact),
自造 id/title/detail 一类键名会渲染成全「—」的空表;`disposition[].class` 只认 ⑥ 的五个
枚举值(拼错即拒渲),带 class 就必须带 `basis`,`cases` 是用例编号数组——❌ 用例没被任何
处置条目的 `cases` 覆盖会告警(未分档的 ❌ 进不了 ⑦ 的路由)。

首次在一个新项目使用:先建 `验收记录` 标签、三枚验收状态标签与过程标签
`验收:复测中`(见下方「状态标签」条款)、`acceptance-evidence` 孤儿分支
(孤儿分支 = 只存截图、只追加、永不合 main、永不删除,初始 README 说明规则)。

**结论区三层结构(渲染脚本产出,勿手拼)**:一句判断(如 ❌ 不建议通过,后缀分流交代
「3 条没通过里:1 条要改代码、1 条要 PM 定口径、1 条要改用例」)→ 一行中文数字
(共 N 条用例:通过 x、没通过 y……,零值态不列)→ 非 ✅ 各态一张两列分组表
(编号加粗,长说明进单元格,不堆 bullet);**其中 ❌ 那张按 ⑥ 的档位再拆子表、多一列「依据」**,
未分档的 ❌ 落「归类待判」子表;主流程断点单独成行;通过清单只列编号、`·` 分隔。
逐用例表不加列(会把编号和说明挤成竖排),只在 ❌ 行的说明列前挂【要改代码】这类短标签。

**报告双层语言纪律**:issue 正文(结论区、按结论分组的表格、逐用例表)是给 PM 看的,
一律**业务语言**——「谁、在哪个页面、做了什么、该看到什么、实际看到什么」;
❌ 的 `summary` 是大白话现象(如「派工后工人手机上看不到新派工单」),
技术词汇(hook/接口/断言/水合这类)只许出现在明细评论与 results.json,渲染脚本会告警。
❓/⚠️ 的 `notes` 同理:写清「疑在哪、要 PM 看什么」/「缺什么才能测」。

**发布流程(顺序固定)**:

1. **截图上孤儿分支** `acceptance-evidence`(只追加、永不合 main、永不删;追加命令见该分支
   README):目录 `<YYYYMMDD>-<批次slug>/`,push 后 `rev-parse HEAD` 拿 40 位 SHA。
2. **渲染**:
   ```bash
   node scripts/acceptance-report.cjs <results.json> --evidence-dir <本地截图目录> \
     --sha <证据commit SHA> --prefix <批次目录>
   ```
   产出 `issue-body.md` + 每个非 pass 案例一个 `comment-AC-XXX.md`,并做证据一致性校验
   (报告引用的截图必须在盘上存在,孤儿文件告警)。图链唯一合法形式:
   `https://github.com/<owner>/<repo>/blob/<SHA>/<路径>?raw=true`
   (owner/repo = 本仓库,脚本自动从 git remote 读取,也可 `--repo` 指定;
   禁 raw.githubusercontent.com;ref 禁分支名;中文路径段已由脚本 encodeURIComponent)。
3. **建验收 issue**:标题 `验收 | <批次名> | <日期> | ✅x ❌y …`(**只列非零态**,零值占位是噪音;
   批次名写模块本身,不塞 PR 号/用例条数这类内部信息),标签 `验收记录` + 按总结论挂
   一枚状态标签(见下方「状态标签」条款),
   正文 = issue-body.md(含 `<details>` 收起的 results.json 全文);逐案例明细贴评论。
   正文写明**验收标准基准**——①-A 场景验收填 `docs/验收测试用例/<文件>.md` 在本轮所用 commit
   的 blob 链接(`https://github.com/<repo>/blob/<40位SHA>/<路径>`);**①-B 缺陷批次填 issue 清单**
   (逐个编号 + 永久链接)。回看任何一轮验收,结果与当时 PM 写下的标准版本永远对得上。
4. **贴前核对图链**:`gh api "repos/.../contents/<目录>?ref=<SHA>"` 确认文件在
   (curl 打图链恒 404 是假阴性,不作判据)。
5. **关联 issue 轻评论**:每个被验收 issue 上只贴一行
   `验收结果:AC-003 ❌,明细见 <验收记录issue评论链接>`——单一真值在验收记录 issue。

### 状态标签:issues 列表的红绿灯(2026-08-12 PM 拍板)

三枚互斥状态标签,让 issues 列表**不点开正文**就能看到每个批次的最新结论
(标题尾巴要读字,标签是色块):

| 标签 | 颜色 | 挂上条件(= 渲染脚本的总结论,一一对应、机器可核对) |
|---|---|---|
| `验收:通过` | 绿 `#2da44e` | 总结论「✅ 全部通过,建议流转」 |
| `验收:不通过` | 红 `#d73a49` | 总结论「❌ 不建议通过」(有任一 ❌) |
| `验收:未决` | 黄 `#dbab09` | 总结论「⚠️ 无不通过案例,但存在未决项」(无 ❌ 但有 ⛔/⚠️/❓) |

- 与 `验收记录` 并挂;任一时刻**只挂三枚之一**,换标 = 摘旧贴新,与改标题**同一次操作**
  (首轮发布贴,复测轮修正标题时换);
- 标签是总结论的**镜像,不是第二真值**:真值仍是逐用例五态 verdict 与渲染出的总结论。
  **禁止手工改标签表达异议**——PM 不认可某条 ❌,走 ⑥ 分档(定口径/改用例)+ 复测转绿,
  标签随复测轮自动翻;发现标签与正文总结论不符,以正文为准当场纠标;
- **第四枚:过程标签 `验收:复测中`(蓝 `#0969da`,2026-08-12 PM 拍板)**——不是结论
  镜像,是复测执行期的在场信号,与当前结论标签(通常 `验收:不通过`)**并挂**。
  没有它,「修复中」与「复测中」在列表里签名相同(都是 open + 不通过),PM 分不出
  这批是在修还是在测。贴/摘时机见「复测就绪标记」的摘标记条款与「复测发布」第 4 步:
  开复测轮摘 `<映射:待复测>` 的同一次操作贴上;复测发布修正 issue 的同一次操作摘掉。
  首测轮不涉及(首测执行期 issue 尚未建立);
- 快速过滤:`label:"验收:不通过"` 即全部待收口的红批次;`label:"验收:通过" is:open`
  即全绿但处置/子缺陷未闭环的批次(收口三条件见 ⑥ 末尾);`label:"验收:复测中"`
  即正在复测的批次;`label:"验收:不通过" -label:"验收:复测中"` 且无待复测标记
  即还压在修复侧的批次。

### 复测发布:同批次第 N+1 轮修正原 issue,不开新 issue

同一批用例的复测(2026-08-08 首个落地项目 PM 拍板)**不开新验收 issue**——修正原验收
issue 的标题统计尾巴、正文结论区、逐用例表为**最新状态**;历史轮的明细评论保留不删。
顺序固定:

1. **合并 results.json**:以上一轮全量 JSON 为底,只更新本轮复测用例的条目(每用例取
   最新一次执行的 verdict,未重测的保留原轮结论);`fingerprint` 整体换成新轮指纹;
   顶层新增/追加 `rounds` 轮次元数据数组,每轮一条:
   ```json
   "rounds":[ {"round":1,"date":"2026-08-01","commit":"<40位SHA>","cases":["全部"]},
              {"round":2,"date":"2026-08-08","commit":"<40位SHA>","cases":["AC-003","AC-007"],"note":"复测原因一句话"} ]
   ```
   首轮不写 `rounds`(**无 rounds = 首轮**,渲染与解析行为不变——向后兼容);复测起必须写,
   `rounds` 是 history 脚本「该 issue 有历史轮评论」的唯一信号,漏写 = 机读历史断轮。
2. **先归档再修正(硬)**:修正正文前,必须把被替换的上一轮 results.json 以「历史轮」标记
   评论归档进本 issue——格式与正文 `<details>` 同构,summary 注明第 N 轮已被修正。渲染
   脚本 `--archive-prev <上一轮results.json>` 直接产出 `comment-history-round-N.md`,贴评论
   即可。这条评论是 history 逐轮解析的数据源,漏归档 = 机读历史只剩最新轮。
3. **复测证据走孤儿分支新批次目录**(如 `<YYYYMMDD>-<批次slug>-r<N>/`,禁覆盖已发布的
   历史证据),push 后同首轮流程拿新 40 位 SHA。
4. **重渲全量并修正原 issue**:带 `rounds` 的 results.json 跑渲染脚本,正文自动多出
   「轮次说明」小节(第几轮/日期/更新了哪些用例/新轮指纹 commit);`gh issue edit` 用新
   issue-body.md 替换正文、按新统计尾巴改标题、**按新总结论换状态标签、摘过程标签
   `验收:复测中`**(镜像规则与贴摘时机见上方「状态标签」条款);本轮非 pass 用例的
   明细贴新评论(历史轮明细评论原样保留)。

report.md 不进代码仓库、不提 PR;本地 results.json 与截图目录是工作副本,发布面是 issue。

## ⑥ 处置建议(先分档,再报清单,PM 确认后执行)

### 分档(2026-08-11 加入):❌ 不是只有一种根,路由也不该只有一条

所有 ❌(以及值得立案的 ❓/⚠️/side_findings)进处置清单前先归一个档。不分档 = 所有 ❌ 默认
「打回开发修代码」,而口径分歧派下去,开发子 agent 只能照用例硬改,改出说明书没说的东西;
或者反复改不对,把 ⑦ 的「修不动」轮次白烧掉。**分档的价值不是标签好看,是处置路由分叉。**

| class | 报告里叫 | 成立条件 | 路由 |
|---|---|---|---|
| `code` | 要改代码 | 说明书/需求写了这条,系统没做到或做错了 | 打回开发侧,进 ⑦ 收口循环 |
| `spec-divergence` | 要 PM 定口径 | 说明书与系统实现各说各的,两边都自洽 | **不派发**;报 st-project-req-baseline 走差异登记等拍板,拍板前该争议点冻结 |
| `case-stale` | 要改用例 | 用例与现行说明书+系统都对不上(用例过时)。**①-B 缺陷批次的对应形态 = 缺陷单里 PM 写的期望本身过时/写错了** | ①-A 走 st-project-pm-case 修订 PR,PM merge 即定稿;**①-B 回 PM 修订该 issue 的期望**(AI 不代改他人写下的期望)。两者都**不立缺陷单、不改代码** |
| `platform` | 平台受限 | 非本项目代码可修的平台能力问题 | 报对应平台仓库跟踪,项目内不修、不维护平台缺陷清单 |
| `undetermined` | 归类待判 | 三查做完仍判不清 | 交 PM 定路由;**不许硬塞进 code 档** |

`spec-divergence` 的拍板有三档结局,AI 不预设哪一档:改代码 / 改说明书 /
**双冻结只改用例**(代码与说明书都不动,只把用例改成按现状判——2026-08-11 首例)。

**归类三查(轻量,禁根因深挖)**:① 说明书/SRS 里有没有这条明确条款(有、且系统没做到 →
倾向 `code`)② 用例的需求来源与现行说明书是否同版(用例比说明书旧 → 倾向 `case-stale`)
③ 系统实际行为是不是「另一套自洽口径」而非漏做(是 → 倾向 `spec-divergence`)。
只做到「说明书里有没有这条」这一层,**不追根因、不读实现细节找原因**(与 side_findings
不展开追查同源——验收会话的边界是证据+建议,不是排查);判不清一律 `undetermined`,不猜。

**AI 只出疑似档位 + 依据,不裁**:归类影响计价与责任归属,与 req-baseline
「差异/变更归类不由 AI 裁」同源。每条处置写一句话 `basis`,引用说明书章节号/修正编号/
issue 号;`spec-divergence` 的 basis 必须写全两边说法(「说明书 §X 写……;系统实际……」),
PM 不必翻原文就能拍。归类**只是建议**:标题统计尾巴与逐用例结论仍只按五态,
不把档位写进标题——判定是真值,归类是待批建议,写进标题就成了第二真值。

### 各档处置细则

发布后在对话里给处置清单(渲染脚本按档分组),逐条等 PM 确认:

- 【要改代码】有 ❌ 且关联 issue → 建议该 issue 打 `已打回`、assignee 交回开发侧、评论附证据链接;
  **打回的既有 issue 不挂成验收 issue 的 sub-issue**——它的父级归属属于需求结构,不被
  验收轮收编(GitHub 单亲约束下抢 parent 会打断原有层级),维持上述双向轻关联即可;
- 全 ✅ 且属某 issue 验收 → 建议流转下一状态(assignee 不变归 PM);建议流转到「已完成」时
  附前置检查结果:该工作项场景断言已入回归巡检清单或已登记豁免(权威条款见
  st-project-dev-regression);
- 【要改代码】❌ 但与被验收 issue 无关 / side_findings 值得立案 → **先查重再建议**:按现象关键词与
  用例编号搜既有 issue(open + closed 都搜,`gh issue list --search` / `gh search issues`);
  已报过的不建议新开,改为建议在原 issue 补充本轮证据(案例编号+图链+指纹),清单里写
  「已报,见 #N」;确认未报的才建议起新缺陷 issue(引用案例编号+图链),
  并**挂为本验收 issue 的 sub-issue**(2026-08-08 首个落地项目 PM 拍板)——GitHub 单亲约束:
  一个 issue 只能有一个 parent,新缺陷天生源自本轮验收、无归属冲突,挂上后验收 issue 自带
  子缺陷修复进度条;
- 【要 PM 定口径】→ **不建缺陷单、不打回**(建了就是把待拍板的事按缺陷派下去):建议
  报 req-baseline 差异登记(现象/两边说法/影响面),清单里写明「等拍板,拍板前该点冻结」;
  拍板落成修正编号后,按结局分别转 `code`(改代码,进 ⑦)/ 文档修订 / `case-stale`(改用例)。
  痕迹只在用例注释与验收 issue 里留,别指望说明书当轮就同步;
- 【要改用例】→ ①-A 建议走 pm-case 起修订 PR(**AI 在验收流程中不得直接改用例**,见 ①),
  清单里写清「用例写 X、现状 Y、依据」,PM merge 该 PR 即定稿,下轮按新用例复测;
  **①-B 建议回 PM 修订该缺陷 issue 的期望**(AI 不代改他人写下的期望),PM 改完下轮
  按新期望复测;
- 【平台受限】❌ 疑似**平台能力问题**(非本项目代码可修)→ 处置建议里单独标出,PM 确认后报到
  对应平台仓库跟踪(项目内不维护平台缺陷清单);报前同样先查目标平台仓库既有 issue,
  已报的建议评论补充复现材料,不重复开单;
- 【归类待判】/ ⚠️/❓ → 列给 PM:补要素下轮再测,或人工看一眼定路由。

**后续报 issue 的素材规则(项目缺陷或平台缺陷都适用)**:PM 让 AI 基于报告报 issue 时——

**动手建单前必须再查重一遍(硬,2026-08-10 判例)**:「建议阶段查过」不算数——建议与动手
往往隔着 PM 批复、甚至换了会话,期间别人可能已把同根因 issue 立了甚至修完合了。执行
`gh issue create` 之前,按现象/根因关键词把 open + closed 一起搜(`gh issue list --search`
/ `gh search issues`,再看命中 issue 的关联 PR 状态),命中同根因 → 不建单,改在既有 issue
评论补充本轮证据并回报「已报,见 #N」。判例:某轮处置拿着 PM 批复直接建单,而同根因
issue 三天前已立、修复 PR 当天已合并,新单当场成了 duplicate 关闭。

issue 正文四要素**只能取自 results.json 与明细评论,禁止凭记忆重新描述**:
- 现象 = 该用例的 预期 vs 实际(业务语言);
- 环境 = fingerprint(commit/平台版本/账号);
- 复现步骤 = repro(因此 fail 用例的 repro 必须**独立可执行**:含登录账号、入口路径、
  具体输入——不看用例文件、不看本对话的人照着也能复现);
- 证据 = 明细评论里的图链(SHA 形式,直接引用)。

**验收派生缺陷 issue 的关闭口径(2026-08-10 PM 拍板)**:从测试结果新起的缺陷 issue
(含 side_findings 立案的)修复 PR 合并后,由开发侧**切状态标签 + 交接处理人(交回派单方,
默认 issue 创建人;标签与处理人同一次操作),随即直接 close**——不走「PM验收中/人工测试中」
的完整验收线,是「关闭动作归验收线」的明确例外;close 是合并后的手动动作,PR 正文仍禁
自动关闭语法(std-git 铁律不变)。修没修好由**批次复测**把关:复测该用例仍 ❌ →
reopen 原缺陷 issue 并附新一轮证据。打回的**既有工作项** issue 不适用本条,
仍走自身状态机与验收线。

**关闭条件 = 批次收口(2026-08-08 首个落地项目 PM 拍板),三条件齐备才关验收记录 issue**:
① 批次全绿——逐用例**最新状态**全 ✅(复测轮修正后的正文为准);
② 挂在本验收 issue 下的全部子缺陷 issue 已关闭;
③ 处置清单全部执行闭环。
open 的验收 issue = 批次未收口,与 sub-issue 修复进度条互为印证;
禁按「处置清单执行完即关」的旧口径提前关单——清单执行完但复测未全绿/子缺陷未清零,保持 open。

## ⑦ 批次收口循环(测→修→复测;PM 一次授权,循环自动)

**⑥ 的处置清单即循环入口**:首轮发布后,处置清单随附**收口循环建议**——打回哪些、
立哪些缺陷单、建议的修复派发分组、复测范围(非绿用例)与预计轮次。PM **确认处置并
授权循环**(一次授权覆盖后续各轮)后自动推进;未授权则每轮停在 ⑥ 等确认,本节不生效。

**循环只吃 `code` 档**:`spec-divergence` 待拍板、`case-stale` 待用例 PR merge
(①-B 形态待 PM 修订 issue 期望)、`platform` 待上游——三者都不是「派个开发去修」能推进的,进循环只会空转。它们随轮次推送在决策清单里
等 PM,拍板/合并/上游修复落地后**才转成 `code` 档或直接复测**,重新入环。

**循环体(主 agent 全程仍是调度台:不改代码、不下 verdict)**:

1. **处置落地**:按 ⑥ 执行打回/立单(先分档,再按各档路由;查重、sub-issue、素材规则照旧);
2. **派发修复**:**只把 `code` 档的**打回单 + 缺陷单作为一批就绪工作项交
   [st-project-pm-dispatch](../st-project-pm-dispatch/SKILL.md) 派发开发子 agent
   (独立 worktree 并行,开发纪律归 dev-issue);
   **验收缺陷修复免报方案(2026-08-10 PM 拍板)**:不过 dev-design 放行闸门直接开工,
   但改动范围**限定为缺陷本身**;开发子 agent 发现要动共享资产/跨模块/改业务口径
   (dev-design 判错信号)→ 仅该单停下报审,其余单照走;
3. **收修复**:修复 PR 合并后,缺陷单按 ⑥ 关闭口径改标签+交接处理人后直接 close
   (经 pm-dispatch 派发的批次,调度员在自主合并同一步已执行关单——本步只**核对**
   已关,不重复动手),打回单流转回验收线;**修复与复测跨侧/跨会话时**,本步末尾按下方「复测就绪标记」
   在验收记录 issue 打 `<映射:待复测>` + 评论就绪清单;
4. **复测**:对本轮修复覆盖的非绿用例派发**新的**执行+盲审子 agent(隔离环境、新指纹,
   纪律同 ②③④),按「复测发布」修正原验收 issue(rounds、-rN 证据目录、历史轮归档);
5. **判环**:`code` 档清零(逐用例最新状态全 ✅)且其余档均已有去向 → 按关闭三条件收口,
   循环结束;仍有 `code` 档非绿 → 回 1;只剩非 `code` 档 → **停循环不停单**,出决策清单等 PM,
   验收 issue 保持 open(全绿口径不放宽:等拍板的用例在拍板落地并复测 ✅ 前不算绿)。
   复测轮的「轮次说明」里写明哪些用例是**等拍板/等用例 PR 故本轮不重测**,
   否则 PM 会把「没动」误读成「漏测」。

**停机规则(硬,防无限循环)**:

- 同一用例修复后复测仍 ❌ 累计 **2 轮** → 该用例停止自动派发,标「修不动」升级 PM
  (附逐轮证据对比与原因归类);**若两轮里已把它重归成非 `code` 档,不计入这 2 轮**——
  改错了档不该算修不动,重归档本身就是要报 PM 的结论;
- 自动循环最多 **3 轮**(首轮验收不计),到限未全绿 → 停机出**收口受阻报告**:
  剩余非绿清单 + 逐条原因归类(修不动/待拍板/平台受限),等 PM 裁决;
  **非 `code` 档的用例不消耗轮次**(它们本就不进循环);
- 需拍板事项(升级报审的方案、平台缺陷上报、⚠️/❓ 处置)攒进决策清单随轮次推送,
  不阻塞其他单;即时停机仍只有 P0 环境阻塞一种;
- 每轮结束推送透明摘要(轮次号 + 统计尾巴 + 剩余非绿清单),不要求 PM 回应。

### 复测就绪标记(2026-08-11 PM 拍板;跨侧交接的唯一信号)

验收与修复**分属两侧**(如验收由其他同事跑、修复在本侧)时,「什么时候可以开下一轮」
不能靠谁盯着谁——**修复侧在验收记录 issue 上打 `<映射:待复测>` 标记**,验收侧只认这个
标记排期,不逐单猜进度。

**打标记的条件(四条齐备才算「符合复测条件」,少一条都是骗验收侧白跑一轮)**:

1. 本轮非绿用例对应的修复单**在途清零**——要么修完 close,要么已标 `人工介入` /
   `已挂起`(等人的不算在途);
2. 修复代码**已合入 main**(验收侧自起环境会从 main 拉基线,挂在分支上的修复复测必翻车);
3. 至少有**一条**非绿用例真的被修过(全员等人 = 无可复测内容,不打标记,改为在 issue
   评论说明卡在哪);
4. 同一次操作在 issue 上**评论「复测就绪」清单**:本轮修了哪些用例编号 + 对应 PR/commit、
   哪些没修及原因(人工介入/挂起/待拍板)、建议复测范围。

**摘标记**:验收侧开测复测轮时摘掉,**同一次操作贴上过程标签 `验收:复测中`**
(2026-08-12 加入,见 ⑤「状态标签」第四枚)——摘而不贴,列表里「复测中」与
「修复中」签名相同,PM 分不出这批在测还是在修;标记留着不摘 = 下一轮又被当成就绪,
重复空跑。复测发布修正原 issue 时摘掉 `验收:复测中`(与换结论状态标签同一次操作);
复测后仍有非绿 → 回到修复侧,修复侧按上述条件重新打 `<映射:待复测>`。

**同侧自动循环(⑦ 循环体)可省**:一个会话内从修复走到复测没有交接对象,不强制打标记;
但只要修复与复测跨会话、跨人、跨机器,标记就是硬要求。

## 用例测试历史:一律派生,禁止回写

「某用例测过几轮、每轮 issue/时间/结果/平台版本」这类历史,一律从验收记录 issue **派生**
查询,**禁止回写进用例文件**——用例文件永远只写验收标准。回写 = 制造第二真值(漏一轮就
开始骗人),且污染「merge = PM 签字」语义(pm-case 起草规则本就把「执行后回填段」列为
必须剔除的劣质结构)。

反查(assets 提供 acceptance-history.cjs,复制到项目 scripts/):

```bash
node scripts/acceptance-history.cjs                    # 全量:每用例轮次+最近结果+非pass清单
node scripts/acceptance-history.cjs S01-003            # 单用例逐轮明细
node scripts/acceptance-history.cjs --cases docs/验收测试用例   # 追加「从未测过」清单
```

无脚本时手工等价:`gh search issues "<用例id>" --label 验收记录`(脚本非门槛,缺位不阻塞)。
数据源 = 各验收 issue 里 `<details>` 收起的 results.json:**正文 = 最新轮**;复测归档的
「历史轮」标记评论 = 旧轮(正文超长时最新轮在单独评论)。history 按轮合并出**逐轮序列**,
同一用例展示跨轮演进(如 `#101 第1轮 ❌ → 第2轮 ✅`);正文不带 `rounds` 的 issue 视为
单轮,不翻评论找历史轮。因此 ⑤ 的发布结构——**含「历史轮」评论格式与 `rounds` 信号**——
是历史反查的**解析契约**:改 `<details>`/围栏/历史轮标记格式,report 与 history 两脚本
必须同步改。

## 派发与并行(主 agent)

**委派是强制的,并行是可选的**:任何批次——哪怕只有一个场景——执行与盲审都交子 agent,
主 agent 不亲自测;并行只在多场景时开。规则:

- **切包单位:①-A 按场景文件,①-B 按业务域**(缺陷批次没有场景文件,按修复落点所属的域切,
  如「派工详情 / 维修派工 / 质检报检 / 门禁与点检」)。**两者都禁止用例级切包**——
  before/after 因果断言与链式前置在共享库并发写入下全部失效,用例级并行 = 伪造结果;
  包内用例严格串行。**同一 issue 的多条断言必须同包**(它们共享前置);
- 派发前主 agent 出**环境分配表**(每包:独立端口、独立库文件路径、H5 端口),随派发模板
  下发;执行子 agent 按表自起、各自灌数据底座、各自固化指纹——禁止两包共用端口或库
  (幽灵进程/共库污染出过大事故);
- **派发模板必须自包含**:验收标准(①-A 给用例文件路径;**①-B 把每个 issue 的现象/期望/
  复现步骤全文粘贴进模板**,不许只给编号或链接——子 agent 冷启动打不开你脑子里的上下文)、
  环境分配行、本 skill 对应段落的纪律(执行包=②③,盲审包=④)、返回物契约;
  **①-B 还要把开发侧的需求符合度清单一并喂给盲审**——盲审要拿它与实测三角对质;
- **执行/盲审子 agent 一律指定 Opus 模型**(Agent 调用带 `model: opus`),不用主会话模型;
- 盲审是只读工作,多包盲审可并行;执行并发 **2~3 为硬上限**(每套环境一个 dev server + 浏览器,
  机器资源是上限)——派发前按「执行并发上限」条款清点并清理本机遗留 dev server;超发的直接
  后果是耗时类观察全部失真,把环境慢立成产品缺陷单。

## 断点续测(主 agent 包状态表)

主 agent 维护包状态表:待派 / 执行中 / 待盲审 / 已收单 / 退回。子 agent 中断或收单核实
不过 → 该包重派新执行子 agent:先核指纹,指纹未变(同库同 commit)→ 复用已落盘观察从
断点续跑,已测案例不重测;**指纹变了 → 本包作废从头**(仅该包,不牵连其他包)。
已收单的包永不重跑。
