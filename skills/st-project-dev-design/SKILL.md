# st-project-dev-design — 方案分级

> 建设状态:可用(未实战) | 批次:第一批 | 主责 AI 岗位:AI 架构师/开发工程师 | 人类闸门:技术负责人放行高风险项

**设计核心:AI 犯的错里代价最大的一类是「自作主张动了老功能」。方案分级把授权粒度按
风险定——不是所有改动都要人审(那是把人变成瓶颈),也不是所有改动都免审(那是放任
事故),而是让「要不要人看一眼」本身成为一个有判定树、有留痕、判错会自动收紧的机制。**

两条不对称的成本决定了所有灰区的裁决方向:
高风险误判(其实低)的代价 = 多等一次确认;低风险误判(其实高)的代价 = 返工 +
可能弄坏老功能 + 信任受损。**所以拿不准一律按高风险,没有第三个选项。**

## 上下游边界(硬)

| 方向 | 对接 skill | 交接约定 |
|---|---|---|
| 上游 | [st-project-req-refine](../st-project-req-refine/SKILL.md) | **只接过 DoR 的工作项**。没过 DoR 的不分级——分级建立在需求已可判定的前提上,需求本身模糊时分级结论毫无意义,退回细化 |
| 下游 | [st-project-dev-issue](../st-project-dev-issue/SKILL.md) | 低风险留痕后、高风险放行后,进开发闭环;分级声明/已放行方案是 dev-issue 阶段 PR 描述的素材 |

本 skill 自身**不写代码**:产出到「分级结论 + 方案要点」为止,一行实现代码都不属于本工序。
上游细化阶段「工作项只描述业务不含技术实现」,技术实现方案正是从这道工序开始出现的。

## 流程总览

```
读工作项(已过 DoR)
  → ① 输出「需求理解 + 实现方式」(先于一切编码)
  → ② 三问判定树定级
      ├─ 低风险 → ③ 落分级声明 → 进 st-project-dev-issue
      └─ 高风险 → ④ 按模板挂方案要点 → 异步等人放行 → ⑤ 放行后进 st-project-dev-issue
  → ⑥ 判错兜底:低风险开工后暴露判错 → 首次失败即升级 + 判例回填
```

## ① 先产出「需求理解 + 实现方式」(禁止直接编码)

拿到工作项后的第一份产出,写在工作项评论或对话里:

- **需求理解**:业务语言一两句——谁、要干什么、为什么;
- **实现方式概述**:动哪些资产(对象/字段/页面/流程/权限/脚本),各是**新增还是修改**。

**字段/按钮的落点判定是本 skill 的职责(2026-08-12 PM 拍板)**:细化描述给出的是
字段与按钮的**业务定义**(业务名/类型/边界/来源/可见条件);它们各自**落在哪个对象、
复用已有字段还是新建、API 名、按钮用原生视图还是自定义页承载、逻辑走 hook 还是
自动化**——由本 skill 在实现方式概述里定,判定前先查 dev-inventory 派生清单核对
既有资产。复用/新建判错是「改已有」误判的高发源头:疑似可复用的字段先查它的
被引用面,拿不准按高风险。

这份产出是分级的判定素材:**写不出「动哪些资产、各是增还是改」,说明影响面还没摸清,
不许分级,更不许开工**。摸影响面时只做只读侦察(读代码、查引用、看元数据;项目有
st-project-dev-inventory 派生清单的**先生成/查清单再翻代码**——共享资产、按钮/hook
被引用面一眼可查),不动手改。

## ② 风险分级判定树

对实现方式概述里的改动,顺序问三问,**任一为「是」或「拿不准」→ 高风险;三问全
「否」→ 低风险**:

1. **改已有?** 是否修改任何已有资产的结构、行为或语义?——对象结构、字段语义、
   Hook/自动化逻辑、流程节点、权限声明、页面交互、共享脚本;**删除也是修改**。
   判定口径是「已有读写路径是否会感知到差异」,不是「是否碰了旧文件」。
2. **跨模块?** 影响面是否超出本工作项所属的单个业务模块?——新资产挂接到别的模块的
   流程/对象/页面上、共享资产(翻译包、公共 Hook、公共组件)被触碰,都算跨。
3. **多路径?** 是否存在 ≥2 条都说得通的实现路径(平台原生能力 vs 自建代码、两种数据
   建模、两种交互形态)?——选型是人的决策,AI 给利弊不拍板。

### 判例表(通用示例;项目实战中判错的案例按 ⑥ 持续回填)

| # | 情形 | 判级 | 判定理由 |
|---|---|---|---|
| 1 | 新建独立对象 + 配套列表/表单页,不被任何已有流程、页面引用 | **低** | 三问全否:纯新增、单模块、做法唯一 |
| 2 | 改一处报错文案的错别字,无逻辑变化,文案键不被其他位置复用 | **低** | 修改了旧文件但已有行为零感知;⚠️ 若文案键在共享翻译包里被多处复用,改一处动全身 → 高 |
| 3 | 给已有对象加新字段,只被本次新功能读写(**灰区**) | **通常高** | 字段是新增,宿主对象是已有资产。可判低的条件严苛且须逐项列证:不进任何已有视图/表单/导入模板、无默认值回填存量、不被任何已有 Hook/自动化触碰、权限沿用对象现有声明。**任何一条不成立或查不清 → 高** |
| 4 | 改一个共享 Hook(多个写入路径都会触发它)(**灰区常见误判**) | **高** | 第 1、2 问双命中:表单编辑、批量导入、接口写入、自动化——所有触发该 Hook 的入口都在影响面里,包括你没看见的 |
| 5 | 在已有状态机上新增一个状态或变迁 | **高** | 已有变迁合法性、按钮显隐条件、按状态过滤的列表和统计口径全部要重推 |
| 6 | 给已有对象新增一条校验规则 | **高** | 名为「新增」实为拦截存量:所有已有编辑路径从此被这条规则把关,存量不合规数据当场被拦——**新增的资产会不会拦别人的路,是比「增/改」更真的判据** |
| 7 | 新建通知/提醒,触发点挂在已有流程节点上 | **高** | 资产是新的,触点在别人的流程里(第 2 问):节点语义、触发时序要与原流程对齐 |
| 8 | 需求既可用平台原生能力配置实现,也可自建代码实现 | **高** | 第 3 问命中:两条路的维护成本、平台升级路径不同,选型是人的决策 |
| 9 | 重构/性能优化,声称「不改外部行为」 | **高** | 「不改行为」是待证明的主张,不是免检理由;改的全是已有代码,第 1 问命中 |
| 10 | 纯新增一个定时任务,读已有数据、只写自己的新表(**灰区**) | **通常高** | 写路径纯新增,但「读已有数据」的口径(过滤条件、权限上下文、时区)是否与既有业务一致需要确认;读口径能逐项确认一致才可判低 |

### 禁用的判级理由

- **「改动只有几行」**——分级看影响面不看代码行数,一行改共享 Hook 顶得上一百行纯新增;
- **「顺手把发现的老问题也修了」**——顺手修老问题本身就是高风险信号,且属范围蔓延:
  记录下来单独立项,本工作项不带;边界与搭车细则见 dev-issue「开发中发现新问题」
  (同因同域/阻塞交付的并入不算顺手修;独立小单立单后可同 worktree 搭车执行;
  动共享资产/跨模块/改口径的仍归本条,立单报审);
- **「工期紧,先干了再说」**——紧急程度不改变风险等级,只影响人确认这件事的优先级;
- **「上次类似的判了低」**——判例辅助判断,三问必须逐条重答。

**验收缺陷修复例外(2026-08-10 PM 拍板)**:pm-test 批次收口循环派发的缺陷修复
**免走本 skill 报方案闸门**直接开工,改动范围限定为缺陷本身;修复中发现要动共享资产/
跨模块/改业务口径(即上述高风险信号)→ 仅该单停下补审。权威条款见
[st-project-pm-test](../st-project-pm-test/SKILL.md) ⑦ 批次收口循环。

## ③ 低风险:免审开工,但必须留痕

在工作项上落一条**分级声明**(评论区),然后直接进 st-project-dev-issue:

```
## 方案分级:低风险(免审开工)
- 需求理解:<一句>
- 实现方式:<动哪些资产,全部为新增>
- 三问:改已有=否(<一句依据>);跨模块=否(<一句依据>);多路径=否(<一句依据>)
```

留痕不是形式:判错时它是回溯「当时凭什么判低」的依据,也是 ⑥ 回填判例的素材。
**没有分级声明的「低风险开工」= 跳过了本工序,不算免审,算违规。**

## ④ 高风险:挂方案要点,异步等人放行

1. 按 [proposal-template.md](proposal-template.md) 写方案要点,**挂到工作项评论区**——
   不另开文档、不只写在对话里:评论与工作项同生命周期,人在看板上一眼能看到,
   放行记录也留在同一处;
2. 把工作项状态切到「方案确认中」一类的等确认状态(状态标签的实际名从项目配置读取,
   本 skill 只约定语义);把这件事一句话回报给调度方/人(有 pm-dispatch 在跑就进
   调度回报,没有就在对话里报);
3. 多方案时 AI 给出推荐及理由,**但不拍板**;人选了非推荐项时把人的理由记回评论
   (将来 retro 用)。

### 等待期间的纪律(硬)

- **不许「先干起来等确认」**——一行实现代码都不写(只读侦察不受限)。方案没放行就
  开工,等于把人的闸门变成走过场;
- **不空等**:转投其他就绪工作项,等确认的项挂着不影响吞吐;
- **没回音不催成轰炸、更不视为默认同意**:挂出方案时回报一次;此后在例行回报里
  持续列出「等确认清单」(工作项、挂出时间、等了多久),催办节奏与升级由人/调度方
  决定。**无论等多久,沉默都不是放行**;
- **放行的形式必须是人的明确表态**:工作项评论区的明确同意,或项目约定的等价信号
  (如状态标签被人切走)。**AI 不得自己切「已确认」状态,不得把「没人反对」解释成
  同意**;
- 人带条件放行 / 部分确认 → 按批注把方案评论更新成终版再开工;
- 人打回方案 → 修订后重新挂、重新等,不许按打回前的版本开工。

## ⑤ 放行后:进 st-project-dev-issue

- 实现必须与放行的方案一致;
- **实现中发现方案行不通或要变更**(影响范围比报的大、路径要换)→ 停手,回到本
  skill 挂修订方案重新等放行。**静默改道 = 拿着旧授权干新事,与未审开工同罪**;
- 已放行方案里「兼容与回归」一节列出的既有场景,是 dev-issue 自测阶段的必测项。

## ⑥ 判错兜底:首次失败即升级 + 判例回填

低风险开工后,出现以下**任一**信号,即认定分级判错:

- 实现中发现「不改已有资产就做不完」;
- 自测/回归发现任何老功能行为变化;
- PR 评审、验收或人工反馈指出动了不该动的东西。

处置(两步,顺序固定):

1. **立即停手升级**:第一次暴露就升级,不设「失败 N 次才升级」阈值,更不许硬着头皮
   做完再说。已写的代码停在分支上,按 ④ 补挂方案要点(如实写明「原判低风险,因 X
   信号升级」),等人放行后才继续;
2. **判例回填(经验闭环)**:走 [st-project-meta-retro](../st-project-meta-retro/SKILL.md)
   四问,把该判例——情形、当时判低的理由、暴露方式、正确判级——追加进本 skill
   ②的判例表(skill 库修订走库自身的 PR 流程;项目特有、不可泛化的判例进项目自己的
   记忆)。**判错不回填 = 同一个坑留给下一个工作项。**

## 防 AI 犯错(硬纪律)

1. **影响范围必须逐点列名**——具体到对象/页面/流程/权限点的名字,禁「影响不大」
   「基本无影响」「只影响局部」这类不可核对的表述;写不出名字 = 没查清 = 不许分级;
2. **分级结论出来之前禁止编码**;高风险放行之前禁止编码;
3. **拿不准 = 高风险**,判定树三问任何一问答不出「否」的依据就是拿不准;
4. **AI 不拍板选型、不自行切确认状态、不把沉默当同意**;
5. **每个工作项都要有分级留痕**——低风险留分级声明,高风险留方案要点与放行记录,
   零留痕等于没走本工序;
6. 项目具体信息(状态标签实际名、确认人是谁、工作项载体)从项目仓库配置/CLAUDE.md
   读取,本 skill 只写约定不写死。
