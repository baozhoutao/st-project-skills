# st-project-dev-regression — 夜间回归巡检

> 建设状态:可用(未实战)| 批次:第一批 | 主责 AI 岗位:AI 回归守护(无人值守)| 人类闸门:无(失败自动立单进正常流转)

**会话命名(2026-08-12 约定)**:巡检会话标题设为 **`回归 | <MMDD>`**——定时触发的
无人会话同样适用,失败排查第一步就是找回当晚现场。工具机制与无工具豁免见
pm-test「会话命名」权威条款。

## 目标

「新功能悄悄弄坏老功能」这类缺陷的存活时间不超过 24 小时。体系 = **活清单 + runner + 排程**
三件套:清单随验收通过的工作项增长,runner 每晚照单跑断言,失败自动立回归缺陷单进正常流转。

**无人值守的第一纪律:不刷屏。** 全绿不发声(日志落盘即可);失败去重后才上 issue;
环境问题不立功能缺陷单。

## 约定目录(项目内,首次使用现建)

```
scripts/regression/
  manifest.json        # 活清单(唯一真值,变更走 PR)
  runner.cjs           # runner(按本 skill 第二、三节契约实现)
  <场景id>.cjs         # 仅「薄包装」脚本放这里;能直接引用验收场景脚本的不复制
logs/regression/       # 巡检日志(gitignore,不入库)
```

runner 本身不作为附件分发:按下述契约在项目内实现(百行量级);首个项目实战跑通后,
其通用版回填进本 skill 的 assets/。

## 一、清单 schema(manifest.json)

顶层结构:

```json
{ "version": 1,
  "defaults": { "timeout_ms": 300000 },
  "scenarios": [] }
```

`scenarios[]` 逐场景字段:

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | ✓ | string | 唯一短 id(小写字母/数字/连字符)。**分配后永不复用、永不改名**——缺陷单去重、日志、历史全挂在它上 |
| `name` | ✓ | string | 场景中文名,业务语言(谁、做什么、该看到什么),会出现在缺陷单标题里 |
| `script` | ✓ | string | 断言脚本路径(仓库根相对路径) |
| `enabled` | ✓ | boolean | `false` = 暂停巡检,**必须**同时带 `disabled_reason` |
| `source` | 建议 | string | 来源工作项编号(如 `#123`)——断言依据的追溯锚点,分诊「基线陈旧」时第一个查它 |
| `added` | 建议 | string | 入册日期 `YYYY-MM-DD` |
| `timeout_ms` | 可选 | number | 覆盖 `defaults.timeout_ms` 的单场景超时 |
| `tags` | 可选 | string[] | 业务模块标签,供选跑过滤 |
| `disabled_reason` | enabled:false 时必填 | string | 停用原因 + 恢复条件(引用相关工作项编号) |

硬规则:

- **清单只增不删**:场景失效用 `enabled:false` + `disabled_reason` 下线,不许整条删除——
  删除会抹掉「这里曾经有覆盖」的事实,清单悄悄变薄没人知道;
- 未知字段 runner 忽略不报错(允许项目自扩展),但**必填字段缺失 = 清单解析失败**,
  runner 以退出码 3 中止——坏清单比不跑更危险;
- 示例见 [assets/manifest-example.json](assets/manifest-example.json)(场景名为通用业务示意,
  三条分别演示:直接引用验收脚本 / 薄包装 / 带理由停用;新项目从空 `scenarios[]` 起步)。

## 二、runner 契约

### 场景脚本契约(入册资格)

- **退出码表达结果**:0 = 通过,非 0 = 失败;断言细节打到 stdout/stderr(runner 会截取进缺陷单);
- **环境地址只从环境变量读**(约定名 `OS_BASE`),脚本内不写死任何地址/端口;
- **幂等**:重复跑不依赖上一次的残留;造的数据用可识别测试前缀并自行清理——
  巡检夜夜跑,不幂等的脚本一周内必被自己的残留搞红;
- 单场景可独立执行(`OS_BASE=<地址> node <script>`)——这同时是缺陷单里的复现指令。

### runner 行为

- **逐场景串行**,禁并行——断言脚本可能造数/清数,共享环境并发写入互相污染,
  并行跑出的失败无法归因;
- **单场景超时处置**:超过 `timeout_ms` 即杀掉该脚本进程树,该场景记 `timeout`(按失败处理),
  **继续跑下一个场景**——一个场景挂死不许拖垮整晚巡检;
- **逐场景日志落盘**(结果只认落盘文件,不信内存里的「全绿」):

  ```
  logs/regression/<YYYYMMDD-HHmm>/
    summary.json     # 本轮真值:环境指纹 + 逐场景 verdict/退出码/耗时/关联缺陷单号
    <场景id>.log     # 该场景脚本的完整 stdout/stderr
  ```

- **开跑前环境闸门 + 轻量指纹**:先探活(服务可达、探针账号可登录);探活不过 =
  整场中止(退出码 2),只记日志**不立任何功能缺陷单**——环境不可达时逐场景全红全是假缺陷。
  探活过了,把环境指纹写进 summary.json:环境地址、serving 代码 commit、平台版本、开跑时间
  ——没有指纹,缺陷单的「环境」要素无从谈起,分诊「基线陈旧」也无从对照;
- **连续 2 次环境闸门中止 → 立一条环境类工作项**(同样走去重)——环境常态性不可用本身是
  缺陷,不能让巡检静默停摆;
- runner 退出码:`0` 全部启用场景通过;`1` 有场景失败(已按规则立单/追评);
  `2` 环境闸门未过,整场中止;`3` 清单解析失败或 runner 自身错误;
- 必备开关:`--dry-run`(只跑只落盘,不碰 GitHub——调清单/调脚本时用)、
  `--only <id>`(单场景重跑——分诊复核与修复验证时用)。

## 三、失败 → 回归缺陷单(自动,带去重)

### 去重规则(防刷屏的核心)

- 缺陷单标题约定:`回归 | <场景id> | <场景名>`;正文头部埋机读标记
  `<!-- regression-scenario:<场景id> -->`;
- 立单前先按标记/场景 id 查**同场景的 open 回归缺陷单**:
  - 已有 open 单 → **不新立**,在原单追加一条简评:日期、退出码、当轮日志摘录一行、
    「连续第 N 轮失败」;
  - 无 open 单(含历史已关)→ 新立一单。同场景旧单已关又再失败 = 新问题或复发,新立不追旧;
- 场景**转绿**且存在 open 单 → runner 在该单追评「<日期> 本轮已通过」;
  **关单动作留给处理人**在分诊/修复闭环里做,runner 不自动关单(转绿可能只是环境波动)。

### 缺陷单正文要素(五项,缺一不许立)

1. **场景**:id、name、script 路径、清单 `source`(断言依据的来源工作项);
2. **断言与现象**:失败的断言内容 + 期望 vs 实际(从脚本输出提取),退出码;
3. **日志摘录**:错误段或末 N 行贴正文;写明完整日志的落盘路径(批次目录);
4. **环境**:summary.json 里的指纹原样带过来(地址、serving commit、平台版本、时间);
5. **复现指令**:单场景重跑命令(`OS_BASE=<地址> node <script>` 或 runner `--only <id>`)。

标签:打项目约定的**回归缺陷类型标签** + 流转起点状态标签(具体名称按项目标签体系,
首次使用先建标签);正文末尾注明「第一处理动作 = 假缺陷分诊(见本 skill 第四节)」。

## 四、假缺陷分诊(缺陷单的第一处理动作)

**脚本红 ≠ 功能坏。** 每张回归缺陷单的第一处理动作是分诊,三选一;判序固定:
**先环境 → 再基线 → 才是真缺陷**(同轮多场景齐红先怀疑环境,不许逐单定罪)。

| 类 | 判据(典型信号) | 处置 | 缺陷单收口 |
|---|---|---|---|
| **环境问题** | 多场景同轮齐红;连接/登录/超时类错误;探针波动 | 修环境(重启、重灌数据底座),修完 `--only <id>` 重跑验证;不算功能缺陷 | 关单,备注「环境问题 + 修复动作」;反复出现 → 环境类工作项跟进 |
| **脚本基线陈旧** | 能找到**有意改变该行为**的已合并工作项/PR,且新行为符合其验收标准;或纯脚本问题(选择器/数据前缀过时) | 修正脚本断言至新基线,**走登记**(见下);修完 `--only <id>` 重跑转绿 | 关单,备注引用基线修正 PR |
| **功能真坏了** | 排除前两类;且**真机 UI 手工复现失败**——定罪前必须真机复现一遍,禁止只凭脚本输出定罪 | 按回归缺陷正常流转修复(优先级见第六节) | 修复 PR 合并 + 巡检转绿后关(见第六节闭环定义) |

**基线修正也要走登记(禁悄悄改绿)**:修正断言的 PR 描述必写三要素——
①旧断言(原来断什么)②新断言(现在断什么)③依据(哪个工作项/PR 有意改变了行为,引用编号)。
改绿无据 = 巡检体系开始说谎;缺陷单引用该 PR 后才许关单。若项目维护差异登记册,
基线变更同步登记一条。

## 五、「Done 即入清单」——活清单纪律(体系最常见的死法在这)

> **工作项验收通过、流转「已完成」的同一步,把它的核心业务场景断言追加进清单。**
> 不追加,清单会随项目推进逐渐失去覆盖有效性——巡检还在夜夜全绿,守的却是越来越小的地盘。

- **时机 = 同一步**:与状态流转在同一个收尾动作序列里完成,不是「回头补」——回头补的
  下场是永远没回头;
- **谁负责**:该工作项的**开发闭环收尾动作**(st-project-dev-issue 的处理 AI)——验收通过后
  由它提交入清单变更;PM 侧把「场景已入清单(或已登记豁免)」当作允许切「已完成」的检查项;
- **脚本从哪来(不从零写)**:
  1. **优先直接引用验收场景层脚本**——st-project-pm-test 约定场景脚本保留断言入口
     (退出码 0/非 0、honor `OS_BASE`),清单 `script` 直接指向它:单一真值,用例修订时
     脚本同步演进,回归自动跟上;
  2. 回归断言需要与验收行为不同(裁剪成更快/只读的断言、独立数据前缀)时,才在
     `scripts/regression/` 落**薄包装**,内部仍复用既有框架层能力,不复制粘贴场景逻辑;
  3. 无验收脚本的(小项自测通过即完成),把自测跑绿的脚本按「场景脚本契约」补齐后入册;
- **豁免要显式**:确无回归断言价值的工作项(纯文案、纯样式类)可不入册,但必须在
  工作项上留一句「不入巡检清单,理由:…」——禁止静默跳过,豁免留痕才能事后审计覆盖缺口;
- **载体**:小 PR(清单变更 + 新脚本/薄包装),或搭车该工作项的收尾 PR;清单在 main 上,
  禁直接改。

## 六、回归缺陷的流转:优先级高于普通新工作项

- **接单顺序**:派发/接单时回归缺陷置顶——开发 AI 先清回归缺陷,再接新功能;
  批量调度(st-project-pm-dispatch)拉就绪队列时同样置顶。理由:回归缺陷破坏的是
  **已交付并验收过的承诺**,每多活一天,信任与排错成本都在涨;「存活 ≤ 24 小时」全靠这条;
- **修复的闭环定义**:修复 PR 合并后,该场景巡检**重新跑绿**(`--only <id>` 即时验证 +
  次晚整轮确认)才算闭环,然后关单;只合 PR 不看巡检转绿 = 没闭环;
- 除优先级外,回归缺陷按项目正常工作项状态机流转,不走特殊通道。

## 七、排程(本地 cron / CI,按环境可达性二选一)

选型判据:巡检环境只在本机可达 → 本地排程;有常驻可达的托管测试环境 → CI 排程。
**同一环境不双跑**(两边都跑会重复追评/立单)。

**本地(cron/launchd)通用形态:**

```cron
# crontab -e —— 每晚固定时段,避开数据底座重灌/备份任务
30 2 * * * cd <项目仓库绝对路径> && OS_BASE=<巡检实例地址> node scripts/regression/runner.cjs >> logs/regression/cron.log 2>&1
```

要点:cron 无登录 shell 环境——仓库与 node 都用绝对路径;日志**追加**不覆盖;
到点环境必须可用:推荐常驻**独立巡检实例**(独立端口 + 独立数据库,与白天开发实例分离
——脚本会写库,共用实例夜夜污染开发数据);立单用的 GitHub CLI 凭据对 cron 环境可用。

**CI(GitHub Actions)通用形态:**

- nightly workflow,`on: schedule`(cron 表达式是 **UTC**,记得换算时区);
- 巡检环境地址放仓库 Variables;**未配置则第一步检测并整场 skip**(不误报,新项目
  clone 下来不会夜夜红);
- job 权限含 `issues: write`(runner 立单用);
- 失败立单/去重逻辑全在 runner 内,workflow 只管调度 + 日志归档(当轮
  `logs/regression/` 目录上传 artifact)。

**巡检环境维护**:巡检库数据随夜积累——第一道靠场景脚本幂等 + 测试前缀自清理;
第二道定期重灌数据底座(避开巡检时段)。重灌后首轮失败按「环境问题」分诊,不算回归。

## 防错要点(浓缩)

- 巡检结果**只认落盘日志**,不信内存里的「全绿」;
- 全绿不发声,失败去重后才上 issue,环境问题不立功能缺陷单——无人值守 = 不许刷屏;
- 脚本红 ≠ 功能坏:定罪前必真机复现;基线修正必走登记,禁悄悄改绿;
- 清单只增不删,下线用 `enabled:false` + 理由;「Done 即入清单」是同一步动作,不是回头补;
- 项目具体信息(仓库名、标签名、环境地址、实例端口)从项目仓库配置/`git remote` 读取,
  本 skill 只写约定。
