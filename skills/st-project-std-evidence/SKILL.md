# st-project-std-evidence — 证据规范

> 建设状态:可用(未实战;条款源自已验证的 st-project-pm-test 实战纪律,上升为全阶段通用规范)| 批次:第一批 | 性质:规范(全 AI 岗位遵守)

## 定位:全阶段一把尺子

「做完了」不由做的人说了算,由证据说了算。本规范定义**全生命周期通用**的证据合格线——
开发自测、PM 验收、回归巡检、实施走查、验收材料,共用同一把尺子;流程 skill 引用本规范,
不各自复读条款(分工与冲突裁决见文末)。

## 证据三性(硬标准,缺一即证据无效)

| 性质 | 定义 | 反例(都不算证据) |
|---|---|---|
| **真实** | 功能证据 = 真实环境里的 UI 操作截图,操作者亲手走到那个界面、看到那个结果 | 代码 diff「已实现」;单元测试输出;API 直调返回值;构建产物里有相关代码 |
| **可复核** | 第三方**不看开发过程**,凭「环境(版本/commit)+ 账号(角色)+ 操作路径 + 截图」能独立重现同一现象 | 「在我机器上是好的」;复现步骤要回看原始对话才拼得齐 |
| **完整** | 成功与失败分支全覆盖:需求写了几种校验失败,证据里就有几种失败的现场 | 只测冒烟主流程;「同类失败测一种代表」 |

配套两条:

- **API/DB 查询只能当第二观察点**:关键写操作在 UI 断言之外补一条落库佐证是好习惯
  (界面提示成功 ≠ 数据落库),但**佐证不是替代**——没有 UI 截图,佐证单独不成立。
- **证据只认落盘文件**:结论只能指向已写入磁盘的截图与记录文件;执行器/监控台的过程
  事件流出过「假全绿」,不作证据。

## 截图硬标准(每张截图的合格线)

1. **截图必须支撑旁白**:说「出现了成功提示」就要拍到提示本身。一张撑不住旁白的截图
   = 没有证据(不 = 反面证据)。
2. **落盘后立即回看**:每张截图写盘后当场打开确认三点——①截到的是目标页面/区域
   ②内容支撑要写的结论 ③非半加载/空白态。不符当场重截,禁「拍了就算」;回看到的内容
   写成该图的图注(写图里实际可见的东西,不写预期——图注与图不符,复核者一眼拆穿)。
3. **瞬时提示等待抓拍**:toast 类瞬时反馈用显式等待抓拍;没截到就复跑重抓,
   禁凭「应该弹了」记成功、也禁凭「没截到」记失败。
4. **截图前复位取景**:别让上一步的残留状态(旧弹窗、上个用例的数据、悬浮菜单)混进画面。
5. **权限类证据必用目标角色账号**:管理员什么都看得见,管理员账号的截图对权限验证无效;
   无权反例要真实登录无权账号,截到「看不到/被拒」的现场。
6. **写操作 before/after 成对**:先截前置状态(列表计数、记录不存在),操作后截结果态。
   没有 before 证明不了因果——环境里既有数据碰巧满足预期会骗过你。
7. **视口纪律**:PC 端证据用桌面宽视口,移动端证据用固定手机视口;窄视口触发的响应式
   布局变体不是缺陷,也不许混进 PC 证据。
8. **命名与批次目录**:每轮/每批次一个独立目录(建议 `<YYYYMMDD>-<批次slug>/`),
   图名带定位信息(建议 `<用例编号>-<步骤号>-<观察物>.png`)——图名自己会说
   「这是哪一步、拍的什么」。
9. **禁覆盖已发布历史证据**:已被报告/issue 引用的证据目录永不重写;复用旧脚本重跑前
   先确认输出目录是新目录(重跑旧脚本覆盖已发布证据,是实战踩过的事故)。
10. **瞬时/闪变类缺陷禁单张定因**:位置跳变、闪烁、重复弹出这类现象,单张截图定不了因,
    用逐帧采样取证(连拍/录制逐帧回看),别拿一张模糊瞬间下结论。

## GitHub 图链规范(截图贴上工作项/报告时;实战多次翻车,逐条硬性)

**唯一合法形式**:

```
https://github.com/<owner>/<repo>/blob/<40位commit SHA>/<路径>?raw=true
```

四条禁令与一条核对,一条都不能省:

- **禁 raw.githubusercontent.com 域名**:私有仓 issue 里恒裂图;一律用上面的
  blob…?raw=true 形式(带登录态可访问)。
- **ref 禁用分支名,只用 40 位 commit SHA**:issue/报告是长期存档,分支合并后会被删除,
  分支名图链当场看着是好的、日后全变死链。
- **中文路径段先 URL 编码**(逐段 encodeURIComponent)再拼链接。
- **先 push 后取 SHA**:截图 commit + push 之后再取该提交的完整 SHA 拼链接,
  禁拿本地未推送的 commit 拼。
- **贴前用 contents API 核对文件确实存在**:
  `gh api "repos/<owner>/<repo>/contents/<目录>?ref=<SHA>"`;
  **禁用 curl 直打图链作判据**——私有仓下 curl 探测恒 404,是假阴性:404 不代表链接坏,
  一律以 contents API 结果为准。

## 证据存放:两种模式,按场景选

| 模式 | 做法 | 适用 | 铁律 |
|---|---|---|---|
| **孤儿分支**(多轮证据首选) | 建专用孤儿分支(如 pm-test 约定的 `acceptance-evidence`),只放证据,按批次目录追加 | 验收/测试这类**多轮、量大、与代码无关**的证据存档 | 只追加、**永不合主干、永不删除**;初始 README 写明规则 |
| **随工作分支** | 证据与代码同分支 commit,图链仍用 commit SHA | 单次、量小、且该 commit **确定会进入主干历史**时 | 合并策略必须保留原 commit(squash 会让证据 commit 脱离历史、图链悬空);拿不准合并策略就走孤儿分支 |

共同铁律:**已被引用的证据 commit 永不删除**——issue/报告是长期存档,删证据 = 拆掉历史
报告的证据链。证据是记录,发布面在 issue/证据分支;报告类文件不进主干、不提 PR。

## 报告可复核性

- **首页 = 结论 + 关键截图**:看报告的人 30 秒定去留,不用翻到第二页。
- **结论只有两态**:`✅ 通过`(当且仅当全部通过)或 `❌ 存在问题`(附问题清单)。
  禁「基本通过」「应该没问题」「大体正常」这类含糊表述——含糊结论 = 把判断责任推回给读者。
- **数字可追溯到台账**:报告里每个统计数字(x 通过 / y 失败)必须能对回逐条台账,
  台账逐条「预期 vs 实际」成对、每条指向具体截图;总数对不上台账行数 = 报告作废重出。
- **复现步骤独立可执行**:失败项的复现步骤含登录账号、入口路径、具体输入——不看开发
  过程、不看原始对话的人照着也能复现。

## 与流程 skill 的关系(分工与冲突裁决)

- dev-test / pm-test 等流程 skill **引用本规范,不复读条款**;本规范也不吸收工序细节。
- 分工:**通用尺子归本规范**(证据三性、截图合格线、图链、存放模式、报告可复核性);
  **工序特有纪律归流程 skill**(如 pm-test 的五态结论/盲审分离/基线指纹,dev-test 的
  计划推导/回修重测)。
- 冲突裁决:通用条款以**本规范为准**;流程 skill 只许在本规范之上**加严**(如对某类证据
  追加记录字段),不许放宽。发现两边真冲突(非加严)= 规范失配,登记后改其中一处,
  禁止在执行现场自行取舍。

## 防错速查

- 代码/单测/API 直调不算功能证据;真实环境 UI 截图才算;佐证不是替代
- 每张截图:落盘回看、支撑旁白、复位取景、目标角色账号、写操作 before/after 成对
- 图链:github.com/blob + 40 位 SHA + `?raw=true`;禁 raw 域名、禁分支名;中文段先编码;
  贴前 contents API 核对,curl 404 是假阴性
- 已发布证据永不覆盖、永不删除;孤儿分支永不合主干
- 结论两态;数字对得上台账;复现步骤独立可执行
