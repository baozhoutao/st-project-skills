# st-project-pm-dispatch — 批量调度

> 建设状态:可用(未实战) | 批次:第一批(与 dev 四件套配套) | 主责 AI 岗位:AI 调度员 | 人类闸门:决策清单异步批复

## 目标

吞吐随并行度线性涨,人不用跟着涨。调度员只管「派活—收活—看板」,不亲自写代码;
人只在两端出现:批前(backlog 里的工作项已过 DoR)与批后(批复决策清单、评审 PR)。

## 执行模型:主 agent 是调度台,开发动作全部下沉子 agent

**调度员全程不写代码、不改业务文件、不下功能结论。** 它只做:拉单分组、环境分配、
派发、监控看板、收单核实、处置与决策清单。开发动作全部由子 agent 在隔离 worktree 里完成。

| 角色 | 数量 | 职责 | 硬约束 |
|---|---|---|---|
| 调度员(主 agent) | 1 | 拉单/依赖分组/环境分配/派发/看板同步/收单核实/派评审/合并 PR/处置/决策清单 | 禁写代码;禁改业务文件;禁替子 agent 补作业;禁替人拍板;禁亲自评审代码;合并仅限本批收单核实通过**且评审闸门清零**的 PR(见 ⑤ 末) |
| 开发子 agent | 每工作项 1 个 | 在独立 worktree 按 st-project-dev-issue 走完开发闭环,交结构化报告 | 禁出自己 worktree 操作;禁碰其他并行项的模块;失败一次即停手上报;**一律指定 Opus 模型** |
| 评审子 agent | 每 PR 1 个 | 按 st-project-dev-review 对收单核实通过的 PR 出评审报告(两态结论) | 只读禁写代码;冷启动禁带开发上下文;**一律指定 Opus 模型** |

**委派是强制的,批量是可选的(2026-08-08 拍板)**:工作项开发一律在独立开发子 agent
中执行——哪怕只有一个工作项,也按「1 项的批」走完整调度流(环境分配→模板派发→收单
核实),主会话不亲自开发。**开发子 agent 一律指定 Opus 模型**(Agent 调用带
`model: opus`),不用主会话模型——与 st-project-pm-test 的执行/盲审子 agent 同一口径。

为什么强制下沉(不是可选优化):调度与开发混在一个上下文里,长批次必然塌方——
执行细节(编译报错、选择器调试、环境修复)会挤掉调度账本;子 agent 卡住时调度员
「顺手帮着改两行」= 角色混线,批次状态表当场失真。子 agent 卡住只有两个出口:
退回重派,或升级决策清单。

## 会话命名(2026-08-10 约定)

进入本 skill 第一动作把会话标题设为 **`派发 | <批次内容一句> | <MMDD>`**
(如 `派发 | 缺陷修复×5 | 0810`);同日第 N 批追加 ` 批<N>`。
工具机制与无工具豁免见 pm-test「会话命名」权威条款。

## 流水线

```
① 拉单+依赖分组 → ② 环境分配+派发(批内并行) → ③ 监控+看板同步
→ ④ 收单核实(逐项命令核对)+ 评审闸门(独立子 agent) → ⑤ 处置(合并/退回/升级) → ⑥ 决策清单报批 → 派下一批
```

## ① 拉单与依赖分组

**拉单**:取所有处于逻辑状态「待开发」且过 DoR 的工作项(项目侧实际标签名/看板列名
从项目仓库配置或实际标签表读取,本 skill 不写死)。DoR 不齐的不入队,退回
st-project-req-refine,不许调度员现场脑补要素。

**打回单与验收派生缺陷单优先入池(2026-08-10 PM 拍板)**:拉单范围除「待开发」外还含
①逻辑状态「已打回」且处理人在开发侧的返修单 ②验收派生的 open 缺陷单——两类**优先于
新开发单**派发(返修拖着,验收批次收不了口);带 `人工介入` 或 `已挂起` 标记的除外,
那是等人的,不派。返修纪律归 dev-issue 支线 A(AI 第一轮接手,处理不了标 `人工介入`)。

**批收口即打复测就绪标记(2026-08-11 PM 拍板)**:一批修复收单核实通过后,调度员在
对应的**验收记录 issue** 上打 `<映射:待复测>` + 评论就绪清单(修了哪些用例/PR、哪些
没修及原因)——跨侧场景里这是验收侧唯一的开测信号,漏打 = 修完了没人知道,批次干等。
四条打标记条件与摘标记规则的权威条款见
[st-project-pm-test](../st-project-pm-test/SKILL.md)「复测就绪标记」,本处不复读。

**值守模式(无人盯单)**:验收由他人执行、打回随时可能出现的项目,用定时任务
(Claude Code scheduled task / cron)按固定间隔(如每 1~2 小时)发起一次本 skill 会话:
拉单为空即安静退出,不产噪音;拉到单按上述优先级派发。人只在 `人工介入` 标记出现时
才需要看。

**依赖判定(读工作项的依赖标注)**:

- 显式依赖:正文/评论里的「依赖 #N」「前置:#N」「blocked by #N」等标注,以及需求
  文档里写明的先后关系;
- 隐式依赖(保守规则):**两项改同一个对象/模块/流程,即视为有依赖**,禁同批并行——
  同处并行改动合并时必然冲突,返工比排队贵;
- 拿不准是否依赖 → 按有依赖处理,宁慢勿乱。

**分组**:无依赖的进并行池;有依赖的按拓扑排队,**前置项的 PR 合入 main 后**,后继项
才有资格入池(后继要基于含前置代码的基线开发)。前置项收单核实通过后由调度员**直接
合并**(见 ⑤ 末「调度员自主合并」),后继项随之入池,不再存在「等人合并」的排队;
前置项因核实不过/失败升级被冻结 → 后继项继续排队,把「前置受阻」写进决策清单
(见 ⑥)——仍禁基于未合分支硬开 stacked。

**同域小单合批(2026-08-10 PM 拍板)**:同一模块/同一对象域的多个小单(缺陷修复、
小改动)合成**一个执行批**,派给同一个开发子 agent 在同一 worktree **串行**处理——
冷启动与起环境是小单成本大头,合批摊薄它;逐单独立 commit、PR 逐单关联、各单独立
流转与关闭,收单核实仍逐单过,禁因合批混台账。合批与「同处改动禁并行」的隐式依赖
规则同向:同域小单本就不许并行,合批串行正是正解。

**并行度上限**:建议 2~3。每个开发子 agent 要起自己的 dev server + 浏览器真机自测,
机器资源是硬上限;超发的结果是全体变慢+环境互踩。上限内按优先级派(P0 先行)。
**批 = 同时在跑的一组子 agent,批内各项必须互无依赖。**

## ② 环境分配与派发

**环境分配表(派发前必做)**:批内每项分配独立 worktree 路径、独立分支名
(`issue-<n>-<slug>`)、独立 dev server 端口、独立数据库文件路径,写成一张表随派发
模板下发。**禁两项共用端口或库文件**——共库污染与幽灵进程是并行开发的头号事故源。
开发子 agent 内部按 st-project-dev-test 派独立自测子 agent 时,复用本项已分配的
worktree dev 环境(「独立的是判断不是环境」),不另占环境分配表名额、不另起 dev
server;派发时机与环境交接细节归 dev-test,此处不展开。

**派发 prompt 一律从 [dispatch-template.md](dispatch-template.md) 实例化**,逐字段
填齐后作为子 agent 的完整初始 prompt。子 agent 冷启动、不共享主会话上下文——
**模板缺什么它就瞎猜什么**,所以:

- 工作项正文**全文粘贴**进模板,不许只给编号或链接;
- 项目约定入口(CLAUDE.md/.claude/ 配置)、纪律摘要、环境分配行、返回报告格式,
  一项不许省;
- 模板自带「实例化检查清单」,派发前逐项打勾。

**派发瞬间由调度员占坑**:把该项逻辑状态切到「AI开发中」并按项目规则设好处理人——
防止重复派发,也让看板即时可见「这项有人在做」。其余细状态流转
(方案确认中/自测报告中/PR审查中)归子 agent 按 st-project-dev-issue 自己切。

## ③ 并行安全(硬)

- **子 agent 间禁共享远端分支**:两个实例推同一远端分支会互相强推顶掉提交
  (st-project-std-git 铁律);一项一分支,分支名按环境分配表;
- **每项独立 worktree**:子 agent 只许改自己 worktree 路径下的文件;派发模板里
  写明「禁触碰 <并行项涉及的模块>」;
- **批间隔离**:新批次的 worktree 一律从**最新 main** 重新拉出,禁复用上一批的
  worktree 或环境;上一批未合入的分支不作为新批的基线(要 stacked 必须先过决策清单);
- 子 agent 中断(超时/崩溃):重派前先核对其分支遗留状态(分支头是否已含其提交、
  内容是否完整),沿用分支必须确认头部干净,拿不准就弃分支重开。

## ④ 监控与看板同步

调度员维护**批次状态表**(自己的账本):

```
| 工作项 | 子agent | 分支 | 状态(待派/开发中/待收单/已收单/退回/升级) | 派发时间 | 备注 |
```

**看板同步纪律**:每次状态流转**即时**反映到工作项看板(逻辑状态见
st-project-std-git 的状态机;项目侧实际标签名由项目配置映射)。看板是人看进度的
唯一窗口——状态表只有调度员自己看得见,只更新状态表不更新看板 = 人眼里整批都在漂。

| 调度事件 | 工作项逻辑状态流转 | 谁动手 |
|---|---|---|
| 派发瞬间 | 待开发 → AI开发中 | 调度员(占坑) |
| 子 agent 报高风险方案待确认 | → 方案确认中 | 子 agent |
| 自测报告挂上 | → 自测报告中 | 子 agent |
| 提 PR + 处理人交接验收侧 | → PR审查中 | 子 agent |
| 收单核实不过,退回补作业 | 状态不动,工作项评论说明退回原因 | 调度员 |
| 升级决策清单 | 冻结当前状态(项目有挂起类标记则打上) | 调度员 |

## ⑤ 收单核实清单(硬)——不采信子 agent 自述

子 agent 的返回报告是**自述不是真值**。「报告全绿」与「平台上真有 PR」是两回事——
收单一律逐项跑命令核对真实平台状态:

| 核对点 | 命令(示例,`<owner>/<repo>` 从 git remote 识别) | 过关标准 |
|---|---|---|
| PR 真实存在且关联本项 | `gh pr view <URL> --json state,title,body,headRefName` | PR 存在且 open;正文含工作项编号;分支名与分配表一致 |
| PR 含真实改动且无夹带 | `gh pr diff <URL> --stat` | 非空;改动文件范围与工作项相符,无并行项/无关文件混入 |
| 提交确属本子 agent | `gh pr view <URL> --json commits` | 提交在、内容对得上;不是别人分支上的旧提交 |
| 测试报告真实挂上 | `gh issue view <n> --comments` | 报告评论存在,含结论与截图,非占位空文 |
| 证据图链真实有效 | `gh api "repos/<owner>/<repo>/contents/<路径>?ref=<SHA>"` | 文件在该 commit 下存在(禁用 curl 打图链判活——私有仓恒 404 是假阴性) |
| 状态标签真实切了 | `gh issue view <n> --json labels` | 处于「PR审查中」对应的项目标签 |
| 处理人真实交接了 | `gh issue view <n> --json assignees` | 已交接验收侧/工作项创建人 |
| 需求符合度清单在盘(反降级门禁,st-project-dev-issue 步骤 4.5) | `gh issue view <n> --comments` | 清单评论存在;逐条三态(✅/⚠️/❌)齐全,无「基本实现」类含糊词;**非 ✅ 条目均有出口链接**(退细化记录 / 平台挂起记录 / 升级记录),链接真实可达 |

**边界:收单核实只验「流程完整性」,不验「功能正确性」。** 功能是否达标归验收线
(st-project-pm-test / 人工测试)判定,调度员不下功能结论——调度员宣布「功能没问题」
既越权也没证据。

**核实不过的处置**:

- 缺报告/缺证据/标签没切/处理人没交接 → **退回原子 agent 补齐,一次机会**;退回时
  写明缺哪几项,不许含糊「重交」;
- 符合度清单缺失、三态不全、含含糊词、或非 ✅ 条目无出口链接 → 同上整项退回;清单
  自述与平台可见事实矛盾(如条目标 ✅ 而报告问题清单里同一功能未闭环)→ 静默降级
  信号,按「自述失真」处置,升级决策清单;
- 同一项**核实第二次仍不过**,或自述与平台状态矛盾(报告说有 PR 实际没有)→ 该项
  停派、冻结状态,升级决策清单——自述失真是最严重的信号,不是补作业能解决的;
- 子 agent 报「开发失败/自测不过」→ **失败一次即升级**,进决策清单,禁止调度员
  安排无限重试(与 st-project-dev-issue 的首次失败升级口径一致)。

### 评审闸门(合并前,2026-08-14 PM 拍板)

收单核实全项过关后、合并之前,调度员为该 PR 派发**独立评审子 agent**,按
[st-project-dev-review](../st-project-dev-review/SKILL.md) 出评审报告——收单核实
明文不看代码,自主合并模式下这是链路上**唯一读代码的关口**,不许跳过。工序纪律
(冷启动只喂工作项全文 + PR diff + 符合度清单三样、档位随 dev-design 分级、发现
三级、两态结论)的权威条款归 dev-review,本处只定挂钩:

- 🔴 阻塞 / 🟡 应修**清零才放行合并**;修复退回原开发子 agent 原分支追加提交,
  复查只查修复点;⚪ 记录不阻塞;
- 静默降级证据坐实(清单 ✅ 与代码矛盾)按「自述失真」处置,二轮复查不清零同——
  升级决策清单,该项冻结;
- **调度员禁亲自评审**——自派自评又是一处角色混线,评审必须下沉独立子 agent;
- 评审结论与报告链接记入批次状态表。

### 调度员自主合并 PR(2026-08-12 PM 拍板)

收单核实清单**全项过关且评审闸门清零**的工作项,其 PR 由调度员**当场直接合并,
不询问、不等人批复**——人从逐 PR 放行中退出,批次吞吐不再卡在等合并上。本条即
st-project-std-git「AI 绝不自行合并 PR(默认铁律)」所要求的**显式成文授权**,
授权范围与生效条件如下:

- **范围只有一种**:本批次派发产生、⑤ 收单核实全项通过、且评审闸门阻塞/应修清零的
  PR。他人的 PR、历史遗留 PR、核实不过/评审未清零/升级中/冻结项的 PR,一律不碰——
  「收单核实 + 评审闸门」双过关是合并的**完整入场券**,「先合了再补核实/补评审」
  不存在;
- **合前三核照做**(std-git §五.4):①分支头包含子 agent 全部提交 ②检查状态达标——
  项目配了 CI 则必须绿,CI 红按「开发失败」口径退回/升级,**不硬合** ③目标分支正确;
- **合并遇冲突不现场解**:调度员禁写代码的边界不破——退回原子 agent 在原分支合 main
  解决冲突,重新走收单核实后再合;
- **合并 ≠ 验收通过**:合并只是代码进主干;功能达标仍归验收线(pm-test/人工)判定,
  工作项状态照走既有状态机(PR审查中 → 验收线),验收打回照旧走 dev-issue 支线 A;
- **合并即关单——验收派生缺陷单专属(2026-08-12 PM 拍板)**:合并的 PR 对应
  **验收派生缺陷单**(含 side_findings 立案的)时,调度员在合并的**同一步**按
  pm-test ⑥「验收派生缺陷 issue 的关闭口径」执行:切状态标签 + 交接处理人
  (交回派单方,默认 issue 创建人)+ 直接 close——自主合并模式下开发子 agent
  提 PR 即收工,调度员不关就没人关,验收批次收口条件「子缺陷全关闭」会永远差一口。
  修没修好仍由批次复测把关,复测该用例仍 ❌ → reopen 原缺陷单(权威条款见
  pm-test ⑥)。**打回的既有工作项单不适用**:不关,按上一条流转回验收线;
- 合并方式与分支清理按 st-project-std-git 及项目约定执行;每笔合并记入批次状态表
  与看板(工作项评论一行:合并了哪个 PR、核实清单过关)。

## ⑥ 决策清单机制——攒批上报,不逐条打断

**时机**:批内全部收单完成后一次性报出。唯一例外:阻塞整批的 P0(平台环境崩、
基线错了)即时报,不等收单。

**入清单的事项类型**(枚举,超出此表的拿不准也入清单):

- 高风险方案待确认(st-project-dev-design 高风险级,子 agent 已停手);
- 基准差异(实现与需求文档对不上,子 agent 报告里带出来的);
- 开发失败 ≥1 次(含自测不过、疑似平台能力受限);
- 依赖等待超批(前置项核实不过/升级被冻结未能合并,后继项压着);
- 收单核实二次不过 / 自述失真;
- 评审闸门升级(静默降级证据坐实 / 二轮复查阻塞·应修不清零,见 dev-review);
- 范围疑似蔓延(子 agent 改动超出工作项边界)。

**每条格式(让人 30 秒能批一条)**:

```
【#<编号> <一句话事项>】
背景:≤2 行——发生了什么、卡在哪(带工作项/PR/报告链接)
建议:A <推荐项+一句话理由> / B <备选+理由>
不批的后果:该项停在 <状态>,影响 <后继项/批次>
```

**纪律**:每条必须给上下文和带倾向的建议选项——只丢问题不给选项 = 把调度工作
推回给人;人批复前该项冻结,**不占并行池名额**,其余项照常推进;人批复后按批复
执行并更新看板,禁止「先斩后奏」。清单发布位置(专用工作项/评论/对话)按项目
约定,本 skill 只定格式与时机。

## 防错要点

- 并行实例间不共享分支:两个实例推同一远端分支会互相覆盖提交;
- 收单必须核实,不许直接采信子实例的自述——「报告全绿」与「平台上真有 PR」是两回事;
- 合并前评审闸门不跳过、调度员不亲自评;阻塞/应修不清零不合并;
- 有依赖的工作项严格排队,宁慢勿乱;拿不准算不算依赖 → 算;
- 决策清单必须给上下文和建议选项,让人 30 秒能批一条;
- 调度员永不亲自下场写代码——下场一次,批次账本就开始失真;
- 项目具体信息(仓库名、标签名、环境地址、端口段)从项目仓库配置/git remote 读取,
  本 skill 与派发模板都不写死。
