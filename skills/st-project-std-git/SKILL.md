# st-project-std-git — Git 与状态流转规范

> 建设状态:可用(未实战) | 批次:第一批 | 性质:规范(全 AI 岗位遵守)

**设计核心:git 事故的共性是"单条命令退出码为 0,整体状态已经坏了"——污染主干、
顶掉别人的提交、弹出别人的 stash、假成功的空操作,全都不在命令报错里。所以本规范的
每条铁律都配一个动手前/动手后的核对动作,把合规从"AI 自觉"改成"可执行、可核对"。**

## 定位与分工(引用不复读)

- 本 skill 是**规范线**:定义全阶段生效的"什么算合格",不描述任何工序怎么走。流程
  (接单→开发→自测→PR→交接)归各流程 skill;任何流程 skill 的 git 动作都默认已加载
  本规范,两边表述不一致时,以更严的一侧为准。
- **状态机与标签映射的权威定义在 [st-project-dev-issue](../st-project-dev-issue/SKILL.md)**
  (逻辑状态机 + 其 project-setup.md §B 的项目标签映射表),本规范不复读、不另画流转
  图。本规范只固化其中与 git 动作绑定的两条语义:**PR 绝不自动关闭工作项**、**合并
  动作默认归人/验收线**(均见 §五)。
- **项目具体值一律不写死**:仓库名从 `git remote get-url origin` 自动识别;主干名、
  分支命名、标签名、账号从项目配置/启用清单读取。本文出现的 main/master 均指
  "项目主干",以项目实际默认分支为准。

## 一、主干保护(最高优先级铁律)

1. **动任何 git 写命令之前,先跑 `git branch --show-current`**;输出是主干 → **停手**,
   先建/切工作分支再动。没有例外,"只改一行""马上改回来"都不是例外。
2. **主干上绝对禁止**:`commit`、`reset`(尤其 `--hard`)、`merge`、`rebase`、
   `restore` / `checkout --` 覆盖工作区、`push`、强推、`clean -f`。一切改动经 PR
   合入主干,一个工作项一个分支。
3. **绝不 cd 进用户主仓库工作区或别人的工作目录跑 git 写操作**。"帮忙同步主干"
   "顺手清理主仓库"这类事归人,不归 AI。
4. 误在主干做了写操作 → **立即停手、如实报告现场**(当前分支、`git status` 输出、
   最近提交),处置等人裁决;不自行 reset/强推"抹掉"——自行补救常造成二次破坏。

## 二、多会话 / 多 agent 并行安全(实战血泪,逐条硬性)

并行开发时,git 的共享状态(远端分支、stash 栈)是事故高发区:

1. **合 PR 前必核分支头包含自己的提交。** 共享分支可能被并行会话 rebase 后强推顶掉,
   顶掉后 PR 页面看起来一切正常,合进去的却不是自己交付的内容。核对动作:记下自己
   最后一次 push 的 commit SHA,合并前先 `git fetch`,再执行
   `git merge-base --is-ancestor <自己的SHA> <远端分支头>`——不成立(或肉眼在
   `git log` 里找不到自己的提交)→ **停手报告,不合**。
2. **并行实例禁止共用远端分支。** 要基于别人(或另一个会话)的分支继续做,走
   **stacked PR**:以该分支为基新开自己的分支、提独立 PR;绝不向同一远端分支追加
   push,更不 rebase + 强推别人正在用的分支。
3. **`git stash pop` / `stash apply` 必须带明确的 stash ref**:先 `git stash list`
   确认哪条是自己的,再 `pop stash@{n}`。裸 `pop` 弹的是栈顶——并行会话也在往同一个
   栈里压,弹出来的可能是别人的现场。并行环境下能不用 stash 就不用:提交到自己的
   工作分支,或用独立 worktree 隔离,都比 stash 安全。
4. **退出码 0 ≠ 干成了。** zsh 下 shell 变量默认不分词,`git stash push $FLAGS` 一类
   写法会把整串参数当一个词传入,命令"成功"返回但实际没干成想干的事。关键 git 操作
   (stash/push/reset/checkout/rebase)之后**必须核对真实状态**:`git status`、
   `git stash list`、`git log <远端>/<分支>`,看到预期结果才算数,禁止只凭退出码或
   "没报错"认定成功。
5. **强推纪律**:主干绝对禁强推;其他分支仅在确认只有自己一个使用者时允许,且用
   `--force-with-lease` 替代 `--force`;对任何可能有并行使用者的分支禁强推(回到
   第 2 条:那本来就不该是共用分支)。

## 三、分支与 worktree 约定

- **一工作项 = 一分支 = 一 worktree**。分支基于主干最新提交建;命名按项目约定
  (建议默认 `issue-<n>-<slug>`,必须含工作项编号)。同一工作项不开第二条分支,
  返修回原分支(流程见 dev-issue 支线 A)。
- **worktree 内只改本 worktree 路径下的文件**。发现自己在改别的目录(主仓库工作区、
  别的 worktree)→ 立即停手、如实报告,不许悄悄挪回来当没发生。
- **新建 worktree 后依赖必须重装/重新初始化**(按项目声明的初始化命令):worktree
  不共享主工作目录的依赖与构建产物,跳过初始化的典型症状是旧依赖**静默**吞掉新配置
  ——不报错、行为陈旧,坏起来无声无息。
- worktree 的项目级操作细节(存放目录、初始化命令清单、并行端口/数据隔离)由各流程
  skill 的启用清单声明(如 dev-issue 的 project-setup.md §C/§D),本规范不写死。

## 四、提交规范

- **message 说清"改了什么、为什么"**,并关联工作项编号。项目有自己的 commit 规范
  按项目的;默认建议 `<类型>(<范围>): <一句话摘要>`(类型如 feat/fix/docs/test/
  chore),正文补动机与影响面。
- **原子提交**:一次提交一件事;无关改动不混进同一提交。
- **add 用明确路径,禁盲加**(`git add -A` / `git add .`):盲加会把临时调试产物、
  计划外目录的改动一起扫进来。提交前 `git status` + `git diff --staged` 过目每个
  文件,确认没有计划外内容(临时产物、密钥/凭据、本地环境文件、依赖目录)。
- 重跑旧脚本可能覆盖已提交的证据/产物文件——staged 里发现计划外的文件改动,先还原
  再提交,不许"顺手一起交"。

## 五、PR 规范

1. **一次改完整再提**:PR 提出即表示"可评审、可合并"——实现完整、所在流程要求的
   自测/证据已达成。禁半成品占位 PR、禁"先提 PR 再慢慢补功能"。评审意见的修复在
   原分支追加提交,属正常迭代,不算半成品。
2. **一 PR 对应一个工作项**;设施/脚本类改动走独立小 PR,不与业务改动互相夹带。
3. **正文关联工作项只写裸编号**(如 `#123`);**绝不写 Closes/Fixes/Resolves 等自动
   关闭语法**——工作项的关闭动作归验收线人工判定(状态语义见 dev-issue 状态机)。
   PR 合并 ≠ 验收通过,自动关闭会让未验收的工作项从看板上消失。
4. **AI 绝不自行合并 PR**(默认铁律)。项目若授权自主合并,必须显式成文(授权范围、
   生效条件、批准人),不存在"上次让合了这次也能合"。被授权合并时,合前三核:
   ①分支头包含自己的全部提交(§二.1);②评审/检查状态达到项目要求——委派场景下
   这含 st-project-dev-review 合并前评审闸门(阻塞/应修清零,2026-08-14 PM 拍板);
   ③合入的目标分支正确。已成文的授权:pm-dispatch 调度员对本批收单核实通过且评审
   闸门清零的 PR 自主合并(2026-08-12 PM 拍板,范围与条件见该 skill「调度员自主
   合并 PR」)。
5. 提 PR 与切状态标签、交接处理人"同一步完成"的纪律归流程 skill(dev-issue 步骤 5),
   本规范不复读;但无论流程怎么走,本节第 3、4 条在任何阶段都不许破。

## 六、证据与临时产物入库边界

按用途三分,判定口诀:**下一轮还会用的是设施,给人看结论的是记录,只服务本次排查的
是临时产物**。

| 类别 | 例子 | 去向 |
|---|---|---|
| 设施 | 可复用脚本、模板、种子/导入数据、CI 配置 | **进仓库**:走 PR 入主干,按项目脚本目录规范归类登记 |
| 记录 | 测试报告、走查记录、截图与图注 | **进工作项**(issue 等发布面),不进代码主干;截图归档与图链形式按 [st-project-std-evidence](../st-project-std-evidence/SKILL.md) |
| 临时产物 | 一次性调试脚本、日志抓取、试验数据、截图工作目录 | **不入库**:放版本忽略路径或会话临时目录,提交前清理 |

- 拿不准算设施还是临时 → 按临时处理,并在工作项里报一句,由人决定要不要沉淀;
- 证据类文件一旦发布(已 push 且被工作项引用)即冻结:禁覆盖、禁删除,重跑任何脚本
  前先确认不会碰到它。

## 七、发布与分支策略:main 之外何时需要更多

**基线不变**:本规范的分支模型始终是 trunk-based——主干是唯一集成分支,工作分支短命
(一工作项一分支,合入即完成使命),PR 合入即集成,夜间回归测的就是主干。本节不推翻前文
任何铁律,只补一个前文没管的问题:**部署环境该跟着什么走**。

**判据一句话(硬)**:合并进主干本身从来不是问题,问题在部署环境追不追主干——
**"正在开发的"与"客户正在用的"不再是同一版本时,进入下一级**。反过来同样成立:
判据没触发就不加机制——发布机制每多一层,都是漂移与漏合的新来源。

### 三级递进

| 级别 | 进入条件 | 部署环境认什么 | 新增机制 |
|---|---|---|---|
| ① main-only | 开发期,尚无客户在用 | 主干任意时点 | 无 |
| ② tag 发布(硬) | 试运行/生产开始 | **只认发布 tag,不追主干** | 发布 tag + 发布台账 |
| ③ release 分支 | 并行维护多条客户在用的版本线 | 各版本线各认各的 tag | `release/x.y` 长命分支 + cherry-pick 纪律 |

**② tag 发布(客户开始用即强制)**:

- 发布动作 = 从主干挑一个**回归全绿**的提交打版本 tag(命名建议 `vX.Y.Z`,规则项目侧
  定),并记一条发布台账:tag、日期、发到哪个环境、包含哪些工作项。台账载体项目侧定
  (工作项系统/文档均可),但必须有;
- 部署环境**只认 tag**:发布 = 把环境切到某个 tag,绝不"拉最新主干"。半成品/未验收
  改动照常合入主干,但不会漂进客户环境——集成节奏与发布节奏就此解耦,前文"合入即
  集成"的纪律一条不改;
- 与验收指纹的关系(呼应 [st-project-pm-test](../st-project-pm-test/SKILL.md) §② 基线
  指纹):验收/值守环境的 serving commit **应当等于当期部署 tag 指向的 commit**;两者
  不等 = 环境漂移,先查发布链路,再谈功能缺陷——陈旧基线是历史上最贵的假缺陷源;
- 回滚 = 把环境切回上一个 tag 并记台账,不是在部署环境上做任何 git 写操作。

**③ release 分支(不到不开,硬)**:

- 唯一进入条件:必须**同时维护两条以上客户在用的版本线**(典型:质保期修 1.0、同时
  开发 2.0,且 1.0 客户暂不升级)。只有一条线在用时,②的 tag 已经够用——**不到③
  绝不开 `release/x.y`**:长命分支每多一条,漂移与漏合的风险面就翻一番;
- 从该版本线最后一个发布 tag 拉出 `release/x.y`;此后该线的发布 tag 打在 release
  分支上,主干继续承载新版本开发;
- **热修默认先进主干、再 cherry-pick 到 release**——保证主干永远是全量真值;主干已
  大改导致无法直接 cherry-pick 时,允许按项目约定反向(release 先修、再合回/重做进
  主干),但**反向流程必须成文**,不存在口头例外;
- cherry-pick 纪律:逐提交挑(不整段 merge)、`cherry-pick -x` 注明源 SHA、指定同步
  责任人;并做定期漏合检查——比对 release 与主干上的热修清单,任何一条只落了一边的
  修复都是事故候选;
- 版本线退役(客户全部升级/质保结束):该 release 分支停止维护并成文归档,不删除。

### 热修路径分级(与 pilot-ops 加急道衔接)

- **②级热修**:修进主干 → 回归 → 打新 tag → 部署。与
  [st-project-pilot-ops](../st-project-pilot-ops/SKILL.md) 热修加急道完全一致:**加急
  压缩的是等待,不是工序**——tag 与台账步骤不可省,省掉它,"生产跑的到底是哪版"
  从此说不清;
- **③级热修**:主干 + cherry-pick **双落**(或成文的反向流),缺一边就是漏合;
- **任何级别禁止直改部署环境**(代码、配置、数据),与 pilot-ops「禁直改生产」同一
  条线,此处从 git 侧再钉一遍:部署环境上不存在 git 写操作这回事。

### 启用声明与升降级

- 项目启用时应声明:**当前处于哪一级、tag 命名规则、发布台账位置**。声明位见
  [st-project-dev-issue](../st-project-dev-issue/SKILL.md) 的启用清单(project-setup.md);
  建议项目侧在其 §C(分支与 worktree)一并补充上述声明行——本规范只定义"要声明
  什么",不代改该清单;
- **②退①**(试运行终止且不再有任何客户环境在用):台账记一条终止记录后停用 tag
  发布,回到 main-only;
- **②进③**(出现第二条必须维护的版本线):从旧线最后一个发布 tag 拉 `release/x.y`,
  同时把 cherry-pick 同步责任人写进项目约定。

## 八、违规处置

发现自己(或接手的现场)违反本规范任何一条:**立即停手 → 如实报告**(违了哪条、
现场状态、影响面)→ 处置等人裁决,不自行"悄悄修复"。事后按
[st-project-meta-retro](../st-project-meta-retro/SKILL.md) 回填:哪条规范没拦住这个
错、要怎么改写才拦得住。

## 附:git 写操作自检卡(动手前过一遍)

```
□ git branch --show-current —— 不是主干
□ 在自己的 worktree/工作分支里,改的文件都在本 worktree 路径下
□ 这条远端分支只有我一个使用者(否则停手,走 stacked PR)
□ add 的是明确路径;git diff --staged 里没有计划外文件
□ stash 操作带明确 ref;关键操作后核对了真实状态,不是只看退出码
□ 提 PR:改动完整、证据已按流程达成、正文只写裸编号、无自动关闭语法
□ 合 PR(仅被显式授权时):分支头包含我的全部提交
□ 发布(②级及以上):部署只经 tag——tag 指向回归全绿的主干提交,台账已记,环境不直追主干
□ ③级热修:主干 + cherry-pick 双落(-x 注明源 SHA);未到③,仓库里没有任何 release 长命分支
```
